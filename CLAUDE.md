# BetterDesk

Кроссплатформенный remote desktop с низкой задержкой. Ядро — Rust.

**Целевая задержка:** 20–30 мс glass-to-glass в LAN, 40–70 мс через интернет при 1080p60.
**Ориентир по качеству:** Parsec / Moonlight. **По функционалу:** AnyDesk.

---

## 0. Как читать этот документ

Этот файл — контракт для любого агента (и человека), который пишет код в этом
репозитории. Он описывает **архитектуру, границы модулей и правила**, а не задачи.
Задачи и этапы — в [docs/roadmap.md](docs/roadmap.md).

Порядок работы: прочитать этот файл → **прочитать §0.1 «Состояние проекта»** →
найти текущий этап в roadmap → работать строго в границах этого этапа.
Не реализовывать фичи из будущих этапов «заодно».

**Запуск без флагов (2026-09-01).** Владелец задал вопрос, который
стоит записать целиком: «можно ли обойтись без сервера, чтобы все
могли юзать сразу без настроек?»

**Без сервера — нельзя, и это не наша недоделка.** Компьютер за NAT
не знает своего внешнего адреса: он видит только `192.168.x.x`, и
узнать настоящий можно единственным способом — спросить кого-то
снаружи. Плюс адрес одной стороны надо передать другой ДО того, как
между ними появилась связь. Сделать один из двух компьютеров сервером
можно только с белым IP и пробросом порта — то есть ровно с той
настройкой, которой хотелось избежать.

**Без настроек у пользователя — можно, и сделано.** Адрес сигналинга
вшит (`bd_core::signaling::DEFAULT_SIGNALING`), порт по умолчанию
7000, справка показывается только по `--help`. Хост запускается
двойным щелчком и печатает ID; клиенту достаточно девяти цифр.
Проверено живьём: 813 кадров, 54.1 fps, 0 потерь, 9.17 мс.

Раньше запуск без `--listen` показывал список флагов вместо работы —
то есть главная функция продукта пряталась за флагом, о котором
человек не знал. `--no-signaling` оставлен для замеров в LAN, где
сервер только добавляет зависимость.

Цена вопроса записана, чтобы к ней не возвращаться: сигналинг — это
2.4 МБ бинарь с `HashMap` из ID в адрес и сообщениями по 512 байт.
**Видео через него не идёт** (§3.1), поэтому бесплатного VPS хватает
на тысячи пользователей.

### Что делать в следующей сессии

**Весь план прошлой сессии выполнен** — битрейт флагами, FEC, прогон
с Максимом, UI со всеми настройками. Порядок ниже **не выбран
владельцем**, а предложен по состоянию кода; начинать с обсуждения.

1. **Честный замер задержки — камерой на 240 fps.** Единственное,
   чем сейчас нельзя мерить glass-to-glass через интернет:
   `ClockSync` уносит половину RTT в смещение часов и показывает
   джиттер (находка 67). Клиент об этом честно предупреждает, но
   **настоящей цифры задержки через интернет у проекта нет**, а это
   главная метрика продукта (§10.4). Метод описан там же: счётчик
   на экране, съёмка двух экранов рядом.
2. **Этап 5 — безопасность.** Записанная дыра: сигналинг недоверен,
   **подставной хост примет любой пароль** и покажет свой экран
   (находка 64, оговорка в коде). Пароль защищает от чужого, но не
   от подмены. Лечится пиннингом ключей устройств — Ed25519 в DPAPI,
   Noise IK поверх QUIC.
3. **Этап 6 — контроллер битрейта.** FEC есть, реакции на реальный
   канал нет: избыточность и битрейт задаются флагом и не меняются,
   что бы ни происходило с потерями. Политика FEC уже едет атомиком
   в `SharedStats` именно ради этого — контроллер сможет крутить её
   без задержки между решением и применением.
4. **Этап 7 — довести оболочку.** Установщик, список сохранённых
   машин, настройки. Сессия из окна уже запускается.

**Что нельзя забыть при прогоне:** хост печатает ID **и пароль**,
диктовать надо оба. Пароль новый при каждом запуске. Обе стороны
ждут по 300 с — и подключения, и ввода пароля.

**Сессия 2026-09-01 (десятая).** Закрыты **этапы 3 и 4** — оба одним
живым прогоном между двумя машинами через интернет: хост в Москве,
клиент во Франции, **1589 кадров, 0 потерь, RTT 68.6 мс**.

До прогона сделаны три вещи, каждая из которых была для него
обязательной:

- **Битрейт и качество флагами** (`--bitrate`, `--quality`). Формула
  масштабирует битрейт от площади кадра — через интернет это неверно
  вовсе: канал задан провайдером, а не разрешением монитора. Побочно
  нашёлся настоящий дефект: `--fps` **не доходил до энкодера**, тот
  настраивался на вшитые 60 (копии разошлись — находка 62);
- **FEC (Reed-Solomon)** — потери кадров 38.8 → **2.9 %** (находка
  66). Заодно закрылся висевший критерий этапа 3: p95 восстановления
  1149 → 117 мс при пороге 200;
- **UDP-STUN** (находка 65) — без него первый прогон провалился:
  стороны били в **TCP-порт** друг друга.

**Прогон нашёл четыре дефекта, и ни один не был сетевым.** Три —
про ожидание человека: хост давал на ввод пароля 60 с (человек
диктует голосом, ушло 70), обещал 300 с ожидания клиента, а ждал 90,
и печатал «Неверный пароль» на служебный зонд, до того как человек
что-либо ввёл. Четвёртый — **отчёт врал**: «медиана 13.99 мс» при
RTT 68.6, то есть быстрее половины RTT (находка 67).

После прогона по решению владельца оболочка **научена запускать
сессию** (§11 больше не мешает — вопрос «работает ли вообще» отвечён)
и собрана в **один `.exe`**: бинари сессии вкомпилированы внутрь.

**Сессия 2026-09-01 (девятая).** Сделан **пароль сессии** — не по
расписанию этапов, а потому что деплой сигналинга создал реальное
свойство: хост стал виден с публичного сервера без всякой
аутентификации. Argon2id, шесть цифр, новый при каждом запуске,
три попытки, проверка ДО первого кадра.

**Живой прогон нашёл дефект с чёрным экраном** (находка 64): клиент
выяснял, нужен ли пароль, читая очередь и выбрасывая первый кадр, —
а первым идёт ключевой, без которого декодер не начнёт. Хост слал
2379 кадров, клиент показывал ноль, без единой ошибки в логе.
Нашлось сравнением двух режимов, `git stash` подтвердил, что регресс
свежий.

Побочно: пароль печатался только в ветке сигналинга, то есть при
`--no-signaling` требовался и не показывался.

**Сессия 2026-09-01 (восьмая).** Сделан **hole punching** — главный
незакрытый пункт этапа 4 (находка 63). Развязка оказалась дешевле
ожидаемого: `quinn::Endpoint::new` принимает готовый `UdpSocket`,
поэтому сокет создаётся заранее, пробивается им же и отдаётся QUIC.
Обе стороны бьют встречно; хост ждёт `PeerWants` перед тем, как
слушать.

**Первый же живой прогон нашёл дефект:** хост регистрировал на
сигналинге свой `--listen`, то есть `0.0.0.0:7000`, и клиент честно
бил в никуда. При этом предупреждение уверенно называло причиной
symmetric NAT — правдоподобно и неверно; такое сообщение хуже, чем
никакого, потому что его проверяют первым. Лечится `reachable_addr`.

Побочно тест поймал то, чего я не предусмотрел: Windows отдаёт
`WSAECONNRESET` на UDP, когда на предыдущий пакет пришёл ICMP «порт
недоступен». Первая версия считала это фатальным — то есть сдавалась
ровно в той ситуации, ради которой написана. На Linux-CI это не
проявилось бы никогда.

**Проверено на одной машине, и это надо помнить:** настоящего NAT там
нет, проверка подтверждает механику, а не пробивание. Вердикт ждёт
двух машин за разными роутерами.

**Сессия 2026-08-31 (седьмая).** Репозиторий выложен на GitHub
(приватный, `spookwy/BetterDesk`), и **первая же чужая машина нашла
дефект, который у разработчика не мог проявиться в принципе**:
`bd-codec` требовал LLVM/libclang для сборки биндингов NVENC — на
машине без NVIDIA, где NVENC не нужен. Клиент не собирался вовсе
(находка 61).

Это четвёртый случай класса «роль требует того, что ей не нужно»
(47, 55, 56), и самый злой: требование было **в сборке**, а не в
рантайме, то есть машина не доходила даже до понятного отказа.

Правка сама оказалась неверной с первого раза и отключила NVENC на
машине разработчика: проверка искала libclang по PATH, а установщик
LLVM под Windows себя туда не прописывает. Проверка воспроизводила не
то состояние — снова находка 32.

Побочно исправлены два лживых сообщения `machine_probe`: оно называло
причиной отсутствие заголовка (который на месте) и не говорило, что
именно подвело хосту.

**Сессия 2026-08-31 (шестая).** Видео, ввод и курсор сведены в
**одно QUIC-соединение** вместо трёх на трёх портах. Это не уборка,
а предпосылка hole punching: пробивать NAT надо с того же порта, на
котором пойдут данные, и три порта означали втрое больше пробивания.

Развязка оказалась дешёвой — состояние сборки и нумерация разделены
по `PayloadKind`, курсор получил свой вид. **Дорогим оказалось
другое:** переписанный цикл ожидания клиента срезал частоту вдвое
(29.8 fps вместо 54.8), не тронув ни задержку, ни потери, ни один
из 263 тестов (находка 60). Нашлось только замером обеих версий
подряд через `git stash`.

Проба под это (`quic_probe`, фаза 2) в третий раз за проект оказалась
неверной раньше проверяемого кода: она мерила глубину приёмной
очереди, вынося вердикт о маршрутизации.

Побочно: в файрволе теперь открывается один порт вместо трёх, и из
инструкции для второй машины исчез симптом «видео идёт, а мышь и
клавиатура нет».

**Сессия 2026-08-31 (пятая).** Начат **этап 4**: поднят сигналинг
(`server/`, отдельный workspace на axum) и подключён к обеим сторонам.
**Подключение по девяти цифрам работает**: хост печатает ID, клиент
вводит только его — адрес выясняется сам.

Осталось честно отметить, чего нет: **hole punching не сделан**, и
через интернет за NAT это ещё не заработает. Причина конкретная —
сокет сигналинга не связан с сокетом QUIC, а пробивание требует бить
с того же порта, с которого пойдут данные.

Две вещи, ради которых он и нужен, работают и проверены живьём:
**сервер сообщает хосту его внешний адрес** (за NAT хост своего
адреса не знает — это простейший STUN) и **хост узнаёт о клиенте**
до того, как тот постучится (без встречного движения NAT не пробить).

`DeviceId` вынесен из оболочки в `bd-core`: он нужен всем троим.

**Сессия 2026-08-31 (четвёртая).** Сделана **оболочка на Tauri v2** —
досрочно, по прямому решению владельца, обоснование в §11. Есть
`bd-shell.exe`: свой ID, пароль сеанса, проверка пригодности машины.
Тема одна, светлая: тёмную убрал по просьбе.

Живой запуск нашёл **три дефекта, каждый из которых давал неверный
экран без единой ошибки** (находка 57) — в том числе значок,
уверенно сообщавший «только просмотр» на машине, которая часом
раньше отдавала экран через `bd-host`.

Лицензии проверены **до** написания кода, как требует §9.1: Tauri
принёс MPL-2.0, и `cargo deny` упал раньше, чем появилась первая
строка экрана (находка 58).

Заодно: проект **взят под git** (103 файла первым коммитом — до

**Важно про монитор разработчика: он 2560×1600, а не 1080p.**
Все цели проекта (15 Мбит/с, ≤ 25 мс) заданы для 1080p. Здесь

**Этап 2, часть 1 — основа ввода (сделано 2026-08-30):**
- `bd-core::input` — `InputEvent`, `KeyCode`, `MousePosition`,
  `SequencedInput`. Портируемо, `#![forbid(unsafe_code)]`, 21 тест
- **Координаты нормализованы** (доли 0.0–1.0), а не в пикселях:
  разрешения клиента и хоста не совпадают, и пересчёт должен быть
  в одном месте — в момент инжекта, где известно настоящее
  разрешение. Пиксельные координаты потребовали бы пересчёта на
  обеих сторонах, а «уезжающий» курсор трудно диагностировать
- **Клавиши — коды USB HID**, а не виртуальные коды Windows: HID
  описывает *физическую* клавишу, и раскладку применяет хост.
  Виртуальные коды зависят от раскладки — на AZERTY `VK_A` это
  физическая `Q`, то есть человек печатал бы не то, что нажимает
- Wire-формат фиксированной длины (9 Б событие, 25 Б с номером
  и меткой времени). Парсер недоверенных данных: проверка длины,
  кода вида, кода кнопки; `NaN` в координате обнуляется (обычный
  `clamp` его не ловит — все сравнения с `NaN` ложны)
- `bd-input::InputTracker` — отслеживание зажатых клавиш, 11 тестов.
  **Асимметрия нажатия и отпускания:** потеря нажатия безобидна
  (человек нажмёт ещё раз), потеря отпускания **необратима** —
  клавиша залипнет навсегда. Отсюда `release_events()`, выдающий
  конкретные идемпотентные отпускания вместо одной команды
  `ReleaseAll`, которая сама может потеряться
- **Модификаторы отпускаются последними.** Отпустить Ctrl раньше C
  в аккорде Ctrl+C — значит дать хосту увидеть одиночное C, то есть
  напечатать букву вместо копирования
- Ёмкость трекера ограничена 8 клавишами: состояние наполняется
  данными из сети, и сторона, шлющая одни нажатия, не должна
  заставлять нас расти без предела
- `bd-input::windows` — `InputInjector` (`SendInput` со скан-кодами
  и `MOUSEEVENTF_ABSOLUTE`), таблица HID→скан-код, захват сообщений
  окна в очередь. Сигнатуры сверены с исходниками `windows` 0.62 (§12)
- Очередь захвата, а не флаг (как у оверлея): лишнее нажатие F9
  безвредно, потерянное отпускание клавиши — нет

**Этап 2, часть 2 — путь ввода замкнут (сделано 2026-08-30):**
- `bd-render` собирает **сырые** сообщения окна в очередь и отдаёт
  их наружу. Разбирать их там нельзя: `bd-render` не вправе зависеть
  от `bd-input` (§4.2.5), а окно вывода не должно понимать формат
  событий. Мост живёт в `bd-bench::input_bridge` — он видит оба
  крейта; в продукте переедет в `bd-client`
- `WM_SYSKEYDOWN`/`WM_SYSKEYUP` обрабатываются наравне с обычными:
  именно ими приходит **Alt**. Без них Alt+Tab не работал бы,
  а сам Alt остался бы зажатым — то самое залипание
- F9 перехватывается **до** ветки ввода: это наша горячая клавиша,
  и слать её на хост незачем
- `WM_KILLFOCUS` → `ReleaseAll`, но в сеть уходит **не** он, а
  конкретные отпускания из трекера: `ReleaseAll` — команда, которая
  может потеряться, а отпускания идемпотентны
- Обратный канал — **отдельный экземпляр** транспорта с тем же
  профилем канала. Идеальный обратный канал скрыл бы главную
  проблему ввода — потерю отпускания
- По завершении сессии всё зажатое отпускается принудительно:
  иначе человек за хостом остался бы с зажатым Ctrl и чинил это
  вслепую
- `input_probe` — 6 проверок, из них живой `SendInput` под флагом
  `--inject`. Проба проверена на способность провалиться

**Этап 2, часть 3 — курсор (сделано 2026-08-30):**
- `bd-core::cursor` — `CursorPosition` (9 Б), `CursorShape`,
  `CursorShapeCache`. 16 тестов
- **Курсор идёт отдельным каналом, а не вморожен в кадр.** Картинка
  отстаёт на задержку пайплайна; позиция весит 9 байт и успевает
  раньше. Иначе человек видел бы, как стрелка тянется за его рукой
- **Позиция и форма разделены.** Позиция меняется сотни раз в
  секунду и весит байты, форма меняется редко и весит килобайты.
  Позиция ссылается на форму номером, клиент кеширует по нему
- Форма отправляется **раньше** позиции, которая на неё ссылается:
  обратный порядок давал бы кадр с невидимым курсором на каждой
  смене формы
- DXGI отдаёт три формата курсора, и все три пришлось поддержать.
  Монохромный — **две маски по 1 биту** (AND и XOR), буфер вдвое
  выше курсора; путать высоту буфера с высотой курсора нельзя
- Конверсия в BGRA — чистая функция `to_bgra`, 10 тестов. Ошибка
  здесь даёт не отказ, а неправильную картинку
- Инвертирующие пиксели (`MaskedColor`, монохромный `AND=1 XOR=1`)
  рисуются **прозрачными**. Сначала были чёрными — это давало
  сплошной чёрный квадрат вместо текстового курсора (находка 36б).
  Настоящая инверсия требует `ID2D1DeviceContext`, то есть переделки
  всего слоя Direct2D; прозрачность даёт верную форму, теряя
  контраст на тёмном фоне
- Цель вывода Direct2D создаётся с **96 DPI**, а не с нулём.
  Ноль означает DPI системы, и при масштабе 150 % курсор рисовался
  в полтора раза больше (находка 36а)
- Курсор и оверлей рисуются **одним проходом** Direct2D: два
  `BeginDraw` в одну цель — ошибка D2D, а два прохода стоили бы вдвое
- Битмап курсора отпускается вместе с целью вывода перед
  `ResizeBuffers` — та же причина, что у оверлея
- Живой прогон: 8 позиций, 3 смены формы, все применены

  горячий путь не попадает
- Ни `send`, ни `receive` не блокируют. Полная очередь отправки —
  сигнал **дропнуть кадр**, а не ждать (§5.3)
- Это снимает дефект из находки 34: приём идёт своим темпом, а не
  в такте энкодера
- Зависимости: `quinn` 0.11, `rustls` 0.23 на `ring`, `rcgen`.
  Лицензии проверены **до** написания кода — `licenses ok`
- Таймаут простоя 8 с (критерий этапа требует пережить разрыв 2 с),
  keep-alive 5 с (NAT закрывает отображение секунд через 30)
- **Сертификат самоподписанный, клиент принимает любой.** Шифрование
  есть, аутентификации стороны нет — MITM возможен. Это записанный
  временный компромисс до этапа 5 (§7.3, §8.1); проверяющий назван
  `AcceptAnyServer`, чтобы не забылось
- `quic_probe` — настоящее соединение через UDP-сокет. **Живой
  результат: 300 кадров отправлено, 300 принято, 0 искажений,
  2100 датаграмов, RTT 0.17 мс, 11.9 Мбит/с**

**Этап 3, часть 2 — QUIC в пайплайне (сделано 2026-08-30):**
- `bd-bench::any_transport` — `AnyTransport`: заглушка или QUIC
  за одним API. Enum, а не trait: транспортов ровно два, оба
  известны при компиляции, а динамическая диспетчеризация в горячем
  пути ни к чему
- **Заглушка не выброшена** и не будет: она единственный способ
  измерить пайплайн отдельно от канала. Цифра «3.0 мс из 25»
  получена ею, и через сеть она утонула бы в шуме
- `VideoDirection` — кто шлёт, кто принимает. Понадобился после
  того, как обе стороны, шлющие видео с номера 0, начали собирать
  кадры друг друга (находка 39)
- `QuicTransport::send` возвращает номер кадра, как у заглушки:
  вызывающему он нужен, чтобы сверить пришедший кадр с оригиналом.
  Номер присваивается при постановке в очередь и **не растёт**, если
  кадр отброшен, — иначе приёмник счёл бы его потерянным
- **Живой прогон через QUIC: 733 кадра, 0 ошибок целостности.**
  Задержка не измеряется — см. находку 40

**Этап 3, часть 3 — задержка между машинами (сделано 2026-08-30):**
- Wire-формат вырос до **24 байт**, версия протокола → **2**:
  добавлена метка времени захвата. Без неё приёмник не знает,
  когда кадр родился, и glass-to-glass не считается (находка 40)
- Метка идёт в **каждом** фрагменте, а не только в первом. Восемь
  байт при полезной нагрузке 1146 — это 0.7 %, и такой ценой разбор
  остаётся одинаковым для всех фрагментов
- `bd_core::ClockSync` — оценка смещения часов **по минимуму
  наблюдённых разниц**. Задержка всегда положительна, значит
  наименьшая разница `наши_часы − чужие_часы` содержит наименьшую
  задержку и ближе всего к чистому смещению
- Окно скользящее (256 наблюдений ≈ 4 с): иначе одно старое
  наблюдение навсегда испортило бы все последующие измерения, а
  часы двух машин дрейфуют
- Метод **не заменяет NTP** и не даёт абсолютной точности. Он даёт
  то, что нужно: разницу задержек внутри окна. Ограничение записано
  в тесте `constant_offset_is_removed` — при постоянной задержке
  метод честно показывает нули
- **Живой прогон через QUIC: медиана 21.6 мс, 836 кадров.** Первое
  честное измерение задержки между двумя процессами по сети

**Этап 3, часть 4 — джиттер-буфер (сделано 2026-08-31):**
- `bd-transport::jitter` — `JitterBuffer`, 10 тестов. Удержание
  измеряется **во времени**, а не в кадрах: при переменном битрейте
  «два кадра» — это то 33 мс, то 5 мс, а время прямо сопоставимо
  с бюджетом задержки
- Удержание = разброс задержек (p95 минус минимум) по окну в 120
  наблюдений. Не максимум — один выброс на Wi-Fi раздул бы буфер
  навсегда; не среднее — сгладить надо именно хвост
- **На идеальном канале удержание нулевое.** Это главное свойство,
  и оно защищено тестом: буфер — чистая задержка, и держать без
  причины значит платить ни за что
- Потолок 150 мс: при большем работать невозможно, и рваная
  картинка честнее плавной, но неотзывчивой
- Очередь упорядочена по номеру кадра, а не по приходу: пакеты
  обгоняют друг друга, и порядок прибытия дал бы декодеру
  перемешанный поток
- **Буфер по умолчанию выключен** (`--jitter-buffer`) — по итогам
  измерения, см. находку 42

### Ошибки и находки — чтобы не повторять

1. **`license = "proprietary"` ломает cargo-deny.** Это не валидный SPDX,
   из-за него наши же крейты считались «нелицензированными» и проверка
   падала. Правильно: не указывать `license` вовсе + `[licenses.private]
   ignore = true` в deny.toml.
2. **`wildcards = "deny"` срабатывает на внутренние path-зависимости.**
   У них нет версии, и это норма для workspace. Нужен
   `allow-wildcard-paths = true`; правило продолжает работать для внешних.
3. **`cargo fmt --check` без `--all` падает** с «Failed to find targets»
   при наличии `[[bin]]` рядом с lib. В командах и CI — всегда `--all`.
4. **Проверять запрет GPL надо настоящим GPL-крейтом.** Первая попытка
   взяла `readability` (оказался MIT) — проверка «прошла» и создала ложное
   чувство защищённости. Настоящая проверка на `sequoia-openpgp` (LGPL-2.0)
   дала ожидаемое `error[rejected]` и ненулевой код возврата. Урок общий:
   **тест защиты, который не падает, ничего не доказывает** — убедиться,
   что он умеет падать.
5. **Dev-зависимости cargo-deny по умолчанию не проверяет.** Это корректно
   (они не линкуются в продукт), но при проверке самой защиты сбивает с толку.
6. **Сигнатуры `windows`-крейта отличаются от MSDN.** В версии 0.62
   `IDXGIOutput::GetDesc()` и `IDXGIOutputDuplication::GetDesc()` возвращают
   структуру **по значению**, а не через out-параметр, как в C++.
   `D3D11CreateDevice` принимает `HMODULE::default()`, а не `None`.
   Вывод общий: сверяться с исходниками крейта в
   `~/.cargo/registry/src/*/windows-*/src/Windows/Win32/...`,
   а не только с документацией Microsoft (§12).
7. **`LastPresentTime == 0` в `DXGI_OUTDUPL_FRAME_INFO` означает, что
   изменился только курсор**, а не содержимое экрана. На практике таких
   кадров ~90% при обычной работе. Их не нужно перекодировать — экономия
   и битрейта, и такта энкодера.
8. **Проба захвата на статичном экране даёт 0 кадров, и это правильно.**
   DXGI отдаёт кадр только при изменении картинки; в покое честно
   возвращает `DXGI_ERROR_WAIT_TIMEOUT`. Первый прогон легко принять
   за поломку — при замерах нужна реальная нагрузка на экран.
9. **PowerShell портит кириллицу при `-RedirectStandardOutput`.** Вывод
   проб читать прямым запуском, а не через перенаправление в файл.
10. **bindgen не переносит функциональные макросы и `static const`.**
    Версии структур (`NV_ENC_*_VER`) и GUID кодеков пришлось выписать
    вручную в `versions.rs` и `guids.rs`. Ошибка в номере **не даёт
    ошибки компиляции** — только `NV_ENC_ERR_INVALID_VERSION` в рантайме.
    Отсюда правило: после обновления заголовка сверять номера заново.
11. **Имена модулей в биндингах непредсказуемы.** Большинство
    перечислений bindgen кладёт в модуль с подчёркиванием
    (`_NVENCSTATUS`, `_NV_ENC_DEVICE_TYPE`), но `NV_ENC_TUNING_INFO` —
    без него. Гадать бесполезно: смотреть сгенерированный
    `target/*/build/bd-codec-*/out/nvenc_bindings.rs`.
12. **ГЛАВНАЯ НАХОДКА: совместимость NVENC односторонняя.**
    Приложение со СТАРЫМ SDK работает на новом драйвере, но не наоборот.
    Драйвер 591.91 (API 13.0) отверг заголовки SDK 13.1 с
    `NV_ENC_ERR_INVALID_VERSION` на первом же `nvEncOpenEncodeSessionEx`.

    **Моя ошибка по пути:** я решил, что раз NVENC декларирует обратную
    совместимость, то расхождение в минорной версии безопасно, и
    ослабил проверку до мажорной. Проба это опровергла. Затем я
    попытался «договориться» — подставить версию драйвера в поля
    `version` структур. **Тоже не сработало.** Единственное решение —
    собираться с заголовками не новее драйвера.

    Урок общий: **декларация совместимости в документации не заменяет
    проверку на живом железе.** Проба, которая только загружает API,
    ничего не доказывает — нужна та, что открывает сессию.
13. **Заголовки NVENC доступны под MIT** в проекте nv-codec-headers
    (FFmpeg). Это лучше официального SDK сразу по двум причинам:
    лицензия позволяет вендорить, и можно выбрать версию под драйвер.
    См. `vendor/nvcodec/README.md`.
14. **Динамическая загрузка DLL вместо линковки.** `nvEncodeAPI64.dll`
    грузится через `libloading`. Иначе бинарник не запустился бы на
    машине без NVIDIA GPU — вместо понятного сообщения пользователь
    получил бы отказ загрузчика Windows.
15. **`cargo build` не всегда обновляет бинарник при смене build.rs.**
    Дважды запускалась старая версия пробы, что уводило диагностику
    в сторону. При странных результатах — удалить `.exe` и собрать заново.
16. **Порядок полей структуры = порядок освобождения ресурсов.**
    Rust уничтожает поля сверху вниз. В `NvencEncoder` поле `session`
    сначала стояло первым, поэтому энкодер закрывался раньше буфера
    битстрима и регистраций текстур — их освобождение возвращало
    `NV_ENC_ERR_DEVICE_NOT_EXIST` (код 5), ресурсы драйвера текли.

    Правило для FFI-структур: **владелец объявляется последним.**
    Ошибка тихая — компилятор её не видит, а проявляется только
    предупреждением при выходе, которое легко пропустить.
17. **`&mut self` в вспомогательном методе съедает всю структуру.**
    `resource_for(&mut self) -> &RegisteredResource` удерживал
    заимствование до конца кодирования и блокировал чтение остальных
    полей. Решение: метод `ensure_registered` ничего не возвращает,
    а ссылка берётся отдельным неизменяемым доступом. Типичная
    ситуация в Rust, стоит помнить при работе с кешами.
18. **Декодер отдаёт 1920×1088, а не 1920×1080.** H.264 кодирует
    макроблоками 16×16, а 1080 на 16 не делится. MFT сообщает
    `MF_E_TRANSFORM_STREAM_CHANGE` и переходит на выровненную высоту.
    Это норма, а не сбой. **Следствие для рендера:** кадр надо
    обрезать до настоящего разрешения, иначе внизу будет полоса
    мусора в 8 строк. Настоящий размер — из `MF_MT_FRAME_SIZE`
    выходного типа, а не из настроек, которые мы задали сами.
19. **Кадр приходит срезом текстуры-массива, а не отдельной текстурой.**
    `IMFDXGIBuffer::GetSubresourceIndex()` возвращает индекс, и
    игнорировать его нельзя: рендер будет показывать всегда нулевой
    слой, то есть один и тот же старый кадр. Индекс проносится
    наружу в `DecodedFrame::subresource()`.
20. **Замер времени декода без синхронизации с GPU обманывает.**
    `ProcessOutput` возвращается за 0.03 мс, потому что GPU ещё
    работает. Настоящая цифра (0.21 мс) видна только после ожидания
    `ID3D11Query` типа EVENT. При этом `GetData` возвращает `S_FALSE`,
    пока не готово, а windows-rs считает **успехом любой
    неотрицательный HRESULT** — цикл ожидания на `Result` завершился
    бы сразу же. Проверять надо записанное значение, а не `Ok`.
21. **Декодер, отдающий пустые поверхности, выглядит как исправный.**
    Ошибок нет, тайминги отличные. Поэтому проба читает пиксели
    одного кадра и проверяет разброс яркости. Это тот же урок, что
    и находка 4: проверка, которая не умеет провалиться, ничего
    не доказывает.
22. **`MFStartup`/`MFShutdown` глобальны на процесс.** Декодеров может
    быть несколько (многомониторность, этап 11), и выключение MF при
    живом MFT даёт россыпь `MF_E_SHUTDOWN` в неожиданных местах.
    Отсюда счётчик пользователей в `runtime.rs`, а не «включить
    один раз и не выключать».
23. **Поверхности декодера по умолчанию непригодны для шейдера.**
    MFT создаёт текстуры с одним флагом `D3D11_BIND_DECODER` (`0x200`),
    и `CreateShaderResourceView` на них возвращает `E_INVALIDARG`.
    Лечится атрибутом `MF_SA_D3D11_BINDFLAGS` со значением
    `BIND_DECODER | BIND_SHADER_RESOURCE` на **выходном потоке** MFT.
    Важен момент: выставлять **до** `MFT_MESSAGE_NOTIFY_BEGIN_STREAMING`,
    потому что пул поверхностей выделяется именно там, и после этого
    флаги не изменить. Без атрибута рендеру пришлось бы копировать
    каждый кадр в свою текстуру — лишний проход по 3 МБ 60 раз
    в секунду, то есть ровно то, что запрещает §4.2.3.
24. **Разбивка по стадиям молча теряла декод.** `breakdown()` строил
    интервалы между *соседними* стадиями перечисления. Пока нет
    транспорта, `Sent` и `Received` не отмечены — и время декода,
    попадавшее в несуществующую пару `Received → Decoded`, исчезало
    из отчёта. Итог при этом оставался верным, поэтому дефект
    не проявлялся ничем, кроме отсутствующей строки в таблице.
    Теперь пары строятся по фактически отмеченным стадиям, и есть
    тест `breakdown_sums_to_total`. Урок: **отчёт, который не обязан
    сходиться с итогом, рано или поздно разойдётся с ним незаметно.**
25. **Окно вывода на захватываемом экране создаёт петлю обратной
    связи.** Каждый `Present` меняет содержимое экрана, DXGI отдаёт
    новый кадр, тот выводится в окно — и так по кругу на предельной
    частоте. В прогоне это выглядело как 213 fps при мониторе 60 Гц.
    **На задержку не влияет** (каждый кадр измеряется отдельно), но
    fps в таком прогоне бессмыслен. Для честного fps — `--monitor`
    на соседний экран и окно туда же.
26. **ГЛАВНАЯ НАХОДКА СЕССИИ: `recover()` не работал вообще.**
    Код обработки `ACCESS_LOST` был написан с самого начала и
    считался рабочим. На деле в нём было **две** ошибки подряд:

    - пересоздавалось **устройство D3D11**, хотя `ACCESS_LOST` —
      это потеря дупликации, а не устройства (то было бы
      `DEVICE_REMOVED`). На устройстве захвата живут энкодер,
      декодер и окно вывода: подмена оставляла весь стек с
      мёртвым указателем;
    - новая дупликация создавалась **до** освобождения старой.
      DXGI разрешает одну дупликацию на выход в процессе, поэтому
      `DuplicateOutput` возвращал `E_INVALIDARG`. Присваивание
      полю не спасает: старое значение освобождается только после
      того, как новое уже создано. Отсюда `Option` у поля.

    Вторая ошибка перекрывала первую — падало раньше, чем успевало
    навредить. **Итог: первый же UAC-диалог оборвал бы сессию.**

    **Почему дожило до сих пор.** `ACCESS_LOST` не случается по
    команде, и все прогоны показывали «Восстановлений: 0». Нулевой
    счётчик читался как «всё хорошо», хотя означал лишь, что путь
    ни разу не исполнялся. Тот же урок, что и находка 4, в новой
    форме: **ноль срабатываний — это не «работает», это «неизвестно».**

    Проверяется пробой `recover_probe`, которая вызывает `recover()`
    принудительно. Проба **сначала была запущена на сломанной версии
    и провалилась**, и только потом на исправленной — иначе она бы
    ничего не доказывала.

27. **Канал с задержкой ломает наивное «отправил → сразу забрал».**
    Первая интеграция транспорта в `loopback` сравнивала пришедший
    кадр с только что закодированным. На профиле `perfect` это
    работало: задержки нет, и `receive` отдавал ровно тот кадр, что
    ушёл строкой выше. На `mobile` (80 мс) проба немедленно
    напечатала «транспорт исказил кадр 0».

    **Транспорт был ни при чём.** Приёмник честно отдал кадр,
    отправленный 80 мс назад, — а сравнивался тот с текущим. Дефект
    был в пробе, и он же скрывал вторую, более важную ошибку:
    тайминги брались от свежего кадра, а не от доставленного, то есть
    задержка измерялась бы по пути, который кадр не проходил. Лечится
    журналом отправленных кадров (номер + тайминги + байты), из
    которого доставленный кадр забирает свои.

    **Урок:** сверка целостности поймала не порчу данных, ради
    которой писалась, а ошибку в собственной логике измерения. Это
    аргумент писать такие проверки даже когда «ломаться нечему» —
    и не сворачивать проверку, когда она сработала неожиданно.
    Второй урок: **профиль без задержки — не проверка транспорта.**
    Задержка меняет структуру потока управления, а не только цифры.

28. **ГЛАВНАЯ НАХОДКА СЕССИИ: 3 % потерь датаграмов = 51 % потерь
    кадров.** Прогон `--link mobile` (3 % потерь, как в профиле
    §10.3) потерял 663 кадра из 1290. Это не сбой, а арифметика:
    кадр 1080p идёт ~24 фрагментами, вероятность дойти целиком —
    0.97²⁴ ≈ 48 %. Потеря **одного** датаграма убивает **весь** кадр,
    потому что неполный кадр не ждётся и не переспрашивается (§5.3).

    **Следствие для этапа 6.** FEC для видео переходит из
    «желательно» в «обязательно»: без него мобильный интернет даст
    не «слегка хуже картинку», а неработоспособную сессию. Цель
    проверяемая: при 3 % потерь доля потерянных кадров должна упасть
    с 51 % до единиц процентов.

    **Следствие для этапа 3.** Крупные ключевые кадры опаснее, чем
    кажется: чем больше фрагментов, тем ниже шанс дойти. Это ещё один
    довод за Intra Refresh вместо полных IDR (§5.2) — и повод
    подумать о приоритетной защите первых фрагментов кадра.

29. **Вердикт пробы сравнивал не с тем.** На профиле `mobile`
    `loopback` печатал «❌ ВЫШЕ 25 мс», складывая задержку пайплайна
    с нарочно внесённой задержкой канала. Порог 25 мс задан **для
    localhost** (docs/roadmap.md), поэтому такой вердикт означал
    лишь, что эмуляция работает — но выглядел как провал критерия
    этапа. Исправлено: при ненулевой задержке канала оценивается
    пайплайн за её вычетом (5.92 мс из 85.92).

    **Урок:** проверка, выносящая вердикт не по тому, что она
    измеряет, хуже отсутствия проверки — она убедительна и при этом
    врёт. Родственно находкам 4 и 26, но с другой стороны: там
    проверка не умела провалиться, здесь — проваливалась зря.

30. **ГЛАВНАЯ НАХОДКА: лишние кадры воруют битрейт, и это видно
    глазом.** Пользователь сообщил о периодической пикселизации:
    вся картинка грубеет крупными квадратами на ~0.5 с.

    **Первая гипотеза была неверной.** Предполагались полные IDR
    (тем более что `intra_refresh` в конфиге объявлен, но к NVENC
    **не применяется** — дефект настоящий, просто не тот).
    `quality_probe` показала: за 40 с ключевой кадр **один**, и
    всплески к нему не привязаны. Правка под IDR не дала бы ничего.

    Настоящая причина — в частоте. DXGI отдаёт кадр на каждое
    изменение экрана, а не 60 раз в секунду; при активной работе
    это 150–250 кадров/с, и все шли в энкодер. **CBR делит
    фиксированные 15 Мбит/с на фактическое число кадров:**

    | Кадров/с | Медиана разностного кадра |
    |---|---|
    | 222 | 2 301 Б |
    | 32 | 12 071 Б |

    Разница в 5.2 раза при одном и том же битрейте.

    **Исправлено шестью правками:** `bd_core::FrameLimiter` (новый
    модуль `pacing.rs`), `maxQP = 38`, VBV 1.5 кадра вместо 1.0,
    `enableAQ = 1`, `maxBitRate = averageBitRate` для CBR,
    явное `enableLookahead = 0`. Результат: **+45 % бит на кадр**
    при той же сцене (12 071 → 17 540 Б), задержка не пострадала.
    **Пикселизация исчезла полностью** — подтверждено визуально.

    **Два урока.** Первый: гипотеза, объясняющая симптом, ещё не
    является причиной — проба опровергла её за один прогон, дешевле
    любой правки вслепую. Второй, более коварный: **счётчик fps
    всё это время показывал причину**, но на него перестали
    смотреть, объявив «неинформативным в этом прогоне» из-за петли
    обратной связи (находка 25). Отмахнувшись от метрики один раз,
    легко не заметить, что она сообщает о другом.

31. **Предупреждение в логе — это не обработка события.** `recover()`
    честно писал `warn!` «разрешение изменилось — стек кодеков надо
    пересоздать», и это читалось как «случай учтён». На деле
    предупреждение было единственным, что происходило: `loopback`
    брал `size` один раз при старте и после восстановления
    продолжал с прежними энкодером и декодером.

    **Отказа при этом не было бы.** NVENC не меняет геометрию на лету
    (`nvEncReconfigureEncoder` покрывает битрейт, но не размер), а
    декодер ждёт SPS прежней геометрии — то есть смена разрешения
    дала бы не ошибку, а поток мусора на экране. Это хуже падения:
    падение видно сразу.

    Разделение обязанностей само по себе верное — капчурер не вправе
    пересоздавать чужой стек, он лишь сообщает. Ошибка в том, что
    у сообщения не оказалось адресата. **Правило: если код пишет
    «вызывающий обязан», надо пойти и проверить, что вызывающий
    это делает** — комментарий об обязанности не является её
    исполнением.

    Исправлено в `loopback`: размер перечитывается после каждого
    `recover()`, при изменении энкодер и декодер пересоздаются на
    том же устройстве (устройство `recover` намеренно не трогает),
    журнал отправленных кадров очищается — кадры в пути относятся
    к прежней геометрии. Проверяется второй фазой `recover_probe`,
    которая строит стек на двух разных размерах подряд. Проба
    **сначала была прогнана на заведомо невозможном размере и
    провалилась** (exit 1), и только потом на рабочем.

    Побочная находка: **декодер MFT создаётся даже на 1×1** без
    единой жалобы. Геометрию он не валидирует при создании, так что
    «декодер открылся» ничего не говорит о разумности размера —
    проверять надо энкодером.

32. **ГЛАВНАЯ НАХОДКА: UAC ронял процесс — и нашёл это живой прогон,
    а не тесты.** Сразу после того, как находка 31 была объявлена
    закрытой, пользователь запустил `loopback` и вызвал UAC. Процесс
    завершился.

    **Две ошибки, одна поверх другой:**

    - `DuplicateOutput` при secure desktop отвечает
      **`E_ACCESSDENIED`**, а не `DXGI_ERROR_ACCESS_LOST`. Этот код
      не был разобран в `hresult_to_error` и попадал в
      `CaptureError::Platform`, у которого `is_recoverable() == false`.
      То есть штатнейшее событие Windows числилось фатальным;
    - и даже будь классификация верной, в `loopback` стояло
      `capturer.recover()?`. Восстановление предполагалось удачным
      с первой попытки. Но пока пользователь смотрит на UAC-диалог,
      дупликация не создастся **ни с какой** попытки — нужно ждать,
      а `?` завершал процесс.

    Исправлено: вариант `DesktopUnavailable` + признак
    `needs_backoff()` (повтор без паузы сжёг бы процессор десятками
    тысяч вызовов в секунду), а в `loopback` — цикл ожидания с шагом
    100 мс и потолком 60 с, с прокачкой оконных сообщений внутри
    (иначе Windows пометит окно зависшим) и запросом ключевого кадра
    после возврата (декодер потерял опору).

    **Главный урок — про сами проверки.** `recover_probe` вызывала
    `recover()` на обычном рабочем столе, где он всегда успешен.
    Проба была зелёной ровно потому, что воспроизводила **не то
    состояние**: не «UAC на экране», а «всё в порядке, пересоздай».
    Синтетическая проверка проверила механику пересоздания и ничего
    не сказала о том, при каких условиях оно вызывается.

    Это уточняет находку 26. Там урок был «ноль срабатываний — это
    не работает, а неизвестно». Здесь — следующий слой: **сработавшая
    проверка тоже может ничего не значить, если воспроизводит не то
    состояние, ради которого писалась.** Живой прогон нашёл за одну
    минуту то, чего не увидели ни компилятор, ни clippy, ни 80
    тестов, ни специально написанная проба.

    Теперь `E_ACCESSDENIED` покрыт модульным тестом в
    `windows/mod.rs`, и тест **проверен на способность провалиться**:
    с откаченной правкой он падает. Но тест — это фиксация уже
    понятого дефекта, а не его поиск: нашёл его человек, нажавший UAC.

    **Следствие для этапа 8.** Secure desktop из пользовательской
    сессии не захватывается в принципе (§5.1) — сейчас картинка на
    время UAC замирает, и это лучшее, что возможно без службы. Полное
    решение — захват из службы, и находка добавляет к нему требование:
    служба обязана переживать эти переходы, а не только запускать
    агента.

33. **Дорогая проверка не проводится — и критерий висит месяцами.**
    Критерий «30 минут без утечек» оставался последним незакрытым
    не потому, что код был не готов, а потому, что проверка требовала
    получаса ручного шевеления окон: DXGI отдаёт кадр только на
    изменение экрана (находка 8), и на статичном рабочем столе
    прогон измеряет пустоту. Пользователь честно сказал: «лень над
    ПК сидеть и тыкать».

    Это не лень, а верный сигнал. **Проверку, которую неудобно
    проводить, не будут проводить** — и она перестаёт защищать,
    оставаясь в списке критериев как успокоительная запись.

    Лечится не дисциплиной, а инструментом: флаг `--agitate`
    поднимает маленькое окно без рамки, которое само меняет цвет и
    геометрию. Полчаса прогона больше не требуют присутствия
    человека. Проверено: 20 с с агитатором дали **1047 кадров**
    против **143** без него при том же бездействии.

    Агитатор по умолчанию выключен: он рисует поверх экрана и мешает
    работать, а короткие замеры и так делаются при живой работе.
    Проверено, что без флага поведение прежнее — иначе инструмент
    удобства незаметно менял бы цифры всех прогонов.

    Побочно добавлено поле `MonitorInfo::origin` (координаты монитора
    в виртуальном рабочем столе): без него нельзя разместить окно на
    нужном экране. Понадобится и дальше — для пересчёта координат
    мыши (этап 2) и многомониторности (этап 11).

35. **Проверка целостности сама оказалась неверной: «77 искажённых
    событий» при исправном транспорте.** Первый прогон `input_probe`
    сообщил, что транспорт портит 77 событий ввода из 194. Цифра
    выглядела катастрофой — порча данных в канале ввода означала бы,
    что клики уходят не туда.

    **Транспорт был исправен.** Координаты мыши кодируются в `u16`
    (точность 1/65536 экрана), поэтому `0.25` возвращается как
    `0.24998856`. Формат отработал ровно так, как задуман, а проба
    сравнивала через `==` и объявляла это искажением. Искажались
    только события с координатами — клавиши и прокрутка проходили
    точно, что и указало на причину.

    Отладка заняла один запуск: вместо правки вслепую сравнил
    туда-обратно три вида событий и увидел, что расходятся ровно те,
    где есть `f32`.

    Исправлено методом `InputEvent::eq_within_wire_precision` в
    `bd-core`: сравнение с тем допуском, который формат обещает.
    Метод покрыт **двумя** тестами — что он принимает потерю точности
    и что он **не** принимает настоящую разницу (0.05, другую кнопку,
    другое состояние). Второй важнее: допуск, сделанный без него,
    легко превращается в «всегда равно», и проверка целостности
    перестаёт ловить что-либо вообще.

    **Урок продолжает находку 27**, где сверка целостности поймала не
    порчу данных, а ошибку в логике измерения. Здесь то же самое в
    третий раз: **проверки ошибаются чаще, чем проверяемый код** —
    у них нет своих проверок. Практическое следствие: увидев отчёт
    о поломке, сначала подтвердить её независимо, и только потом
    чинить. Правка вслепую здесь «исправила» бы исправный транспорт.

    Побочно: `--fps`-подобных флагов у проб становится много, поэтому
    `parse_flag` вынесен отдельно от `parse_arg`.

36. **Три бага курсора и окна, найденные пользователем за один
    прогон.** Все три прошли мимо 183 тестов и мимо моих собственных
    живых проверок. Общее у них то, что каждый виден **только
    глазом** — ни один не даёт ни ошибки, ни неверной цифры.

    **(а) Курсор слишком большой.** Direct2D работает в
    аппаратно-независимых пикселях, а цель вывода создавалась с
    `dpiX/dpiY = 0.0` — «взять DPI системы». При масштабе Windows
    150 % всё рисуемое растягивалось в полтора раза, и курсор 32×32
    выводился как 48×48. На панели статистики это было незаметно
    (она и так «на глаз»), поэтому дефект дожил до курсора.
    Исправлено явным `96.0`: масштаб 1:1, единица Direct2D равна
    пикселю поверхности.

    **(б) Чёрный квадрат вместо текстового курсора.** Инвертирующие
    пиксели рисовались чёрными — так было **написано в комментарии
    как сознательный компромисс**, и тест это подтверждал как
    правильное поведение. Ошибка в том, что у курсора «I-beam»
    инвертирующая не палочка, а **почти вся площадь картинки**:
    именно инверсия делает его видимым и на белом поле ввода, и на
    тёмном. Закрасив её чёрным, я закрашивал весь прямоугольник.
    Исправлено на прозрачность: форма верная, теряется только
    контраст на тёмном фоне.

    **(в) Окно закрывалось после UAC — снова.** Находка 32 починила
    `recover()?`, но осталось **две** ветки, выходящие из цикла по
    нераспознанной ошибке: `Err(err)` у `next_frame` и «сломался
    необратимо» внутри ожидания. Secure desktop возвращает не только
    `E_ACCESSDENIED`, но и другие коды, которых классификация не
    знает, — и прогон завершался.

    Общая правка: **отличать «временно нельзя» от «сломано навсегда»
    по коду ошибки ненадёжно**, потому что полного списка кодов
    secure desktop нет. Надёжнее время: любая ошибка ведёт к повтору,
    а сдаёмся по таймауту в минуту (600 попыток по 100 мс). UAC-диалог
    столько не живёт, настоящая поломка за минуту не пройдёт.

    **Урок — про пределы тестов.** Тест (б) не просто пропустил
    дефект, он его **закреплял**: проверял именно то поведение,
    которое оказалось неверным. Тесты защищают от регресса, но не
    от неправильно понятого требования — а понять, как выглядит
    курсор, можно только посмотрев на него.

    Практическое следствие для этапов вперёд: **у всего, что видно
    глазом (курсор, масштаб, цвета, компоновка), проверка — глаз, а
    не тест.** Планировать живой просмотр наравне с прогоном тестов,
    а не вместо него.

37. **Окно выглядело зависшим — и это был дефект, а не Windows.**
    Пользователь запустил `loopback` без `--agitate` и сообщил, что
    окно «зависло», а при перетаскивании «отвисает на секунду».

    Причина прямо в цикле: `Ok(CaptureOutcome::Timeout) => continue`.
    DXGI отдаёт кадр **только при изменении экрана** (§5.1), поэтому
    на статичном рабочем столе кадров нет — и `Present` не вызывался
    вообще. Окно не перерисовывалось. Стоило подвигать его мышью,
    как экран менялся, DXGI отдавал кадр, картинка обновлялась —
    отсюда «отвисает при движении».

    Тот же дефект был ещё в двух местах: кадры «менялся только
    курсор» и кадры, пропущенные ограничителем частоты. При лимите
    60 fps и потоке 200 кадров/с две трети итераций уходили в
    `continue`, то есть окно обновлялось втрое реже возможного.

    Исправлено методом `VideoWindow::redraw_last_frame`: копия
    последнего кадра держится в своей текстуре (`CopySubresourceRegion`,
    на GPU, без системной памяти) и рисуется заново. Текстура
    декодера для хранения не годится — MFT переиспользует пул
    поверхностей. Повторить `Present` тоже нельзя: `FLIP_DISCARD`
    не сохраняет содержимое буфера.

    Проверка: статичный экран, 10 с → **489 кадров вместо ~0**,
    задержка не изменилась (3.07 мс).

    **Почему не заметил раньше.** Все мои прогоны шли с `--agitate`
    или при живой работе на экране — то есть в условиях, где кадры
    идут постоянно и дефекта не видно. Флаг, добавленный ради
    удобства (находка 33), заодно **замаскировал** дефект: он
    создавал ровно ту активность, которой не хватало.

    Урок: **удобный режим проверки может скрывать то, что видит
    пользователь в обычном.** Хотя бы один прогон должен идти в
    самых обычных условиях, без вспомогательных флагов.

38. **Два дефекта QUIC, которые нашлись на первом же соединении.**
    Оба прошли мимо юнит-тестов, потому что тесты проверяли, что
    конфигурация **собирается**, а не что стороны **договариваются**.

    **(а) ALPN не согласован.** `ServerConfig::with_single_cert` —
    удобный конструктор — молча не выставляет `alpn_protocols`.
    Клиент при этом требует `betterdesk/1`, общего протокола нет, и
    рукопожатие обрывается с `peer doesn't support any known
    protocol` — сообщением, которое ничего не говорит о причине.
    Лечится ручной сборкой `rustls::ServerConfig` ради одной строки.

    **(б) Соединение устанавливалось и тут же завершалось.**
    `recv_async` возвращала `Option` и отдавала `None` в **двух
    разных смыслах** — «очередь пуста» и «канал закрыт». Вызывающий
    различить их не мог и выходил из цикла в обоих случаях. В логе
    это выглядело так: «соединение установлено» и сразу «поток
    транспорта завершён».

    Урок по (б) общий и переносимый: **если функция отвечает
    «ничего» по двум разным причинам, а реакция на них разная —
    `Option` неверный тип.** Нужен собственный enum, как здесь
    `PollOutgoing` с вариантами `Frame`/`Idle`/`Closed`.

    Урок по (а) — про класс ошибок: **согласование сторон нельзя
    проверить, глядя на одну сторону.** Конфигурации собирались обе,
    по отдельности валидные, а вместе не работали. Такие дефекты
    ловит только проба, поднимающая настоящее соединение, — поэтому
    `quic_probe` существует и проверена на способность провалиться
    (с откаченным ALPN падает с той же ошибкой).

    Побочно: clippy указал, что три моих теста сравнивали константы
    между собой (`SEND_QUEUE_FRAMES > 0`), то есть проверяли
    вычисляемое компилятором. Заменены на проверку **поведения**:
    что очередь отказывает при переполнении, а закрытый канал
    отличим от пустого.

39. **«Транспорт исказил кадр» — а искажения не было.** При первом
    прогоне пайплайна через QUIC обе стороны сообщили о порче:
    хост ждал 40363 байта и получил 40219, клиент — ровно наоборот.

    **Зеркальность цифр и была ответом.** Байты не портились: каждая
    сторона собрала кадр собеседника. Заглушка замкнута сама на себя,
    и `loopback` писался под неё — обе стороны шлют видео и обе
    нумеруют кадры **с нуля**. По одному соединению пошли два потока
    с одинаковыми номерами, и сборщик не смог их различить.

    Дефект в конструкции пробы, не в транспорте. Настоящий продукт
    так не устроен (§3.1): хост захватывает и шлёт, клиент принимает
    и показывает. Введён `VideoDirection` с вариантами
    `Loopback`/`SendOnly`/`ReceiveOnly`.

    **Как нашёл — важнее, чем что нашёл.** Первая гипотеза (потеря
    фрагмента) была правдоподобной: пришло меньше ожидаемого.
    Проверил счётчиком отказов `send_datagram` — **ноль**. Вторая
    попытка дала обратную картину: пришло *больше* ожидаемого. Именно
    это «больше» и опровергло потерю, а зеркальность цифр у двух
    сторон указала на смешение потоков.

    Это тот же урок, что в находках 27, 34 и 35, уже в четвёртый раз:
    **сообщение о порче данных чаще означает ошибку в проверке или в
    постановке опыта, чем настоящую порчу.** Практика, которая
    работает: не чинить по первой гипотезе, а добавить в сообщение
    факты (сколько пришло, сколько ждали, где разошлось) и посмотреть
    ещё раз.

40. **Задержку между машинами пока нечем измерить.** После
    разделения ролей клиент показывает кадры (733 за прогон, 0
    ошибок), но в итогах пишет «недостаточно данных».

    Причина фундаментальная, а не мелкая: отметка `Captured` ставится
    **на хосте**, а wire-формат её не передаёт — в 16-байтовом
    заголовке места под метку времени нет. Клиент физически не знает,
    когда кадр был захвачен, и glass-to-glass не считается.

    В заглушке этого не было видно: там обе стороны — один процесс с
    общей эпохой, и тайминги просто лежали в памяти рядом.

    **Что нужно сделать** (этап 3, до замера ≤ 35 мс в LAN):
    добавить в заголовок метку времени захвата и синхронизацию часов
    сторон — без второго первое бессмысленно, потому что часы двух
    машин расходятся на десятки миллисекунд. Правка затрагивает
    §4.5 (единое время), этап 5 (метка попадёт под шифрование) и
    этап 6 (контроллер битрейта строится на времени доставки), так
    что делать её надо не наспех.

    **Сделано в тот же день:** заголовок вырос до 24 байт, версия
    протокола → 2, добавлен `bd_core::ClockSync`. Задержка между
    процессами измеряется: **21.6 мс медиана**.

41. **Гипотеза о нулевом таймауте оказалась неверной — прогон
    показал ухудшение вдвое.** После первого замера через QUIC вся
    задержка (20.7 мс из 21.0) сидела в стадии `network`, хотя дело
    было на localhost, где сети фактически нет.

    Объяснение выглядело очевидным и правдоподобным: приёмник
    вызывает `receive()` раз в итерацию, а итерация ждёт собственный
    захват с таймаутом 16 мс — кадры просто лежат в очереди. Раз
    приёмнику захват не нужен, дать ему нулевой таймаут.

    **Прогон дал 33.5 мс вместо 20.7.** Цикл без ожидания крутится
    на полной скорости и вытесняет поток QUIC — тот самый, которому
    и надо доставить датаграмы. Правка не ускорила приём, а отняла
    процессор у сети.

    Откачено, объяснение записано в код рядом с таймаутом. Остаток
    ~20 мс — цена привязки приёма к такту цикла (родственно находке
    34), и лечится он не таймаутом, а разделением на потоки: приём и
    показ должны идти своим темпом. Это работа для `bd-client`, а не
    для пробы.

    **Урок практический:** правдоподобное объяснение — не проверка.
    Замер занял три минуты и опроверг гипотезу, на которую иначе
    ушёл бы день переделки цикла. Это тот же приём, что спас время
    в находке 30, где `quality_probe` за один прогон опровергла
    гипотезу про IDR.

42. **Джиттер-буфер ухудшил задержку втрое — и это привело к
    настоящему дефекту.** Первый прогон с буфером дал 67.9 мс против
    21.6 без него. Выглядело как «буфер плохой».

    **Цифры показывали другое:** целевое удержание 21.5 мс,
    фактическое — 53.5 мс. Расхождение вдвое означало, что кадры
    лежат дольше положенного, то есть их не забирают вовремя.

    Причина нашлась в цикле пробы: **ограничитель частоты кодирования
    стоял до приёма и применялся к обеим ролям**. Приёмник ничего не
    кодирует, но исправно пропускал две трети итераций — и готовые
    кадры ждали в буфере, пока цикл занят чужой работой.

    Правка (`direction.sends() && !limiter.should_encode_now()`)
    убрала не только проблему буфера, но и **половину задержки
    вообще**: без буфера стало 9.3 мс вместо 21.6.

    Побочно всплыл второй дефект отчёта, ровно как в находке 34:
    стадия `decode` показывала 25.6 мс вместо 0.04. Отметка
    `Received` ставилась при приёме из транспорта, до буфера, и
    удержание попадало в следующую стадию. Цена буфера должна быть
    видна там, где возникает.

    **Итоговый размен, измеренный, а не предполагаемый:**

    | | медиана | p95 |
    |---|---|---|
    | без буфера | 9.3 мс | 17.9 мс |
    | с буфером | 34.5 мс | 42.8 мс |

    Буфер делает ровно то, ради чего нужен, — режет хвост, — но
    платит медианой. На хорошем канале размен невыгоден, на плохом
    будет наоборот. Поэтому он **выключен по умолчанию**, а
    автоматика (включать по превышению порога джиттера) отложена
    до этапа 6, где появится контроллер качества.

    **Урок:** плохой результат измерения — повод искать причину, а
    не отменять изменение. Буфер оказался ни при чём; он лишь
    сделал видимым дефект, который до этого просто добавлял 12 мс
    ко всем прогонам молча.

43. **`intra_refresh` был декоративным полтора этапа.** Настройка
    объявлена в `EncoderConfig` с этапа 1, покрыта тестом
    «обязательна по §5.2» — и **не доходила до NVENC вообще**.
    CLAUDE.md честно называл её декоративной, и именно поэтому она
    так долго не чинилась: запись о дефекте заменила собой дефект.

    Проявлялось как пикселизация. Полный IDR при 2560×1600 весит
    88 КБ при бюджете кадра 61 КБ — в VBV он не помещается
    **никогда**, ни при каком размере буфера (при 1080p/15 Мбит/с
    это 63 КБ против 46 КБ, та же пропорция). Энкодер, обязанный
    уложиться в CBR, огрубляет всю картинку.

    Исправлено: `enableIntraRefresh(1)`, период 4 с, полоса 0.5 с.
    Ограничение из заголовка — Intra Refresh молча отключается,
    если `gopLength` не равен `NVENC_INFINITE_GOPLENGTH`; у нас он
    выставлен, но при правке GOP об этом надо помнить.

    Настройка теперь **пишется в лог** при включении. Причина та же,
    что в находке 26: молчаливая настройка не имеет свидетеля и
    потому неотличима от отсутствующей. Проверено на живой машине:
    `Intra Refresh включён period=240 count=30`.

44. **Ограничитель частоты уезжал ВНИЗ, а не вверх — и гипотеза была
    обратной.** `quality_probe` показала 76.4 кадра/с при лимите 60,
    и объяснение напрашивалось: отметка ставится по времени прихода
    кадра, ошибка копится, частота дрейфует вверх.

    **Тест опроверг это за один прогон:** неравномерный источник дал
    **48** кадров/с, а не 76. Механизм оказался противоположным:
    кадр, пришедший на долю миллисекунды раньше слота, отвергался,
    а следующий приходил только через 9 мс — слот пропускался
    целиком. Сетка каждый раз отсчитывалась от последнего
    **принятого** кадра, то есть всегда позже, чем надо.

    Прежний тест этого не ловил, потому что подавал **идеально
    равномерный** источник в 240 кадров/с. DXGI так себя не ведёт.

    Исправлено сдвигом отметки на целое число интервалов. После
    правки: 44.3 кадра/с вместо 76.4, предупреждение «кодируется
    в 1.3× больше кадров, чем заложено» исчезло.

    **Урок — продолжение находки 41:** правдоподобное объяснение не
    является проверкой. Тест писался, чтобы зафиксировать понятый
    дефект, а вместо этого опроверг гипотезу до того, как была
    написана хоть строка правки.

45. **ГЛАВНАЯ НАХОДКА: три догадки о курсоре подряд, и все три
    неверны.** Пользователь сообщил, что курсор пропадает над
    текстом. История одной строки кода:

    | Попытка | Результат |
    |---|---|
    | чёрные (изначально) | чёрный квадрат (находка 36б) |
    | прозрачные (36б) | курсор пропадает над текстом |
    | белые (эта сессия) | **белый квадрат** |

    Каждая правка делалась по рассуждению о том, как устроен формат,
    и каждая была зеркальным повторением предыдущей ошибки.

    **Вопрос закрылся за один прогон, как только форма была
    напечатана.** Дамп настоящего I-beam с живой машины:

        ..........######..######........
        ..........##############........
        ................##..............
                  (и так 20 строк)
        ..........##############........
        ..........######..######........

    Маска стоит на **всей площади** 48×48, а форму несёт **яркость**
    пикселя. Ни одна из трёх догадок этого не учитывала: все решали
    судьбу пикселя по маске, которая здесь ничего не различает.

    Правило: яркий пиксель под маской — часть формы, тёмный — фон.
    Дамп оставлен в коде под `trace`: следующая жалоба на курсор
    должна начинаться с него, а не с гипотезы.

    **Побочно выяснилось, что монохромных курсоров машина не
    присылает вообще** — только `Color` и `MaskedColor`. Вся работа
    над монохромной веткой (и находка 36б целиком) касалась кода,
    который на этой машине не исполняется ни разу.

    **Урок.** Находка 36 говорила: у видимого глазом проверка —
    глаз. Здесь следующий слой: **глаз видит результат, но не
    причину.** Три правки подряд были сделаны вслепую именно потому,
    что глаз показывал «неправильно», но не показывал, чем именно
    неправилен формат. Нужен был дамп данных — то есть инструмент,
    а не наблюдательность.

46. **Курсор рисовался в пикселях хоста поверх ужатой картинки.**
    Кадр 2560×1600 ужимается в окно 1280×800 вдвое, а форма курсора
    приходит в пикселях **хоста** (48×48 при масштабе Windows 150 %)
    и рисовалась в своём родном размере. Курсор выходил вдвое
    крупнее всего остального.

    Это НЕ находка 36а, хотя симптом тот же. Там Direct2D сам
    растягивал всё нарисованное из-за DPI, и лечилось это явными
    96 DPI. Здесь DPI ни при чём — расходятся системы координат
    хоста и окна, и лечится это множителем `presented_size / кадр`.

    Позиция при этом была верна всегда: она нормализована в доли
    (§0.1, этап 2), а размер — нет. Показательно: нормализованная
    величина пережила смену разрешения без единой правки,
    пиксельная — нет.

47. **Клиенту требовался аппаратный энкодер, чтобы ничего не
    кодировать.** `NvencEncoder::new` вызывался безусловно, **до**
    всякой проверки роли. На машине без NVIDIA проба падала здесь,
    не дойдя до кода, которому энкодер не нужен вовсе.

    Тестовая машина во Франции (§0.1) — клиент без рабочей
    видеокарты, то есть до сих пор на ней нельзя было запустить
    **ничего**, и «проверить, что работает у всех» было физически
    невозможно. Дефект жил с этапа 3, когда появились роли: до него
    заглушка была замкнута сама на себя, и обе стороны действительно
    кодировали.

    Исправлено: роль выясняется до создания энкодера, `encoder`
    стал `Option`. `None` означает «не нужен», а не «не удалось» —
    вторая ситуация по-прежнему обрывает запуск у того, кому энкодер
    нужен. Проверено живым прогоном через QUIC: клиент показал
    1497 кадров при 59.9 fps, медиана 8.83 мс.

    **Урок про роли.** Разделение на хост и клиент было объявлено
    (§3.1) и даже реализовано в `VideoDirection`, но код инициализации
    о нём не знал: он строил **весь** стек до того, как роль
    выяснялась. Объявленное разделение обязанностей ничего не значит,
    пока порядок инициализации ему противоречит — родственно находке
    31, где у сообщения «вызывающий обязан» не оказалось адресата.

48. **`machine_probe`: что делать, когда машина чужая.** Остальные
    пробы отвечают «с какой задержкой работает подсистема» и почти
    все требуют NVENC — то есть на машине без NVIDIA не запускается
    ни одна, и о ней нельзя узнать вообще ничего.

    Новая проба отвечает на другой вопрос: **годится ли машина в
    хосты, в клиенты или ни во что**. Устройство подчинено тому, что
    её запускает человек, не читавший код, на машине без отладчика:

    - она **не падает** на первой неудаче. Отказ NVENC — не конец
      проверки, а один из результатов. Отсюда свой тип `Check`
      вместо `Result`: `Result` подталкивает к `?`, то есть к выходу
      на первой же ошибке;
    - каждый ответ словами, а не кодом;
    - в конце вывод, который можно переслать одной строкой.

    Проверено на способность провалиться: с подменённым результатом
    NVENC проба честно печатает «❌ ХОСТ: нет» и **продолжает**,
    выдавая «✅ КЛИЕНТ». Это ровно тот случай, который ожидается
    во Франции.

    Ошибки создания захвата и декодера в `loopback` тоже теперь
    объясняются человеку, а не только кодом: голое `?` дало бы
    строку «H.264 MFT не поддерживает D3D11», по которой человек за
    той машиной не может сделать ничего.

    **Известный предел.** Декодер при `MF_SA_D3D11_AWARE == 0`
    по-прежнему **отказывает**, а не откатывается на софт. Это
    осознанно оставлено: `openh264` (§5.5) не сделан, BSD-2-Clause
    под него в `deny.toml` разрешён с этапа 0. До тех пор машина без
    аппаратного декода видео не покажет — но теперь скажет об этом
    внятно.

49. **Двусторонняя проверка упирается не в код, а в единственный
    бэкенд энкодера.** Роли несимметричны: клиенту нужен только
    декодер (есть почти в любой Windows), хосту — захват **и
    энкодер**. Энкодер реализован ровно один, NVENC, поэтому **хостом
    может быть только машина с NVIDIA**.

    Из этого следует то, что легко упустить при планировании
    проверки: «посмотреть экран друг друга» — это не одна сессия и
    не одна настройка, а **два прогона со сменой ролей**, и второй
    возможен только если у второй стороны есть NVIDIA.

    Чтобы не гадать, добавлено перечисление энкодеров
    (`mediafoundation::h264_encoders`, `MFTEnumEx` по категории
    `VIDEO_ENCODER`). Оно отвечает на вопрос, от которого зависит
    решение о нескольких днях работы: есть ли на машине аппаратный
    энкодер вообще. Если есть Intel QuickSync или AMD — машина
    **смогла бы** хостить, надо написать бэкенд (§5.2 их и
    предполагает). Если нет ни одного — бэкенд ей не поможет.

    На машине разработчика найдено 5 записей, среди них NVIDIA,
    два Intel QuickSync и встроенный в Windows H264 Encoder MFT
    (в аппаратном и софтверном виде). Последнее означает, что даже
    машина без дискретной карты энкодер имеет.

    **Оговорка, записанная в коде:** перечисление — это «заявлено»,
    а не «работает». MFT из списка может отказать при создании ровно
    как NVENC отказал на несовместимых заголовках (находка 12).

    Побочно: `IMFAttributes::GetAllocatedString` отдаёт имя через
    **два out-параметра**, а не возвращает кортежем — сигнатура
    сверена с исходниками windows 0.62, как предписывает §12
    (находка 6).

    Ещё побочно: имя энкодера Intel система отдаёт с лишним символом
    «Ð’» перед «®». Две гипотезы («виновата консоль», «не та длина
    строки») опровергнуты сравнением байт: правильное имя даёт
    `C2 AE`, система отдаёт `D0 92 C2 AE`, причём сам «®» целый.
    То есть искажение записано в системе, а не возникает у нас.
    Чистится `clean_vendor_name` — на логику имя не влияет, но его
    читает человек на чужой машине.

50. **Энкодер Media Foundation: хостом может быть любая машина.**
    NVENC работает только на NVIDIA, и это делало продукт негодным
    для §7.1 («скачал и запустил»): ноутбук с Intel-графикой не мог
    отдать свой экран вовсе.

    Добавлен `mediafoundation::MfEncoder` — Intel QuickSync, AMD VCE
    и всё, что система считает аппаратным. Выбор бэкенда —
    `bd_bench::any_encoder::AnyEncoder`: сначала NVENC (у него есть
    Intra Refresh, точный VBV и `maxQP`, которых через MF не
    получить), при его неудаче — MF.

    **Живой прогон через MF: 1188 кадров, 59.4 fps, медиана 0.43 мс,
    ноль ошибок целостности.** Пайплайн целиком, включая декод и показ.

    Три дефекта, найденных живой пробой, — все прошли бы мимо тестов
    конфигурации:

    **(а) Аппаратные MFT асинхронны.** Перечисление спрашивало
    `MFT_ENUM_FLAG_SYNCMFT`, но система всё равно отдавала
    асинхронный MFT, и тот отвечал `MF_E_TRANSFORM_ASYNC_LOCKED`
    (0xC00D6D77) на первое же сообщение. Асинхронный MFT до
    разблокировки (`MF_TRANSFORM_ASYNC_UNLOCK`) не делает **ничего**,
    а выход отдаёт событиями `METransformNeedInput` /
    `METransformHaveOutput`, а не по опросу — `ProcessOutput` у него
    возвращает `E_UNEXPECTED`.

    **(б) `AVEncCommonLowLatency` аппаратные MFT отвергают**
    (0x80070057). Нужен `CODECAPI_AVLowLatencyMode`. Смысл один,
    принимают разные — и это ровно тот случай, о котором предупреждает
    заголовок модуля: настройка молча не применяется.

    **(в) Софтверный MFT не берёт GPU-текстуру** —
    `DXGI_ERROR_INVALID_CALL` (0x887A0001). Ему нужны пиксели в
    системной памяти, то есть копия 12 МБ на кадр: 5–10 мс, прямо
    запрещённые §4.2.3. Поэтому софтверный путь **исключён**, и вместо
    тихой деградации даётся честный отказ. Настоящий софт-путь —
    `openh264` (§5.5), он остаётся несделанным.

51. **Выбор энкодера — это перебор с проверкой, а не чтение списка.**
    На гибридной графике энкодеров несколько, и не каждый видит нашу
    текстуру. Проверено живьём: на ноутбуке, где дисплей ведёт
    NVIDIA, Intel QuickSync отвергает D3D-менеджер (0x80070057), а
    затем выходной тип с `MF_E_UNSUPPORTED_D3D_TYPE` (0xC00D6D76) —
    он физически не видит чужой адаптер.

    Это тот же класс ограничения, что у DXGI в §5.1: кодировать надо
    на том адаптере, которому принадлежит кадр. Первая версия брала
    первый MFT из списка и сдавалась при его отказе — то есть на
    машине с двумя GPU могла выбрать заведомо негодный.

    Теперь `MfEncoder::new` перебирает **всех** кандидатов, пытаясь
    настроить каждого, и берёт первого, кто прошёл полную настройку.
    Отказ принять D3D-менеджер стал фатальным для кандидата (раньше
    был предупреждением): без него кадры пошли бы через системную
    память, то есть путь негоден целиком.

    Проверено прогоном с пропуском NVIDIA: проба честно перебрала
    3 кандидата, объяснила отказ каждого и вернула последнюю ошибку.

    **Урок.** «Система вернула список» и «эти вещи работают» —
    разные утверждения, и второе проверяется только попыткой. Тот же
    урок, что находка 12 (декларация совместимости не заменяет
    проверку на живом железе), в новой форме.

52. **Шторм ключевых кадров: каждая потеря требовала IDR.**
    `request_keyframe` вызывался на **каждый** потерянный кадр. При
    1 % потерь датаграмов это дало 459 запросов за 25 с — **707
    ключевых в минуту**, то есть почти каждый кадр становился
    ключевым, а битрейт вырос до 21.2 Мбит/с.

    Петля самоусиливающаяся: потеря → ключевой кадр → он в разы
    крупнее → больше фрагментов → выше шанс потери (арифметика
    находки 28) → снова ключевой.

    Исправлено паузой между запросами. Значение выбрано **замером**,
    а не на глаз (профиль `lossy`, 25 с каждый прогон):

    | пауза | медиана восст. | p95 | битрейт |
    |---|---|---|---|
    | 250 мс | 330 мс | 2239 мс | 12.9 |
    | 150 мс | 150 мс | 899 мс | 18.4 |
    | 80 мс | 100 мс | 500 мс | 24.9 |

    Размен монотонный: короче пауза — быстрее восстановление и дороже
    трафик. Взято 120 мс. Число подавленных запросов печатается в
    отчёте: без него «пауза работает» не отличить от «потерь не было»
    (находка 26).

    **Побочно опровергнута собственная гипотеза.** Я ожидал, что
    меньше ключевых кадров = меньше потерь. Замер показал обратное:
    30.68 % → 35.99 %. Причина в том, что потери кадров при 22
    фрагментах на кадр **неустранимы арифметически** (0.99²² ≈ 80 %),
    и к ключевым кадрам отношения не имеют. Пауза лечила шторм
    трафика, а не потери.

53. **Критерий «артефакты не дольше 200 мс» был непроверяем — и
    теперь не выполняется.** Критерий этапа 3 существовал с самого
    начала, но ничто не измеряло время восстановления: проверить его
    можно было только глазом, а 200 мс — это 12 кадров, которые на
    глаз от 30 не отличить.

    Добавлен замер: интервал «потеря → первый дошедший ключевой
    кадр». Добавлен профиль `LOSSY` — ровно 1 % потерь, как в
    формулировке критерия (на профиле с 0.5 % или 3 % вердикт
    относился бы не к тому, что записано, — находка 29).

    **Результат: критерий НЕ выполняется.** На 1 % потерь медиана
    183 мс, p95 767 мс при пороге 200 мс.

    Причина найдена и она арифметическая: **ключевых выдано 158,
    восстановлений 86 — 54 %**. Больше половины ключевых кадров сами
    теряются, потому что при 72 КБ кадр идёт 63 фрагментами, и
    `0.99⁶³ ≈ 53 %` — предсказание совпало с замером. Подбором паузы
    это не лечится: даже при 80 мс p95 остаётся 500 мс.

    Лечится FEC (этап 6), и находка 28 это уже предсказывала.
    Вердикт в пробе печатает причину рядом с крестиком, чтобы её не
    пришлось выводить заново.

    **Две оговорки, записанные в код:**

    - метрика — **верхняя оценка**, а не длительность артефакта.
      Декодер после потери не останавливается: он продолжает
      декодировать разностные кадры, и порча затухает по мере прихода
      интра-макроблоков. Настоящая видимая порча короче;
    - при выборке меньше 30 случаев вердикт **не выносится**: p95 на
      десятке наблюдений — это просто максимум, и один выброс
      определял бы всю картину. Печатается предупреждение вместо
      уверенного крестика.

54. **Записанная причина — не устранённая причина.** Находка 41
    установила, почему на localhost стадия `network` показывает
    20.44 мс там, где сети нет: приёмник ждал `AcquireNextFrame` с
    таймаутом 16 мс, то есть кадры забирались в такте **захвата
    чужого экрана**, который приёмнику не нужен вовсе.

    Диагноз был верным, был записан в код рядом с таймаутом, и там
    же было сказано, что лечится это разделением на потоки и «это
    работа для `bd-client`, а не для пробы». После чего **полтора
    этапа ничего не происходило**: цифра 20 мс входила во все
    измерения как данность, а комментарий рядом объяснял, почему она
    такая.

    Устранение заняло меньше, чем ушло на её объяснение: клиент,
    которому не нужен захват, ждёт на канале транспорта
    (`receive_timeout`) — и стадия упала до **7.58 мс**.

    Это в точности та же ошибка, что в находке 43, где `intra_refresh`
    был декоративным полтора этапа: **CLAUDE.md честно называл
    настройку декоративной, и именно поэтому она так долго не
    чинилась — запись о дефекте заменила собой дефект.** Здесь запись
    была даже подробнее, с измерением и указанием, что делать.

    Правило, которое из этого следует: у записи «известное
    ограничение, лечится тем-то» должен быть **срок или этап**, иначе
    она превращается в описание нормы. Пункт «известное требование от
    этапа 1» в разделе «что дальше» жил без адресата ровно так же,
    как комментарий из находки 31.

55. **Роль объявлена — но порядок инициализации ей противоречит.**
    Третий случай подряд, и уже пора считать это классом, а не
    совпадением:

    | Находка | Что требовалось для роли, которой это не нужно |
    |---|---|
    | 47 | клиенту — **энкодер**, чтобы ничего не кодировать |
    | 55 | клиенту — **работающий DXGI-захват**, чтобы показать чужой экран |

    Второе нашлось при выносе клиента в отдельный бинарь:
    D3D11-устройство бралось из `DxgiCapturer`, то есть через
    дупликацию **своего** монитора. На машине, где захват недоступен
    (гибридная графика, §5.1), клиент не запустился бы — хотя
    дуплицировать ему нечего, а декодер и окно работают на любом
    адаптере.

    Лечится `D3dDevice::for_decode` — устройством без монитора и без
    дупликации.

    **Общее у всех трёх случаев:** разделение ролей было объявлено в
    §3.1 и даже реализовано в типах (`VideoDirection`), но код
    инициализации строил **весь** стек до того, как роль выяснялась.
    Пока обе роли жили в одном процессе, это ничего не стоило —
    проба и правда нуждалась во всём сразу. Отсюда практический
    вывод: **совмещение ролей в инструменте замера скрывает именно
    те требования, которые продукт не должен предъявлять.**

56. **Три канала на трёх портах — и это не эстетический выбор.**
    При выносе клиента выяснилось, что ввод и курсор **никогда не
    ходили через настоящий QUIC**: в `loopback` они всегда шли через
    заглушку, и только видео переключалось на сеть.

    Первая попытка открыть три соединения на одном порту провалилась
    бы очевидно (один UDP-сокет), но интереснее другое — почему
    нельзя пустить всё в одно соединение. `Reassembler` ведёт **один**
    `last_delivered` на поток и выбрасывает всё с меньшим номером.
    Видео идёт 60 кадрами в секунду, ввод — сотнями событий, и
    нумерация у каждого своя: в общей очереди каждый вид считал бы
    чужие пакеты устаревшими и молча их терял.

    Взято временное решение — три порта подряд, — и оно **помечено
    как временное** в коде обеих сторон: на этапе 4 пробивать три
    порта через NAT втрое дороже, чем один, и тогда придётся
    разделять состояние сборки по `PayloadKind`.

    Побочно это добавило человеку работы: в инструкции для второй
    машины теперь отдельный шаг про файрвол, и отдельная строка в
    таблице неполадок — «видео идёт, а курсор и клавиатура нет»
    означает открытый только 7000-й порт. Такой симптом без
    подсказки диагностируется долго.

    **ЗАКРЫТО 2026-08-31 (находка 60).** Каналы сведены в одно
    соединение: состояние сборки разделено по `PayloadKind`, порт
    снова один. Временная пометка сработала — она пережила ровно
    один этап, а не превратилась в описание нормы (в отличие от
    находок 43 и 54, где запись о дефекте заменила собой дефект).

57. **Три дефекта оболочки, и все три — «неверно, но без ошибки».**
    Первый запуск `bd-shell.exe` открыл окно, которое выглядело
    исправным: вёрстка, шрифты, отступы на месте. При этом экран
    сообщал неправду, и ни одна из трёх причин не давала ни
    исключения, ни записи в логе.

    **(а) Мост Tauri брался вне `try`.** `window.__TAURI__.core`
    кидает при разборе самого скрипта — до того, как появится хоть
    один обработчик. Мой `try/catch` вокруг `invoke` был недостижим,
    и вместо объяснения человек видел «— — —» на месте ID.

    Причина отказа при этом была тривиальной: в `tauri.conf.json`
    не стоял `withGlobalTauri`, без которого мост в страницу не
    внедряется вовсе.

    Урок переносимый: **обработка ошибки бесполезна, если она
    недостижима из места, где ошибка возникает.** Внешние зависимости
    (мост, глобальный объект, API браузера) надо трогать внутри
    защищённого участка, а не строкой выше него.

    **(б) `[hidden]` молча не работает.** Атрибут скрывает только
    элементы с `display` по умолчанию. У `.pill` задан
    `display: inline-flex`, и он перебивает `hidden` — оба значка
    состояния («Готов принимать» и «Только просмотр») показывались
    одновременно, оранжевый поверх зелёного.

    То есть экран уверенно сообщал, что машина **не может** отдавать
    свой экран, — на машине, которая часом раньше отдавала его через
    `bd-host`. Лечится строкой `[hidden] { display: none !important }`.

    **(в) `cargo build` не пересобрал бинарь после правки конфига.**
    Ровно находка 15, во второй раз: я исправил `withGlobalTauri`,
    пересобрал, запустил — и увидел прежнюю картинку, потому что
    `.exe` остался от предыдущей сборки. Обнаружилось сверкой времени
    файла со временем правки.

    **Как нашлось (б) — это важнее, чем что нашлось.** Логика во
    фронтенде была верной, бэкенд отвечал верно, и я дважды был готов
    чинить не то. Вопрос закрыло **логирование обеих проверок
    отдельно** (`can_view=true dxgi=true`): цифры из бэкенда
    противоречили картинке, и это сразу указало на вёрстку.

    Тот же приём, что в находке 45: глаз видит результат, но не
    причину, и нужен дамп данных, а не гипотеза.

58. **Проверка лицензий сработала до написания кода — и это
    сэкономило разбор.** §9.1 требует настраивать `cargo-deny` **до**
    того, как накопились зависимости. При добавлении Tauri правило
    исполнено буквально: крейт создан, зависимость добавлена,
    `cargo deny check` прогнан — и `licenses FAILED` пришёл раньше,
    чем была написана хоть строка экрана.

    Виновник — **MPL-2.0** у пяти крейтов (`cssparser`, `selectors`,
    `cssparser-macros`, `dtoa-short` — CSS-парсер Mozilla через
    `dom_query`; плюс `option-ext`).

    Разбираться было нечего: §9.1 **разрешает** MPL-2.0 («файловый
    копилефт, но не заражает наш код»), её просто забыли внести в
    `deny.toml` при заведении списка. Добавлена с условием, которое
    записано прямо там: **не изменять исходники этих крейтов.** MPL
    требует раскрывать изменения пофайлово, и форк любого из них
    означал бы обязанность публиковать изменённые файлы — решение,
    которое нельзя принимать мимоходом.

    Ценность порядка действий: сделай я это после экрана, пришлось бы
    выяснять, откуда взялась MPL, посреди отладки вёрстки. Проверка,
    поставленная перед работой, отвечает на вопрос до того, как он
    станет срочным.

59. **Подключение по ID работает, а NAT всё ещё не пробивается — и
    это разные вещи.** Соблазн после первого удачного прогона
    объявить этап 4 сделанным велик: хост печатает девять цифр,
    клиент вводит только их, картинка идёт. На localhost всё честно.

    Через интернет это **не заработает**, и причина не в сигналинге,
    а в том, чего рядом с ним нет.

    Пробивание NAT требует, чтобы обе стороны одновременно послали
    пакеты **с того же порта, на котором потом пойдут данные**.
    Роутер открывает отображение для конкретной пары адрес-порт, и
    пакет, пришедший на другой порт, он отбросит.

    У нас же сигналинг ходит по своему TCP-сокету, QUIC слушает свой
    UDP-порт, и связи между ними нет. Клиент вдобавок сообщает серверу
    `0.0.0.0:0` — заглушку вместо настоящего адреса. То есть адрес,
    который хост получает в `PeerWants`, для пробивания бесполезен.

    В LAN это не мешает: там оба адреса настоящие и достижимы без
    всякого пробивания, и сервер это распознаёт (одинаковый внешний
    IP → отдаём локальные адреса).

    **Записано как ограничение, а не как дефект**, потому что ICE —
    отдельный пункт этапа 4, и он честно не сделан. Но записано
    подробно: следующий, кто увидит работающее подключение по ID,
    иначе решит, что осталось только задеплоить сервер.

    Урок, общий с находкой 32: **проверка на localhost воспроизводит
    не то состояние**, ради которого пишется сетевой код. Там нет ни
    NAT, ни потерь, ни расхождения часов — и всё, что их касается,
    остаётся непроверенным независимо от того, сколько раз прогон
    прошёл зелёным.


60. **Три канала сведены в один — и правка вдвое срезала частоту, не
    тронув ни задержку, ни потери.** Подготовка к hole punching:
    пробивать NAT нужно с того же порта, на котором пойдут данные, и
    три порта означали втрое больше пробивания (находка 59).

    Сама развязка оказалась дешёвой. Состояние сборки разделено по
    `PayloadKind` (`KindState` внутри `Reassembler`), нумерация тоже
    стала раздельной — и в `QuicTransport`, и в заглушке. Курсор
    получил собственный вид `PayloadKind::Cursor`: до этого позиция
    ехала под кодом `Video`, что в отдельном соединении не значило
    ничего, а в общем означало бы столкновение с настоящим видео.

    **Дефект появился там, где его не ждали — в цикле ожидания
    клиента.** Раньше клиент ждал видео на своём канале, а курсор
    опрашивал на другом. В сведённом канале очередь одна, и я написал
    цикл, который ждёт любую нагрузку, разбирает её по виду и
    отсчитывает общий остаток `FRAME_WAIT` от начала итерации.

    Выглядело правильно. Дало **29.8 fps вместо 54.8**.

    Причина: курсорные пакеты идут сотнями в секунду, каждый оборот
    цикла уменьшал остаток, и на очередном курсоре бюджет обнулялся.
    Следующий вызов с нулевым таймаутом отвечал «пусто» — хотя кадр
    в этот момент вполне мог лежать в очереди следующим. Клиент уходил
    перерисовывать старый кадр, а свежий забирал только на следующей
    итерации.

    Лечится правилом: **ждать только когда очередь действительно
    пуста**; уже пришедшее разбирается без ожидания и бюджета не
    тратит. После правки 54.8 fps — ровно как до сведения каналов.

    **Чем этот дефект опасен.** Он не давал ни отказа, ни потерь, ни
    роста задержки: медиана осталась 10.7 мс, потери нулевые, все
    263 теста зелёные. Просто половина кадров показывалась позже, чем
    могла. Ни одна проверка проекта на это не смотрит — они меряют
    доставку и задержку доставленного, а не то, насколько быстро её
    забирают.

    Нашлось сравнением с прежней версией через `git stash`: замер до
    правки, замер после, разница вдвое. Это стоит записать как приём:
    **при переделке горячего пути мерить обе версии подряд, а не
    сверять новую с ожиданием.** Ожидание здесь совпало с новой
    версией — оба раза «работает, задержка та же».

    **Побочно: проба сама оказалась неверной — в третий раз за
    проект.** Написанная под это фаза `quic_probe` сообщила, что все
    три вида теряются (42/21/21 из 60). Первая гипотеза — соединение
    фазы 1 висит без собеседника и роняет фазу 2 по idle-таймауту —
    была правдоподобной и **опровергнута за один прогон**: явный
    `drop` убрал `TimedOut`, а цифры остались.

    Настоящая причина — глубина приёмной очереди: проба слала три
    вида залпом без пауз, `RECV_QUEUE_FRAMES` равна четырём, и поток
    сети штатно отбрасывал лишнее (§5.3). То есть проба выносила
    вердикт о маршрутизации, измеряя глубину очереди, — ровно
    находка 29. После пауз внутри пачки: 57/59/57, ровно по всем
    видам.

    Порог тоже пришлось переписать честно: не «дошло 90 %», а «вид не
    пропал целиком» плюс отдельная проверка **перекоса между видами**.
    Вторая чувствительнее: очередь роняет всех примерно поровну, а
    перепутанный вид проседает один. Проба проверена на способность
    провалиться — с общим состоянием сборки ввод и курсор дают ровно
    0 из 60 при полном видео.

    **Что это дало помимо hole punching.** В файрволе открывается один
    порт вместо трёх, и из инструкции для второй машины исчез симптом
    «видео идёт, а мышь и клавиатура нет» — он означал открытый только
    7000-й порт и без подсказки диагностировался долго.


61. **Клиент не собирался на машине без LLVM — ради энкодера, который
    ему не нужен.** Четвёртый случай того же класса (47, 55, 56), и
    самый злой: там роль требовала лишнего **в рантайме**, здесь —
    **в сборке**, то есть машина не доходила даже до понятного отказа.

    Нашёл это человек за чужой машиной, а не тесты и не CI. У
    разработчика LLVM стоит с этапа 1, и путь «нет libclang» не
    исполнялся ни разу — ровно находка 26: ноль срабатываний означает
    «неизвестно», а не «работает».

    `bd-codec/build.rs` генерирует биндинги к NVENC через `bindgen`, а
    тот **паникует**, если не найдёт libclang. Паника в build.rs
    обрывает сборку всего workspace. Человек на той стороне видел:

        Unable to find libclang: "couldn't find any valid shared
        libraries matching: ['clang.dll', 'libclang.dll']"

    По этой строке сделать нельзя ничего: она про зависимость чужого
    крейта, а не про то, чего от тебя хотят. И главное — она возникала
    на машине, которой NVENC **не нужен вовсе**: без NVIDIA он всё
    равно не заработает, а клиент ничего не кодирует.

    Прямо противоречит §7.1 («скачал и запустил»): требовать гигабайт
    LLVM ради бэкенда, который на этой машине заведомо мёртв.

    Лечится тем, что механизм уже был: `cfg(nvenc_available)`
    существует с этапа 1 и honestly отключает бэкенд, когда нет
    заголовка. Не хватало одной проверки — libclang. Теперь его
    отсутствие даёт предупреждение и сборку без NVENC вместо паники.

    **Проверка сама оказалась неверной — и это интереснее правки.**
    Первая версия искала библиотеку по голому имени (`libclang.dll`),
    полагаясь на PATH. Собрал — и **NVENC отвалился на машине
    разработчика**, где он до этого прекрасно собирался.

    Причина: установщик LLVM под Windows **не добавляет себя в PATH**.
    Файл лежит в `C:\Program Files\LLVM\bin`, PATH о нём не знает, а
    `bindgen` находит его сам, потому что смотрит и типовые каталоги
    установки.

    То есть проверка воспроизводила **не то состояние**, которое
    проверяла (находка 32), и ошибалась в худшую сторону: молча
    отключала бы энкодер там, где он собирается. Хост остался бы без
    NVENC без единого сообщения.

    Отсюда два правила, оба уже встречались:

    - проверять **попыткой загрузить**, а не наличием файла по списку
      путей: попытка отвечает на тот вопрос, который задан, — сможет
      ли `bindgen` этим воспользоваться (родственно находке 51);
    - **условие обязано совпадать в обоих build.rs.** `bd-bench`
      повторяет ту же проверку (флаги cfg не наследуются между
      крейтами), и разойдись они — проба объявила бы NVENC собранным
      и не скомпилировалась бы, ссылаясь на несуществующий тип.

    **Побочно исправлены два лживых сообщения**, и оба нашлись только
    потому, что сценарий был проигран целиком, а не до первой зелёной
    сборки:

    - `machine_probe` объяснял отсутствие NVENC словами «нет
      vendor/nvcodec/nvEncodeAPI.h» — а на машине без LLVM заголовок
      как раз на месте, и человек шёл искать несуществующую проблему.
      Теперь названы обе причины и способ различить их;
    - вердикт «❌ ХОСТ: нет (нужны и захват, и NVENC)» не говорил,
      что именно подвело. На машине с исправным захватом это отправляло
      проверять захват. Теперь три разных текста на три случая;
    - там же подсказка вела на `loopback --quic-connect`, хотя
      продуктовый клиент с прошлой сессии — `bd-client --connect`.

62. **Правка находки 61 сама оказалась половинчатой — и вторая
    половина нашлась там же, на чужой машине.** Прогон после
    исправления дал `✅ КЛИЕНТ`, но в списке железа стояло:

        • AMDh264Encoder — аппаратный  (дважды)

    То есть **аппаратный энкодер у машины есть**, а вердикт говорил
    «нет». Три отдельных дефекта, и все — один и тот же класс: путь
    отключён заодно с соседним, хотя от него не зависит.

    **(а) Media Foundation не проверялся вовсе.** Вызов
    `try_media_foundation` стоял ВНУТРИ ветки `#[cfg(nvenc_available)]`.
    Пока LLVM был обязателен, это ничего не меняло — флаг стоял всегда.
    После находки 61 ветка «NVENC не собран» стала обычным делом, и
    выяснилось, что она не проверяет ничего: машина с исправным AMD
    получала «энкодера нет».

    Компилятор об этом **честно предупреждал** — `try_media_foundation
    is never used`, — но предупреждение появлялось только на сборке
    без LLVM, то есть у того, кто и так видел неверный вывод, а не у
    того, кто мог его исправить. Предупреждение приехало в переписке
    вместе с выводом пробы и было замечено только потому, что вывод
    читали целиком.

    **(б) Условие разошлось между тремя build.rs.** Правку про
    libclang внесли в `bd-codec` и `bd-bench`, а `bd-host` остался со
    старым условием «есть заголовок» — и объявлял NVENC собранным там,
    где `bd-codec` его отключил. Хост переставал собираться на машине
    без LLVM с ошибкой `unresolved import bd_codec::nvenc`, которая
    указывает **не туда**: человек читает про импорт в чужом крейте.

    Комментарий «условие то же, что в bd-codec» в каждом из скриптов
    был — и не помог. Копии не расходятся, только пока их не правят.

    Лечится тем, что копия теперь одна: `build-support/nvenc_probe.rs`
    подключается через `include!` во все три скрипта. Крейт сборки ради
    тридцати строк дороже, а `include!` даёт нужное свойство.

    **(в) `any_transport` и `input_bridge` требовали NVENC.** Оба
    объявлены `#![cfg(all(windows, nvenc_available))]`, хотя первый про
    транспорт, второй про ввод, и кодирования там нет. Флаг стоял с
    тех времён, когда NVENC был обязателен для сборки вообще.

    **Итог: весь workspace, включая `bd-host`, собирается без LLVM.**
    Проверено на живом железе обоими способами — с LLVM (NVENC на
    месте) и с ослеплённым поиском (энкодер найден через Media
    Foundation, вердикт `✅ ХОСТ`).

    **Урок, которого не было в 61.** Там правка проверялась ровно на
    том сценарии, ради которого писалась: «собирается ли клиент без
    LLVM». Собирался — и это засчитали за успех. Но выключение целой
    ветки `cfg` меняет поведение **всего, что под неё попало**, а не
    только того, о чём думали. Проверять надо было не «прошёл ли мой
    сценарий», а «что ещё оказалось под этим флагом» — вопрос, на
    который отвечает `grep nvenc_available`, а не прогон.


63. **Hole punching сделан — и живой прогон сразу показал, что хост
    объявлял себя как `0.0.0.0:7000`.** Пробивание NAT требует, чтобы
    обе стороны одновременно послали пакеты **с того же порта, на
    котором пойдут данные** (находка 59). Развязка оказалась дешевле,
    чем казалось: `quinn::Endpoint::new` принимает готовый
    `std::net::UdpSocket`, поэтому сокет создаётся заранее,
    пробивается им же и отдаётся QUIC.

    Появился `bd-transport::punch` и два конструктора рядом с
    прежними: `host_on_socket` / `connect_on_socket`. Старые
    оставлены намеренно — в локальной сети пробивать нечего, и
    заставлять вызывающего возиться с сокетом там, где это не нужно,
    значило бы усложнять частый случай ради редкого.

    **Дефект нашёлся на первом же живом прогоне по ID.** Клиент
    честно напечатал:

        Найден: 0.0.0.0:7000
        встречных пакетов не было: NAT может быть симметричным

    Диагноз в предупреждении был **неверным**, и это важнее самого
    дефекта: `0.0.0.0` — не адрес, а указание «слушать на всех
    интерфейсах», и бить туда бессмысленно. Хост регистрировал на
    сигналинге свой `--listen` как есть.

    Симметричный NAT тут ни при чём, но сообщение уверенно называло
    именно его — и увело бы отладку в сторону ровно так же, как в
    находке 61, где `machine_probe` называл причиной отсутствие
    заголовка. **Правдоподобная причина в сообщении об ошибке хуже
    отсутствия причины**: её проверяют первой.

    Лечится `reachable_addr`: `0.0.0.0` заменяется на адрес интерфейса,
    через который идёт маршрут наружу. Способ — UDP-`connect` на
    заведомо ничей адрес (203.0.113.1, RFC 5737): датаграмы при этом
    **не отправляются**, ядро лишь выбирает маршрут, а вместе с ним
    исходящий интерфейс. Перечислять интерфейсы вручную было бы хуже:
    на машине с VPN и Hyper-V пришлось бы гадать, какой из них «тот
    самый».

    Функция живёт в `bd-transport` рядом с пробиванием, а не копией в
    двух бинарях: обе стороны нуждаются в одном преобразовании, и
    копии расходятся (находка 62 — ровно об этом).

    **Побочно: тест поймал то, чего я не предусмотрел.** Первая версия
    считала любую ошибку `recv_from` фатальной. На Windows Winsock
    отдаёт `WSAECONNRESET` (10054) следующему `recv`, если на
    ПРЕДЫДУЩИЙ наш пакет пришёл ICMP «порт недоступен» — то есть
    ошибка описывает уже отправленный пакет, а не состояние сокета.
    Для пробивания это **штатнейший случай**: пир ещё не слушает, и
    именно поэтому мы бьём серией. Первая версия сдавалась ровно в той
    ситуации, ради которой написана.

    На Unix такого не бывает, так что на CI под Linux дефект не
    проявился бы никогда.

    **Что проверено и чего проверка не значит.** Живой прогон по ID
    на одной машине: `Найден: 192.168.50.80:7000`, обе стороны
    напечатали «NAT пробит: встречные пакеты дошли», 1034 кадра,
    51.7 fps, 0 потерь, медиана 9.14 мс. Прямое подключение по адресу
    не сломано: 652 кадра, 8.88 мс.

    Но **настоящего NAT здесь нет**, и это надо записать прямо: на
    localhost и в одной подсети пробивание проверяет только механику
    — что пакеты уходят, распознаются и сокет доживает до QUIC в
    рабочем состоянии. Проверка воспроизводит не то состояние, ради
    которого код написан (находки 32, 59), и вердикт «hole punching
    работает» можно будет вынести только после прогона между двумя
    машинами за разными роутерами.

    Ограничение, записанное сразу: **symmetric NAT не покрывается**.
    Он выдаёт новый внешний порт на каждый адрес назначения, поэтому
    порт, который увидел сервер, не тот, что увидит пир. По §5.4 таким
    соединениям нужен TURN-релей, отложенный до появления бюджета;
    ожидаемая успешность прямого соединения — 80–85 %.


64. **Пароль сессии — и дефект, который дал ЧЁРНЫЙ ЭКРАН при
    исправном потоке.** Поводом стало не расписание, а реальное
    свойство системы: после деплоя сигналинга хост оказался виден с
    публичного сервера, а аутентификации не было вовсе. Кто угадает
    девять цифр — увидит экран. ID не секрет (§7.3): он короткий,
    печатается на экране и диктуется вслух.

    Сделано: `bd-crypto::SessionPassword` (Argon2id, шесть цифр,
    новый при каждом запуске), `bd_core::auth` (текстовый протокол
    рукопожатия), `PayloadKind::Auth`, три попытки и проверка **до
    первого кадра** — соединение установлено, но экран ещё не отдан.

    **Дефект нашёл живой прогон, а не тесты.** Клиент должен как-то
    понять, спрашивает ли хост пароль вообще (`--no-password`
    оставлен для замеров). Первая версия делала это просто: читала
    очередь и выходила на любом пришедшем кадре, считая его признаком
    «авторизации нет».

    Кадр при этом **терялся**. А первым идёт ключевой, и без него
    декодер не может начать: все разностные кадры опираются на него.

    Результат: хост отправил **2379 кадров, клиент показал 0**. Ни
    ошибки, ни предупреждения, ни потерь в счётчиках — просто чёрное
    окно. Потери транспорт не считает, потому что их и не было: кадр
    дошёл целым и был выброшен на прикладном уровне.

    Лечится `receive_auth_timeout`: он забирает из очереди **только**
    `Auth`, а чужие кадры откладывает в буфер, откуда их берёт
    следующий `receive`. Очередь `crossbeam` не умеет подглядывать,
    так что буфер здесь неизбежен.

    **Как нашёлся.** Сравнением двух режимов: с паролем 537 кадров,
    без пароля — 0. Разница указала на ветку точнее любого лога. Затем
    `git stash` подтвердил, что до правки режим работал (351 кадр), —
    то есть регресс мой, а не давний. Тот же приём, что в находке 60.

    **Урок про класс ошибок.** Потеря ровно одного кадра выглядит
    безобидно — «ну проскочит следующий». Для H.264 это неверно:
    ключевой кадр не «один из», а точка входа в поток. Правило:
    **выбрасывать кадр можно только тогда, когда известно, что он не
    ключевой** — а на прикладном уровне это неизвестно, там ещё нет
    разбора.

    **Побочно: пароль печатался только в ветке сигналинга.** При
    `--no-signaling` он генерировался, требовался — и не показывался.
    Подключиться было невозможно, а выглядело бы это как «клиент не
    соединяется». Способ подключения и наличие пароля независимы, и
    печать не должна зависеть от первого.

    **Побочно: пустой пароль не засчитывается попыткой.** Клиент шлёт
    его, чтобы отличить хост с авторизацией от хоста без неё. Считай
    хост это попыткой — у человека оставалось бы две из трёх, причём
    он не понял бы, куда делась первая. Подбору это ничего не даёт:
    пустой пароль всё равно неверен.

    **Чего пароль НЕ даёт, и это записано в коде рядом:** защиты от
    подмены хоста. Сигналинг недоверен (§8.1), подставной хост примет
    любой пароль и покажет свой экран. Лечится пиннингом ключей
    устройств — до тех пор дыра остаётся, и записать её важнее, чем
    закрыть наполовину.

65. **ГЛАВНАЯ НАХОДКА: первый прогон между двумя машинами через
    интернет провалился — стороны били в TCP-порт друг друга.**
    Хост в Москве, клиент во Франции (машина Максима). Сигналинг
    свёл стороны, обе узнали адрес собеседника, обе честно
    пробивали — и обе напечатали «встречных пакетов не было: NAT
    может быть симметричным».

    **Symmetric NAT был ни при чём.** Порт в адресе был чужой.

    Сервер сигналинга видит клиента по **WebSocket-соединению**,
    то есть по TCP. `peer.to_string()` — это TCP-адрес: пара
    «внешний IP + внешний TCP-порт». Именно его сервер отдавал
    обеим сторонам как адрес для пробивания.

    А пробивание и QUIC идут по **UDP, с другого сокета**. NAT
    выдаёт ему **свой** внешний порт, никак не связанный с TCP.
    Хост бил в `82.225.151.104:52579` — TCP-порт клиента; клиент
    стучался в `91.211.134.184:34097` — TCP-порт хоста. Пакеты
    уходили в никуда.

    Видно это было прямо в логах хоста, двумя строками подряд:

        Внешний адрес: 91.211.134.184:34097
        ... хост ждёт подключения local=0.0.0.0:7000

    Порт объявленный (34097) и порт слушаемый (7000) — разные, и
    ни один из них не был внешним UDP-портом. Ровно находка 34:
    строки одного отчёта противоречат друг другу, и никто не
    сверил.

    **Почему дожило до живого прогона.** На одной машине сервер
    видит одинаковый внешний IP у обеих сторон, включает ветку
    `same_nat` и отдаёт **локальные** адреса — а в них порт
    настоящий, UDP-шный, потому что клиент берёт его у своего
    сокета (`socket.local_addr()`). То есть проверенная ветка была
    не та, которая работает через интернет. Находка 59 предупреждала
    об этом дословно, и предупреждение сбылось.

    **Сообщение об ошибке снова назвало правдоподобную неверную
    причину** — второй раз подряд после находки 63. Symmetric NAT
    объясняет симптом идеально: пакеты не доходят, диагноз звучит
    технично, и проверять его дорого (нужен другой роутер). Такое
    сообщение хуже отсутствующего — его принимают за вывод.

    **Что нужно, чтобы починить:** UDP-STUN. Внешний UDP-порт может
    узнать только сам UDP-сокет, послав пакет наружу и получив
    ответ с тем, что увидел сервер. TCP-соединение об этом порте не
    знает ничего и знать не может.

    **ЗАКРЫТО в тот же день.** `bd_core::stun` — свой минимальный
    STUN поверх UDP, не RFC 5389: нужен один вопрос своему же
    серверу, а читаемость в дампе при отладке между машинами дороже
    совместимости с чужими реализациями. Сервер слушает UDP **на том
    же порту**, что WebSocket, — иначе в файрволе VPS пришлось бы
    открывать второй. Адрес спрашивается **тем же сокетом**, который
    уйдёт в QUIC: у другого NAT завёл бы своё отображение, и мы снова
    объявляли бы чужой порт.

    Подтверждено замером **до** правки: при неизменном UDP-порте 7000
    «внешний адрес» менялся от запуска к запуску (34097 → 25132) —
    ровно потому, что это порт TCP-соединения.

66. **FEC: потери кадров 38.8 % → 2.9 %, и первая версия сделала
    ХУЖЕ.** Находки 28 и 53 предсказали это арифметикой задолго до
    кода: кадр идёт десятками фрагментов, потеря **одного** убивает
    весь кадр, и при 3 % потерь датаграмов пропадает половина кадров.
    Замер подтверждал — 38.83 % на профиле `mobile`.

    **Reed-Solomon, а не XOR — выбор сделан арифметикой ДО написания
    кода** (приём находок 41 и 44). При одинаковой избыточности 25 %
    XOR по группам даёт 4.4 % потерь на кадре из 22 фрагментов, но
    12.4 % на 63 — то есть проваливает критерий ровно на **ключевых**
    кадрах, чья потеря дороже всего. RS тратит ту же избыточность на
    кадр целиком: 0.0 % на любом размере.

    **Первая версия УХУДШИЛА результат — 45.7 % против 38.8 %.**
    Правдоподобных объяснений было три, и все опровергнуты замером:
    нехватка вызовов `receive` (цикл крутился **чаще**), вытеснение
    по ёмкости (та же ёмкость в тесте давала 5 %), переупорядочивание
    (порядок в очереди сохранялся). Гадать перестал, поставил
    счётчик — он и ответил: **499 кадров выброшено при живом паритете**
    против 45 восстановленных.

    Причина: паритет слался **после** всех данных. Кадр с потерянным
    ранним фрагментом ждёт паритета, а за это время собирается
    следующий кадр и вычищает всё старшее через `drop_older_than` —
    гибель за шаг до спасения. Лечится **перемежением** паритета с
    данными; индексы в заголовке не меняются, меняется очерёдность
    отправки.

    | | потеряно кадров | вытеснено с паритетом | показано |
    |---|---|---|---|
    | без FEC | 38.83 % | — | 906 (36.2 fps) |
    | с FEC | **2.87 %** | 43 | **1450 (58.0 fps)** |

    **Побочно закрылся критерий ЭТАПА 3**, висевший незакрытым
    (находка 53): p95 восстановления 1149 → **117 мс** при пороге 200.
    Причина была ровно та, что записана в находке, — ключевые кадры
    сами терялись.

    **Второй заход: «530 восстановлений» при НУЛЕ потерь.** Паритет
    перемежён с данными, поэтому условие «данных плюс паритета
    хватает» выполняется досрочно — когда недостающие фрагменты ещё
    **в пути**, а не потеряны. Кадры чинились вместо того, чтобы
    дождаться своих данных.

    Четыре попытки дождаться признака «данные кончились» провалились
    все: **отличить «потеряно» от «в пути» на приёме НЕЛЬЗЯ**, это
    свойство задачи, а не недоработка. И замер показал, что ожидание
    стоит дороже лишней работы — пока кадр ждёт, его вытесняет
    следующий: 2.87 % потерь при «чинить сразу» против 6.2 % при
    «ждать хвоста». Ожидание откачено, размен записан в код таблицей.

    Исправлена вместо этого **цифра**: она честная (кадры, собранные
    с участием паритета), но читалась как «спасено». Сколько FEC спас
    на самом деле, показывает только сравнение двух прогонов.

    **Тест на критерий сначала не ловил регресс** — проходил и с
    перемежением, и без (находка 32: воспроизводил не то состояние).
    Признано в коде, добавлен прицельный тест на **порядок отправки**,
    который падает без перемежения.

67. **Отчёт показал задержку МЕНЬШЕ половины RTT — то есть быстрее
    света.** Первый успешный прогон через интернет напечатал «медиана
    13.99 мс» при RTT 68.6 мс и бодрое «✅ критерий этапа 3 выполнен».
    Кадр физически не может долететь быстрее, чем за половину RTT.

    Причина в `ClockSync`: он снимает смещение часов по **минимуму**
    наблюдённых разниц, а в минимум входит и самая быстрая доставка.
    Через интернет это половина RTT, **одинаковая для всех кадров**,
    — она уходит в смещение и исчезает из результата. Остаётся
    разница задержек внутри окна, то есть джиттер.

    **Ограничение было записано в самом `ClockSync`** («метод не
    заменяет NTP», тест `constant_offset_is_removed` показывает нули
    при постоянной задержке) — и до этого дня ничего не стоило: в LAN
    половина RTT это доли миллисекунды. Первый прогон через интернет
    сделал его определяющим. Ровно находка 54: **записанная причина —
    не устранённая причина**, и запись о дефекте заменила собой
    дефект.

    Теперь клиент сверяет медиану с половиной RTT и при невозможном
    значении печатает объяснение вместо галочки: что именно измерено
    (джиттер), почему так вышло, оценку сверху и что честная проверка
    — камерой на 240 fps (§10.4).

    Вердикт по **LAN-порогу** через интернет был неверен и сам по
    себе: 35 мс задано для локальной сети, и код это даже писал
    строкой ниже, продолжая сравнивать. Находка 29 в третий раз.

    **Следствие, которое надо помнить:** настоящей цифры задержки
    через интернет у проекта **нет**. Есть верхняя оценка и честное
    предупреждение.

68. **Три дефекта прогона — и ни один не сетевой: все про ожидание
    человека.** Первый успешный прогон через интернет нашёл подряд:

    - **хост давал на ввод пароля 60 секунд.** Пароль диктуется
      голосом или пересылается в мессенджер: человек ищет, переключает
      окно, набирает — ушло 70 секунд, и хост закрыл сессию за десять
      секунд до ввода. Выглядело как **сетевая ошибка**
      («соединение закрыто», «авторизация не пройдена»), хотя канал
      был исправен и keep-alive работал;
    - **хост обещал 300 с ожидания, а ждал 90.** На экране одна цифра,
      в коде другая. Человек рассчитывал на пять минут, хост вышел из
      ожидания через полторы, и клиент подключался в пустоту;
    - **«Неверный пароль. Осталось попыток: 3»** — до того, как человек
      что-либо ввёл. Клиент шлёт пустой пароль **зондом**, чтобы
      отличить хост с авторизацией от хоста без неё, и ответ `Denied`
      печатался как ошибка человека. Счётчик при этом оставался
      полным — строка противоречила сама себе, находка 34 в миниатюре.

    **Общее у всех трёх: на localhost не проявляется ни один.** Там
    пароль виден в соседнем окне и вводится за пару секунд, а обе
    стороны запускаются одной рукой подряд. Тайминги, рассчитанные на
    машину, оказались рассчитаны не на человека.

    Лечится не только цифрами, но и тем, что `PEER_WAIT` и
    `ACCEPT_TIMEOUT` стали **одной константой**: две разных цифры на
    одно ожидание означают, что одна рано или поздно соврёт.

69. **Один `.exe` вместо трёх файлов рядом.** §7.1 требует «скачал и
    запустил», а три файла — это уже инструкция; один файл человек
    пересылает не задумываясь. `bd-host.exe` и `bd-client.exe`
    вкомпилированы в оболочку через `include_bytes!` и распаковываются
    во временный каталог при первом запуске сессии (5.3 → 12.0 МБ).

    Запуск остаётся **дочерним процессом** (§6.1): окно сессии —
    нативное Win32 со своим циклом сообщений, внутри Tauri ему не
    место. Значит бинари нужны файлами на диске — но принести их можно
    внутри себя.

    Три решения, каждое против конкретной ловушки:

    - **каталог распаковки включает версию оболочки.** Без этого после
      обновления рядом остался бы прежний бинарь и запускался бы он —
      без единого признака, что версия не та. Ровно та ловушка, на
      которой стоял сигналинг на VPS: служба крутила файл, не
      обновлявшийся вместе с кодом (находка 15 в третий раз);
    - **запись атомарная**, через `.part` и переименование: прерванная
      запись прямо в целевой файл оставила бы наполовину записанный
      `.exe`, который Windows попыталась бы запустить;
    - **сборка без продукта остаётся законной** — `build.rs` кладёт
      пустышки и предупреждает. Иначе порядок сборки диктовал бы
      порядок работы, и `cargo build` в пустом клоне падал бы на
      первом шаге.

    Главный тест распаковывает и **запускает** оба бинаря с `--help`:
    файл, записанный наполовину или не тот, там и провалится.

    **Побочно найден тихий дефект до запуска:** JS слал camelCase,
    Rust ждал snake_case. `peerId` не лёг бы в `peer_id`,
    `#[serde(default)]` подставил бы пустую строку, и клиент
    запустился бы **без ID** — отказ случился бы не там, где причина.
    Тот же класс, что находка 57б: вёрстка и бэкенд по отдельности
    верны, вместе не работают.

34. **Отчёт приписывал пайплайну 19 мс чужого времени.** В итогах
    30-минутного прогона стояли рядом две несовместимые строки:
    «профиль lan вносит **1 мс** задержки канала» и стадия
    `network` — **20.44 мс**. Двадцатикратное расхождение.

    **Ни транспорт, ни пайплайн не виноваты.** При ненулевой задержке
    кадр не готов в той же итерации, где отправлен, а `loopback`
    делает один `receive()` на один `send()`. Кадр забирается на
    следующей итерации, и к задержке канала прибавляется шаг цикла
    кодирования — ~17 мс при 60 fps. Это свойство **пробы**: в
    настоящем клиенте приём идёт своим потоком и такта энкодера
    не ждёт.

    Дефект был в вердикте: он вычитал из итога **заявленную профилем**
    задержку (1 мс), а не измеренную стадию (20 мс). Разница в 19 мс
    записывалась в счёт пайплайна, который её не тратил, — и прогон
    рапортовал «пайплайн 22.29 мс» там, где на деле 3 мс. Критерий
    формально выполнялся (22.29 ≤ 25), поэтому никто не смотрел.

    Исправлено: вычитается фактическая стадия, а расхождение
    печатается с объяснением. Проверка после правки: `lan` даёт
    **3.00 мс** против **3.06 мс** на `perfect` — совпадение, которого
    и следовало ожидать.

    **Два урока.** Первый — прямое продолжение находки 29: там вердикт
    сравнивал не с тем, здесь **вычитал не то**. Обе ошибки живут
    в одном месте — в переводе измерений в вердикт, и это место
    оказалось менее надёжным, чем сами измерения.

    Второй важнее. Расхождение было **видно в каждом прогоне с
    `lan`**: две строки в одном отчёте противоречили друг другу
    в двадцать раз. Никто не сверил их, потому что итоговая галочка
    стояла зелёная. Ровно то же самое было в находке 30 со счётчиком
    fps. **Отчёт, в котором строки не обязаны сходиться между собой,
    рано или поздно разойдётся незаметно** — теперь их сводит сама
    проба, а не внимательность читателя. Добавлена и глубина очереди
    датаграмов: без неё расхождение нечем было объяснить.

но в продукте стало бы настоящей задержкой.

Закрыто выносом клиента в `bd-client`: захвата у него нет вовсе, а
ожидание идёт на канале транспорта (`QuicTransport::receive_timeout`).
Стадия `network` на localhost: **20.44 → 7.58 мс**. Требование
провисело полтора этапа при известной причине — см. находку 54 о том,
почему записанный дефект чинится хуже незаписанного.

**Известное требование от находки 28 — ✅ ЗАКРЫТО 2026-09-01.** При
3 % потерь датаграмов терялось 51 % кадров (замер дал 38.8 %).
Сделан FEC на Reed-Solomon — **2.9 %** (находка 66). Формально это
работа этапа 6, но выполнена раньше: без неё прогон через интернет
дал бы рваную картинку, а он был условием закрытия этапов 3 и 4.

FEC **выключен по умолчанию** (`--fec`): избыточность стоит трафика
всегда, а спасает только при потерях — тот же размен, что у
джиттер-буфера (находка 42). Применяется только к видео: ввод и
курсор лечит переотправка состояния.

### Как проверять этап 2 руками

**Важно понимать ограничение.** `loopback` — это петля на одной
машине: события из окна применяются к этому же компьютеру. Полноценно
критерии этапа 2 («работать на хосте вслепую через клиент»)
проверяются только на **двух машинах**, то есть после этапа 3 (QUIC).
Сейчас проверяется другое: что ничего не падает, курсор выглядит
правильно, клавиши не залипают.

**Проверка 1 — курсор (без инжекта, безопасно):**
```powershell
cargo run --release -p bd-bench --bin loopback -- --seconds 60
```
Откроется окно «BetterDesk — loopback» с изображением вашего же
экрана. **Флаг `--agitate` здесь не нужен** — наоборот, без него
проверка честнее (находка 37).

Что делать: смотреть в окно и водить мышью по экрану. Проверять
глазами:
- картинка в окне **живая, а не замирает**. Раньше окно выглядело
  зависшим и «отвисало» только при перетаскивании — это был дефект,
  исправлен;
- курсор в окне **того же размера**, что настоящий (был вдвое
  больше при масштабе Windows 150 %);
- при наведении на текст курсор становится палочкой «I», **а не
  чёрным квадратом**;
- курсор двигается плавно и не отстаёт заметно сильнее картинки.

В отчёте в конце — строка `Курсор:`. Форм должно быть **в разы
меньше**, чем позиций (норма: сотни-тысячи позиций, десятки форм).

**Проверка 2 — UAC и смена разрешения:**
Во время того же прогона:
- вызвать любой UAC-диалог (например, запустить что-нибудь «от
  администратора»);
- **окно не должно закрыться.** Картинка замрёт на время диалога —
  это норма и неустранимо без службы (§5.1, этап 8);
- в консоли: `Захват недоступен (...) — жду`, потом `Захват
  восстановлен спустя N с`;
- отдельно: сменить разрешение монитора. Должно появиться
  `Разрешение изменилось ... пересоздаю стек кодеков`.

**Проверка 3 — ввод (осторожно, мышь будет жить своей жизнью):**
```powershell
cargo run --release -p bd-bench --bin loopback -- --seconds 30 --inject-input
```
Это **петля**: клик в окне применяется к этому же компьютеру. Годится
только чтобы убедиться, что ничего не падает. Осмысленная проверка
отклика — после этапа 3.

Проверять: в конце в отчёте `Ввод:` должно быть
`✅ на хосте не осталось зажатых клавиш`.

**Проверка 4 — залипание клавиш:**
В прогоне с `--inject-input` зажать Shift, не отпуская переключиться
Alt+Tab в другое окно, отпустить Shift там. Вернуться. Shift не
должен остаться зажатым (проверить, печатая текст где-нибудь).

**Проверка 5 — путь ввода без риска:**
```powershell
cargo run --release -p bd-bench --bin input_probe
cargo run --release -p bd-bench --bin input_probe -- --inject
```
Первая — безопасна, только формат и трекер. Вторая **двигает курсор**
5 раз по экрану: убрать руки с мыши на 3 секунды. Обе должны
завершиться `✅ Путь ввода исправен.`

**Ввод прокачивается каждую итерацию, а не только при наличии
кадра.** Человек, ткнувший мышью, ждёт отклика независимо от того,
изменился ли экран.

**Проверку руками нельзя заменить тестами.** Инжект двигает
настоящую мышь, поэтому в юнит-тестах `SendInput` намеренно не
вызывается — иначе он дёргал бы курсор на машине разработчика
и в CI. Живой вызов — только в `input_probe --inject`.

## 2. Почему Rust, а не C++

Это не вкусовщина, а требование к конкретно этому классу продукта.

**Главный аргумент — недоверенный сетевой ввод.** Remote desktop по определению
парсит байты, пришедшие от постороннего, до всякой аутентификации: заголовки QUIC,
кадры протокола, NAL-юниты H.264, события ввода, метаданные файлов. Исторически это
самый плодородный класс уязвимостей: use-after-free в парсере видео и переполнение
буфера в разборе заголовка — типовые CVE в медиастеках на C/C++. В Rust эти классы
ошибок в safe-коде исключены на этапе компиляции, а не отловлены фаззингом. Для
продукта, который даёт полный контроль над чужим ПК, это не «приятный бонус»,
а базовое требование.

**Второй аргумент — конкурентность.** Пайплайн — это 4–6 потоков (захват, энкод,
отправка, приём, декод, рендер), обменивающихся кадрами через каналы. Гонки данных
здесь — источник плавающих багов, которые не воспроизводятся. `Send`/`Sync`
превращают их в ошибки компиляции.

**Третий — сборка и зависимости.** Cargo даёт воспроизводимую сборку без CMake,
vcpkg и ручного вендоринга. Для проекта, который ведёт один человек, это экономит
недели.

**Честно о минусах:**
- Все интересные API (DXGI, NVENC, WASAPI, Win32) — это C-ABI, и их придётся
  оборачивать через `unsafe`. Rust не устраняет эту работу, он её **локализует**
  (см. §4.3).
- Экосистема видеокодеков в Rust беднее, чем в C++. Часть обёрток придётся
  писать самим.
- `windows-rs` покрывает Win32 хорошо, но документация тоньше, чем MSDN для C++.

**Вывод:** Rust не делает FFI безопасным автоматически. Он позволяет запереть
опасный код в ~5% кодовой базы и гарантировать безопасность остальных 95%.
Это правило зафиксировано в §4.3 и обязательно к соблюдению.

### 3.2. Два процесса на хосте — почему

Windows изолирует службы в Session 0 (сессия 0 неинтерактивна начиная с Vista).
Служба **не может** ни захватить экран пользователя, ни отправить ему ввод напрямую.
Поэтому хост — это два процесса:

- **`betterdesk-service`** — служба Windows, работает как `LocalSystem`. Живёт
  всегда, слушает сеть, переживает logout, умеет запускать агента. Не имеет
  доступа к экрану.
- **`betterdesk-agent`** — запускается службой в активной пользовательской сессии
  через `WTSGetActiveConsoleSessionId` → `WTSQueryUserToken` → `CreateProcessAsUser`.
  Делает захват, энкод и инжект ввода. Умирает и перезапускается при смене сессии,
  logout, переходе на secure desktop (UAC).

Связь между ними — named pipe с явным DACL (только SYSTEM и владелец сессии).
Служба владеет QUIC-соединением и проксирует кадры от агента; агент никогда
не общается с сетью напрямую. Это уменьшает поверхность атаки: недоверенные
байты разбираются в процессе с меньшими правами, чем SYSTEM.

**На этапах 1–4 службы нет вообще** — только агент как обычное приложение.
Служба появляется на этапе 8. Не усложняйте раньше.

### 4.2. Границы модулей — жёсткие правила

1. **`bd-core` не зависит ни от чего платформенного.** Он должен компилироваться
   под Linux и macOS даже сейчас. Это дисциплинирует API и оставляет дверь
   открытой для портирования.

2. **Платформенный код только за trait'ом.** Каждый крейт с `windows` в
   зависимостях экспортирует trait и его реализацию. Верхние уровни (`bd-host`,
   `bd-client`) видят **только trait**:
   ```rust
   pub trait Capturer: Send {
       fn next_frame(&mut self, timeout: Duration) -> Result<Option<Frame>>;
       fn size(&self) -> (u32, u32);
   }
   ```
   Если в `bd-host` появился `use windows::...` — это ошибка архитектуры.

3. **Кадр не копируется в системную память.** `Frame` несёт GPU-хендл
   (`ID3D11Texture2D`), а не `Vec<u8>`. Копия GPU→CPU→GPU стоит 5–10 мс и
   убивает бюджет задержки. Это правило нарушать нельзя даже «временно для отладки» —
   заведите отдельный debug-путь.

4. **`bd-transport` не знает, что внутри пакетов.** Он двигает байты с
   приоритетами и не парсит H.264.

5. **Обратная зависимость запрещена.** `bd-capture` не знает про `bd-codec`.
   Их связывает `bd-host`.

### 4.3. Правила для `unsafe` и FFI — обязательны

Это главный механизм, ради которого выбран Rust. Нарушение обесценивает выбор языка.

1. **`unsafe` разрешён только в крейтах** `bd-capture`, `bd-codec`, `bd-input`,
   `bd-audio`, `bd-render`. Во всех остальных — в корне крейта:
   ```rust
   #![forbid(unsafe_code)]
   ```

2. **Каждый `unsafe`-блок сопровождается комментарием `// SAFETY:`,**
   объясняющим, какие инварианты С-API соблюдены. Без исключений.
   ```rust
   // SAFETY: `resource` получен из AcquireNextFrame и не освобождён;
   // QueryInterface для ID3D11Texture2D гарантированно поддерживается
   // ресурсами Desktop Duplication (см. docs MS для IDXGIResource).
   unsafe { resource.cast::<ID3D11Texture2D>()? }
   ```

3. **Сырые указатели не покидают модуль.** Всё, что уходит наружу, обёрнуто
   в тип с `Drop`, который освобождает ресурс. Никаких «вызови потом
   `destroy_encoder`» в публичном API.

4. **Каждая FFI-обёртка — RAII-тип.** Пример контракта:
   ```rust
   pub struct NvencSession { /* ptr внутри, не pub */ }
   impl Drop for NvencSession {
       fn drop(&mut self) { /* nvEncDestroyEncoder */ }
   }
   ```

5. **Все входные данные из сети парсятся в safe-коде.** Никакого
   `transmute` буфера в структуру. Только явная десериализация с проверкой
   длин. Парсеры протокола обязаны иметь фаззинг-цель (§10.3).

6. **`unwrap()`/`expect()` запрещены в путях, обрабатывающих сетевые данные.**
   В инициализации — допустимы.

### 4.4. Конвенции кода

- `rustfmt` с дефолтами. `clippy` с `-D warnings` в CI.
- Ошибки: `thiserror` в библиотечных крейтах, `anyhow` только в бинарях.
- Логи: `tracing`. В горячем пути (per-frame) — только `trace!`, и он должен
  компилироваться в ноль в release (`tracing` features).
- **Никаких `println!`** вне `bd-bench`.
- Асинхронность: `tokio` — только в `bd-transport` и серверной части.
  Пайплайн захват→энкод→рендер — **синхронные выделенные потоки**, а не async.
  Причина: у нас не тысячи соединений, у нас один поток кадров с жёстким
  дедлайном 16.6 мс. Планировщик async здесь добавляет джиттер.
- Имена: `snake_case` модули, `bd-*` крейты, `BetterDesk` в UI-текстах.

### 4.5. Единое время

Весь проект использует один источник монотонного времени: `bd_core::time::now()`.
Каждый кадр несёт `capture_ts` от момента захвата и проносит его через весь
пайплайн до рендера. Без этого измерить задержку невозможно, а измерение
задержки — главный критерий проекта. Реализовать это на этапе 1, а не потом.

## 5. Ключевые технические решения

### 5.1. Захват экрана

**Основной путь: DXGI Desktop Duplication** (`IDXGIOutputDuplication`).
Даёт GPU-текстуру без копирования в RAM, самая низкая задержка, работает с
Windows 8. Это то, что использует Sunshine как основной путь.

Правила работы, важные для задержки:
- Освобождать кадр (`ReleaseFrame`) **непосредственно перед** следующим
  `AcquireNextFrame`, а не сразу после обработки. API накапливает обновления
  между вызовами, и время между release и acquire — это время, когда
  обновления копятся.
- `AcquireNextFrame` с таймаутом ~16 мс; `DXGI_ERROR_WAIT_TIMEOUT` означает
  «экран не изменился» — это не ошибка, это повод не отправлять кадр вообще.
- Обрабатывать `DXGI_ERROR_ACCESS_LOST` (смена разрешения, UAC, Ctrl+Alt+Del,
  переключение GPU) — пересоздавать дупликацию. Это происходит регулярно,
  не считать это исключительной ситуацией.

**Частоту кодирования обязан ограничивать пайплайн, а не источник.**
DXGI отдаёт кадр на каждое изменение экрана — при активной работе это
150–250 кадров в секунду. Кодировать их все нельзя: при CBR битрейт
делится на фактическое число кадров, и каждому достаётся втрое меньше
бит, чем заложено. Это **видно глазом** как пикселизация (находка 30).
Инструмент — `bd_core::FrameLimiter`; он не спит, а отвечает, пора ли
кодировать: ожидание в горячем пути остановило бы захват и сделало
следующий кадр устаревшим.

**Фоллбэк: Windows.Graphics.Capture (WGC).** Нужен потому, что DXGI
Duplication требует, чтобы приложение работало на том же GPU, что и дисплей —
на ноутбуках с гибридной графикой это ломается. WGC работает cross-GPU без
вмешательства пользователя, ценой чуть большей задержки. Требует Windows 10 1903+.

Ограничение обоих: не захватывают secure desktop (UAC, экран блокировки) из
пользовательской сессии — это решается только службой (§3.2, этап 8).

### 5.2. Энкодер

Приоритет реализации: **NVENC** (у вас NVIDIA) → AMF → QuickSync.

Настройки для нашей задачи (NVENC):
- `tuning_info = NV_ENC_TUNING_INFO_ULTRA_LOW_LATENCY`
- preset `P1`–`P3` (P1 — максимальная производительность)
- **Без B-кадров.** B-кадры требуют кадров из будущего → +1–2 кадра задержки.
- **Без look-ahead** по той же причине.
- `rateControlMode = NV_ENC_PARAMS_RC_CBR`, причём
  `maxBitRate = averageBitRate` — иначе пресет оставляет своё
  значение и молча зажимает поток (находка 30)
- Infinite GOP + периодические Intra Refresh вместо полных IDR-кадров.
  Полный keyframe даёт всплеск битрейта → пик задержки на плохом канале.
  **Внимание: `intra_refresh` в `EncoderConfig` объявлен, но к NVENC
  пока НЕ применяется.** На практике это не мешает (за 40 с прогона
  ключевой кадр один), но настройка сейчас декоративная — при
  реализации не считать её работающей.
- **`maxQP = 38`** — потолок огрубления. Без него при нехватке бит
  энкодер уходит в QP 45–51, где картинка распадается на квадраты.
  Размен сознательный: лучше редкий всплеск трафика, чем нечитаемый
  текст (§7.2).
- **`enableAQ = 1`** — адаптивное квантование бережёт текст: без него
  кадр огрубляется равномерно, и текст «плывёт» первым.
- **VBV в 1.5 кадра, а не в 1.0.** Буфер ровно в кадр упирается в
  потолок при любом всплеске сложности сцены, и качество проседает
  рывком. Полтора кадра дают запас, оставаясь много меньше кадра
  задержки.
- **`enableLookahead = 0` явно.** Пресет может включить его сам,
  а look-ahead копит кадры до кодирования — бюджет уедет незаметно.
- Zero-copy: регистрировать D3D11-текстуру напрямую через
  `NvEncRegisterResource`, не проходя через системную память.

**Обёртка — своя, через `bindgen`** (реализовано, см. §0.1). Заголовки
берутся из `vendor/nvcodec/` — это nv-codec-headers под **MIT**, а не
дистрибутив NVIDIA SDK, чьи заголовки вендорить нельзя по лицензии.

Два правила, выведенных из практики:

- **Версия заголовков не должна превышать версию API драйвера.**
  Совместимость односторонняя: старый SDK на новом драйвере работает,
  наоборот — нет. Сейчас взята 13.0 (драйверы 570+), это покрывает
  больше пользовательских машин, чем 13.1.
- **DLL грузится в рантайме, а не линкуется.** Сборка не требует SDK,
  а машина без NVIDIA GPU даёт понятную ошибку вместо отказа загрузчика.

### 5.3. Транспорт

**QUIC через `quinn`** (Apache-2.0/MIT).

Почему QUIC, а не сырой UDP:
- Готовое TLS 1.3-рукопожатие, шифрование и защита от replay — не надо писать
  криптопротокол самому (это самая частая причина катастрофических дыр).
- Connection migration: смена Wi-Fi → LTE не рвёт сессию.
- Готовый congestion control, к которому можно приделать свой.
- Обходит middlebox'ы лучше сырого UDP.

Почему не WebRTC целиком: он тянет SDP, SRTP, весь стек, навязывает свою
модель и добавляет задержку в jitter buffer, которым мы хотим управлять сами.
Берём из него только ICE.

**Разделение трафика — принципиально:**

| Данные | Механизм QUIC | Почему |
|---|---|---|
| Видеокадры | **Unreliable datagrams** | Устаревший кадр не нужен. Ретрансмит старого кадра — хуже, чем его потеря |
| Аудио | Unreliable datagrams | То же + свой FEC |
| События ввода | Unreliable datagrams + свой ACK | Нужна минимальная задержка, надёжность обеспечиваем сами через нумерацию и переотправку последнего состояния |
| Файлы, буфер, управление | Reliable streams | Здесь надёжность важнее задержки |

Использование reliable streams для видео вызвало бы head-of-line blocking:
один потерянный пакет задержал бы все последующие кадры. Это ровно то,
чего мы избегаем.

**Congestion control:** дефолтный BBR/Cubic от quinn на этапах 1–5.
На этапе 6 — свой контроллер битрейта, реагирующий на изменение
времени доставки кадров (по принципу Google Congestion Control), потому что
дефолтный CC оптимизирует пропускную способность, а нам нужна задержка.

### 5.4. NAT traversal

- Хост при старте регистрируется на сигналинге, получает 9-значный ID.
- Клиент запрашивает соединение по ID; сервер сводит стороны, обмениваются
  ICE-кандидатами.
- Hole punching: одновременная отправка UDP с обеих сторон.
- Библиотека: `str0m` (MIT) или извлечённый из него ICE-агент. Не тянуть
  `webrtc-rs` целиком — он тяжелее, чем нужно.
- Ожидаемая успешность прямого соединения ~80–85%. Остальным нужен TURN-релей,
  который **отложен до появления бюджета** (§9.3). До тех пор — честное
  сообщение «прямое соединение невозможно» вместо тихого зависания.

### 5.5. Декодер и рендер

- Аппаратный: D3D11VA через Media Foundation. Выход — NV12-текстура в GPU.
- Софтверный фоллбэк: `openh264` (BSD-2-Clause, бинарники Cisco снимают
  патентный вопрос для декодера). Нужен для машин без аппаратного декода —
  включая тестовую машину во Франции.
- Рендер: D3D11 swapchain с `DXGI_SWAP_EFFECT_FLIP_DISCARD`, конверсия
  NV12→RGB шейдером на GPU.
- **`SetMaximumFrameLatency(1)`** и `WaitableObject` на swapchain — иначе
  DWM добавит 1–2 кадра задержки.
- Не включать VSync (`Present(0, ...)`) — ждать вертикальной синхронизации
  значит добавить до 16 мс. Тиринг здесь предпочтительнее лага.

## 6. UI и дизайн

### 6.1. Разделение UI и видео — критичное правило

**Видео никогда не рендерится в webview.** Ни через `<video>`, ни через canvas,
ни через WebCodecs. Webview добавляет композитинг браузера (+10–20 мс) и
лишает контроля над очередью кадров.

Архитектура:
- **Окно оболочки** — Tauri v2, webview. Список машин, настройки, логин,
  подключение. Здесь задержка не важна.
- **Окно сессии** — обычное Win32-окно, создаётся напрямую, D3D11 swapchain,
  собственный цикл сообщений в своём потоке. Tauri про него не знает.
- Оверлей поверх видео (панель управления, статистика) рисуется **в том же
  D3D11**, а не webview.

Попытки Tauri-сообщества рендерить GPU-контент под webview в одном окне
до сих пор не имеют надёжного решения на Windows. Не идти этим путём.

### 6.2. Визуальный язык

Светлая, минималистичная, спокойная тема. Дизайн-принципы:

- **Основа:** белый/почти белый фон (`#FFFFFF` / `#FAFAFA`), тёмно-серый
  текст (`#1A1A1A`), не чистый чёрный.
- **Один акцентный цвет** — спокойный синий (`#2E6BE6` в районе). Используется
  только для основного действия на экране. Всё остальное — оттенки серого.
- **Скругления:** 12px для карточек, 8px для кнопок и полей. Мягко, но не «пузыри».
- **Тени:** очень мягкие, низкая непрозрачность (`0 1px 3px rgba(0,0,0,0.06)`).
  Никаких резких границ — разделение через воздух и лёгкий фон.
- **Типографика:** системный шрифт (Segoe UI Variable на Win11). Размеры:
  13px основной текст, 11px вторичный, 20px заголовки. Межстрочный 1.5.
- **Воздух:** отступы кратны 4px, базовый ритм 16px. Не жалеть пустого места.
- **Анимации:** 150–200 мс, `ease-out`. Только на смену состояния, не декоративные.

**Дизайн-токены обязательны с первого дня** — CSS-переменные в одном файле.
Даже если тёмная тема не нужна сейчас, добавлять её потом в разбросанные
хардкод-цвета дороже в разы.

**Сделано на этапе 3** (не на 7): `docs/design/tokens.css` и живой макет
`docs/design/mockup.html`. Противоречия с §11 нет: запрещено *писать
оболочку*, а не *решать, как она выглядит*. Второе стоит ничего и
избавляет этап 7 от вычищения литеральных цветов из десятка
компонентов. Правило: компонент **никогда** не пишет цвет литералом,
только `var(--...)` — иначе тёмная тема, уже описанная в токенах,
сломается в первом же месте, где про неё забыли.

Главный экран: крупное поле «ID этого компьютера» с кнопкой копирования,
поле ввода чужого ID, ниже — список сохранённых машин карточками. Всё.
Никаких вкладок и меню на первом экране.

## 7. Модель продукта

### 7.1. Два режима запуска

Один бинарник, два режима — как AnyDesk:
- **Портативный режим** (по умолчанию): запустил `.exe` — получил ID и
  одноразовый пароль, можно принимать подключения. Без установки, без
  регистрации, без прав администратора.
- **Установленный режим**: ставит службу, включает необслуживаемый доступ
  с постоянным паролем, автозапуск.

Это прямое следствие требования «клиент скачал и всё работает».

### 7.2. Что попадает в продукт

Реализуется (в порядке этапов roadmap): видео 1080p60, ввод, звук с хоста,
буфер обмена (текст и файлы), передача файлов, многомониторность,
необслуживаемый доступ через службу, адаптация к плохому каналу.

**Явно НЕ делаем:** геймпады/ViGEm, relative mouse для FPS-игр, звук
с клиента на хост (микрофон), несколько зрителей одновременно, мобильные
клиенты. Это решение принято сознательно — сценарий продукта — работа
и администрирование, а не игры.

### 7.3. Аутентификация

Слои, от нижнего к верхнему:

1. **Идентичность устройства.** При первом запуске генерируется пара ключей
   Ed25519, приватный хранится в DPAPI (`CryptProtectData`, привязка к машине
   и пользователю). Публичный ключ = криптографическая идентичность хоста.
   ID (9 цифр) — это удобное имя, а **не** средство аутентификации.
2. **Пиннинг.** При первом соединении клиент показывает fingerprint публичного
   ключа хоста и запоминает его. При последующих — молча проверяет. Изменение
   ключа = громкое предупреждение (защита от MITM на сигналинге).
3. **Авторизация сессии.** Либо одноразовый пароль (портативный режим,
   отображается на хосте), либо постоянный пароль (Argon2id-хеш, никогда
   не хранится в открытом виде), либо ранее спаренное устройство из списка
   доверенных.
4. **Аккаунт оператора** (только для того, кто подключается): нужен для
   списка своих машин и подписки. Хосту аккаунт не нужен никогда.

## 8. Модель безопасности (сводка; полностью — docs/security-model.md)

### 8.1. Транспорт

QUIC даёт TLS 1.3 из коробки. Но: сертификаты сигналинга/релея не должны
давать доступ к содержимому сессии. Поэтому поверх QUIC — **свой E2E-слой**:

- Обмен ключами: X25519 ECDH, ключи подписаны долговременными Ed25519-ключами
  устройств → аутентифицированный обмен, MITM невозможен без компрометации
  устройства.
- Шифрование: ChaCha20-Poly1305 (или AES-GCM при наличии AES-NI).
- Ротация ключей каждые N минут / M пакетов.
- Библиотеки: `ring` или `rustls` + `snow` (Noise Protocol). **Не писать
  свою криптографию** — использовать Noise IK как готовый проверенный паттерн.

Следствие: сервер сигналинга и будущий релей видят только зашифрованные байты
и метаданные (кто с кем, когда, сколько). Это записано в архитектуру с самого
начала, а не добавляется потом.

### 8.2. Что клиент не должен хранить

Никаких API-ключей, никаких секретов подписи, никаких «магических констант»,
компрометация которых что-то даёт. Всё, что клиент знает — свой приватный
ключ (даёт доступ только к своей же идентичности).

### 8.3. Проверка подписки — на сервере

**Это ключевой пункт.** Клиент не решает, есть ли у пользователя подписка.
Клиент **не может** установить сессию без участия сервера:

- Хост регистрируется на сигналинге и держит соединение. Без сигналинга
  чужой хост не найти (кроме LAN).
- Чтобы получить ICE-кандидаты хоста, клиент предъявляет JWT. Сервер
  проверяет подписку **перед** тем, как выдать кандидатов.
- Токен короткоживущий (минуты), привязан к device_id и session_id.
- Сервер ведёт лимиты: число одновременных сессий, число устройств.

Патч бинарника даёт взломщику работающий LAN-режим — и ничего больше.
Через интернет он не подключится, потому что не получит адрес пира.

### 8.4. Чего защита клиента дать НЕ может — честно

- **Реверс бинарника неустраним.** Код, исполняемый на машине атакующего,
  будет прочитан. Это математический факт, а не недоработка.
- **Обфускация не защищает, а замедляет.** Она превращает час работы в день.
  Для нас это не окупается.
- **Анти-дебаг ломает легальных пользователей** (антивирусы, отладчики
  разработчиков) чаще, чем останавливает взломщиков.

**Где усилия оправданы:**
- Серверная проверка прав (§8.3) — единственная реально работающая защита.
- Подпись бинарников (Authenticode) — против подмены обновлений и ложных
  срабатываний антивирусов. Это защита пользователя, не защита от пиратства.
- Проверка целостности обновлений (подписанные манифесты).
- Rate limiting и аномалия-детекция на сервере.

**Чего мы не обещаем и не будем делать:** «невзламываемость», DRM, packer'ы,
виртуализация кода. Один человек не выигрывает эту гонку, а цена —
ложные срабатывания антивирусов, которые убьют доверие к продукту
на старте гораздо надёжнее, чем пиратство.

### 8.5. Поверхность атаки, требующая особого внимания

Ранжировано по опасности:
1. **Инжект ввода** — цель любого атакующего. События ввода принимаются
   только после полной аутентификации, из установленной сессии.
2. **Передача файлов** — path traversal (`../`), симлинки, запись в системные
   каталоги. Все пути канонизируются и проверяются на принадлежность
   разрешённому каталогу. Никогда не доверять имени файла от пира.
3. **Парсеры протокола и H.264** — обязательный фаззинг (§10.3).
4. **Буфер обмена** — форматы OLE от недоверенной стороны.
5. **Служба, работающая как SYSTEM** — минимум логики, строгий DACL на pipe.

## 9. Лицензии и право

### 9.1. Правило зависимостей — жёсткое

Продукт закрытый и платный. Следовательно:

- **Разрешено:** MIT, Apache-2.0, BSD-2/3, ISC, Zlib, MPL-2.0 (файловый
  копилефт, но не заражает наш код — допустимо при неизменённом использовании).
- **Запрещено:** GPL любой версии, AGPL, LGPL при статической линковке,
  SSPL, любые «source-available» лицензии.

Это проверяется автоматически. `deny.toml` с `cargo-deny` настраивается
на **этапе 1**, до того как накопились зависимости. CI падает при
попытке добавить GPL-зависимость.

Практические следствия:
- **Нельзя брать код из Sunshine** (GPLv3) и **RustDesk** (AGPLv3). Изучать
  их архитектуру как идеи — можно и нужно. Копировать код — нет.
- **Нельзя x264** (GPL) и GPL-сборки FFmpeg. Для софт-декодера — `openh264`
  (BSD-2-Clause).
- FFmpeg-компоненты, если понадобятся, — только LGPL-сборка с динамической
  линковкой, и лучше избежать вовсе.

### 9.2. Кодек — решение и риски

**Решение: H.264 High Profile сейчас, абстракция `trait Codec` готова к
HEVC и AV1.**

Обоснование и честные риски:

*За H.264:*
- Аппаратный энкод есть у любого GPU с ~2012 года, включая вашу GTX 10xx.
  AV1-энкод требует RTX 40xx / RX 7000 / Arc — это отсечёт 90% ваших
  потенциальных пользователей.
- Аппаратный декод есть везде, включая слабые ноутбуки клиентов.
- Работает в браузере без вопросов (важно для будущего веб-клиента).

*Патентный риск — честно:*
- H.264 покрыт патентным пулом Via LA (бывший MPEG LA). За продукты
  «энкодер+декодер», продаваемые конечным пользователям, предусмотрены роялти.
- **Но:** первые 100 000 единиц в год — royalty-free. Реально это означает,
  что до первых 100 000 платящих пользователей в год вы не платите ничего.
  Дальше — $0.20 за единицу с потолком.
- Последние патенты пула в США истекают около 2027 года, то есть проблема
  сама рассасывается на горизонте жизни проекта.
- Отдельно: за платную подписку на сервис (в отличие от продажи копий)
  условия отличаются — этот вопрос надо будет уточнить у юриста **до**
  первой платной продажи, но не сейчас.

*Риск, который принимаем сознательно:* если продукт «выстрелит» до 2027 года
и перевалит 100k пользователей, появится статья расходов. Это хорошая проблема,
и она решается либо роялти (копейки на фоне выручки), либо переключением
на AV1, ради чего и делается абстракция кодека.

*Почему не AV1 сразу:* беспатентный, лучше сжимает — но энкодера нет на вашем
железе, нет у большинства пользователей, и вы не сможете даже разработать
и протестировать. Заложить в архитектуру — да; реализовывать сейчас — нет.

*Почему не HEVC:* худший вариант из трёх — патентная ситуация сложнее H.264
(три конкурирующих пула), а преимущество перед H.264 в нашем сценарии
низкой задержки невелико.

### 9.3. Инфраструктура при нулевом бюджете

- **Сигналинг:** Oracle Cloud Always Free (ARM VPS, бессрочно бесплатно) или
  Fly.io free tier. Rust-сигналинг потребляет <50 МБ RAM и обслужит тысячи
  клиентов. Трафик через него — килобайты на сессию.
- **STUN:** можно поднять свой на том же VPS или использовать публичные
  Google STUN на старте.
- **TURN-релей:** отложен. Это единственная статья, где трафик стоит денег
  (видео 10 Мбит/с × часы). Появляется только когда появится выручка.
  До тех пор пользователям с symmetric NAT честно сообщается, что прямое
  соединение невозможно.

## 10. Сборка, запуск, тестирование

### 10.1. Требования к машине разработчика

- Windows 11, Visual Studio Build Tools 2022+ (MSVC toolchain, **не GNU**)
- Rust stable, target `x86_64-pc-windows-msvc` (версия в `rust-toolchain.toml`)
- Windows SDK
- LLVM/libclang — нужен `bindgen` для генерации биндингов NVENC.
  **Обязателен только для ХОСТА.** Без него сборка не падает: NVENC
  отключается с предупреждением, и клиент собирается как обычно
  (находка 61). Установщик LLVM под Windows не прописывает себя в
  PATH, поэтому проверка смотрит и `C:\Program Files\LLVM\bin`
- Node.js 20+ — для Tauri-фронтенда (с этапа 7)
- `cargo install cargo-deny --locked` — проверка лицензий (§9.1)

**NVIDIA Video Codec SDK устанавливать НЕ нужно.** Заголовки лежат
в `vendor/nvcodec/` (MIT), а `nvEncodeAPI64.dll` приходит с драйвером
и грузится в рантайме. Для запуска хоста нужен драйвер NVIDIA 570+.

Фактическое состояние машины разработчика — в §0.1.

### 10.2. Команды

```powershell
# Сборка всего workspace
cargo build --release

# Прототип пайплайна с выводом задержки (этап 1)
cargo run --release -p bd-bench --bin loopback

# Проверка железа и живой тест пайплайна
cargo run --release -p bd-bench --bin capture_probe
cargo run --release -p bd-bench --bin nvenc_probe
cargo run --release -p bd-bench --bin encode_probe

# Хост
cargo run --release -p bd-host

# Клиент
cargo run --release -p bd-client -- --connect 127.0.0.1:7000

# Проверки перед коммитом — обязательны
cargo fmt --all --check      # --all обязателен, см. §0.1
cargo clippy --all-targets -- -D warnings
cargo test --workspace
cargo deny check licenses bans sources   # запрет GPL/AGPL

# UI (с этапа 7)
cd ui && npm run tauri dev
```

### 10.3. Тестирование

- **Юнит-тесты** — для всей логики без платформенных зависимостей: парсеры
  протокола, джиттер-буфер, контроллер битрейта, канонизация путей.
- **Фаззинг обязателен** (`cargo-fuzz`) для: парсера пакетов протокола,
  разбора имён файлов, десериализации событий ввода. Это код, который
  первым встречает недоверенные байты.
- **Интеграционные** — пайплайн на localhost с синтетическим источником кадров.
- **Замер задержки — часть CI-отчёта, а не ручная проверка.** Регресс
  задержки должен быть виден.
- **Сетевая эмуляция:** `clumsy` или Windows QoS для внесения потерь и
  джиттера. Тестовые профили: LAN (0.1% потерь, 1 мс), хороший интернет
  (0.5%, 30 мс), плохой мобильный (3%, 80 мс, джиттер 40 мс).

### 10.4. Как измеряется задержка

Главная метрика проекта. Определение: **glass-to-glass** — от момента, когда
пиксель изменился на хосте, до момента, когда он показан на клиенте.

Метод для разработки: каждый кадр несёт `capture_ts`; в момент `Present`
на клиенте считается разница. Это не учитывает задержку самого дисплея,
но позволяет отслеживать регрессы.

Метод для честной проверки: съёмка камерой на 240 fps экранов хоста и клиента
рядом, счётчик кадров на экране, подсчёт разницы. Делается на контрольных
точках, не постоянно.

Оверлей со статистикой (задержка по компонентам, fps, битрейт, потери)
должен быть доступен по горячей клавише в любой сборке.

## 11. Границы этапов

Правило, нарушение которого — главный риск проекта:

**Пока не достигнута приемлемая задержка на этапе 1–3, никакого UI,
никаких аккаунтов, никакой передачи файлов.** Если пайплайн не укладывается
в бюджет, весь остальной продукт не имеет смысла — он проиграет Parsec
на его же поле.

Каждый этап в [docs/roadmap.md](docs/roadmap.md) имеет явные измеримые
критерии готовности. Этап не считается закрытым, пока критерии не выполнены
и не зафиксированы измерения.

### Оболочка сделана досрочно — решение от 2026-08-31

**Правило выше нарушено сознательно, по прямому решению владельца
проекта.** Записано здесь, а не в коде, чтобы следующий агент не счёл
это недосмотром и не начал «исправлять».

Что сделано: `ui/` на Tauri v2 — главный экран из `docs/design/`,
собирается в `.exe`, который можно открыть и посмотреть.

**Что защищает от главного риска.** Опасность §11 в том, что UI
съедает время, которое нужно пайплайну, и скрывает недостижимую
задержку за красивой картинкой. Здесь этого не происходит:

- **пайплайн уже уложился** — 8.02 мс между двумя процессами при
  бюджете 25, то есть вопрос «возможно ли вообще» отвечён;
- **оболочка не участвует в пути кадра.** Она отдельное окно и
  отдельный процесс; видеоокно остаётся нативным Win32 + D3D11
  (§6.1). Ни один кадр через webview не идёт — это условие
  нарушать нельзя ни при каких обстоятельствах;
- **оболочка ничего не подключает.** Кнопки не ведут к транспорту:
  соединение по ID требует сигналинга (этап 4), которого нет.
  Экран показывает состояние, а не управляет сессией.

**Чего это стоит.** Этап 3 остаётся незакрытым: замера между двумя
машинами нет. Оболочка его не приближает и не заменяет. Если после
живого замера в LAN окажется, что задержка не укладывается в 35 мс,
разбираться придётся с пайплайном, а оболочка будет лежать
неоплаченным долгом — ровно то, от чего §11 и предостерегает.

## 12. Что делать при неопределённости

- **Не выдумывать сигнатуры API.** DXGI, NVENC, WASAPI, ScreenCaptureKit —
  искать в официальной документации. Неверно вспомненная сигнатура в `unsafe`
  коде — это не ошибка компиляции, это порча памяти.
- Значимые архитектурные решения записывать в `docs/adr/` короткой запиской:
  контекст, решение, последствия.
- Если решение противоречит этому файлу — сначала обновить этот файл,
  потом писать код.
