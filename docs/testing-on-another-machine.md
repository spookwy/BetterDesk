# Проверка на второй машине

Инструкция для второй стороны. Читать код не нужно.

Цель — узнать две вещи: запускается ли BetterDesk на машине, которую
разработчик не видел, и какая получается задержка через настоящую
сеть.

**Самый ценный прогон — в локальной сети,** то есть между двумя
компьютерами, подключёнными к одному роутеру (хоть по Wi-Fi).
Именно он закрывает последний невыполненный пункт текущего этапа:
задержка между двумя реальными машинами должна уложиться в 35 мс.
На одном компьютере это проверить нельзя в принципе — там нет ни
настоящего RTT, ни расхождения часов между сторонами.

Прогон через интернет тоже полезен, но отвечает на другой вопрос
(«работает ли вообще на чужой машине»), и порог 35 мс к нему
не относится.

---

## Про две стороны — прочитать первым делом

Роли **не симметричны**, и это важно понимать до начала:

| Роль | Что делает | Что для этого нужно |
|---|---|---|
| **Клиент** | смотрит чужой экран | декодер (есть почти в любой Windows) |
| **Хост** | отдаёт свой экран | захват **и аппаратный энкодер** |

Видеокарта NVIDIA для роли хоста **не обязательна**: поддерживаются
NVENC (NVIDIA), Intel QuickSync и AMD — всё, что Windows считает
аппаратным энкодером H.264. Обычно это есть на любой машине не
старше десяти лет, включая ноутбуки со встроенной графикой.

Чего пока нет — софтверного кодирования. Машина совсем без
аппаратного энкодера хостом быть не сможет; клиентом — сможет.
Шаг 2 покажет, какой случай перед вами.

---

## Что понадобится

- Windows 10 (сборка 1903+) или Windows 11, 64 бита
- [Rust](https://rustup.rs/) — при установке выбрать вариант по
  умолчанию (MSVC)
- Visual Studio Build Tools с компонентом «Разработка классических
  приложений на C++»

Для роли **клиента** видеокарта NVIDIA не нужна вовсе.

**LLVM ставить не надо.** Он нужен только для сборки NVENC-бэкенда,
то есть только хосту с картой NVIDIA. Без него сборка не падает:
в выводе появится строка `NVENC-бэкенд отключён`, и это нормально.

Если Build Tools не установлены, сборка остановится с сообщением
`linker link.exe not found`. Оно означает ровно одно: при установке
Build Tools не отмечена галочка «Разработка классических приложений
на C++». Отметить её и **перезагрузиться** — без перезагрузки система
не увидит новые программы. VS Code не подходит, это другая программа.

---

## Шаг 1. Собрать

```powershell
cargo build --release
```

Первая сборка занимает несколько минут. Если она падает — прислать
разработчику весь вывод целиком, дальше идти не нужно.

Собираются два приложения: `bd-host` (отдаёт экран) и `bd-client`
(смотрит), плюс набор проб для диагностики.

---

## Шаг 2. Проверить машину

**Это главный шаг.** Проба ничего не ломает и не требует соединения —
она только смотрит, что на машине есть:

```powershell
cargo run --release -p bd-bench --bin machine_probe
```

Вывод на машине без NVIDIA выглядит примерно так:

```
=== BetterDesk: проверка машины ===

✅ Захват экрана: DXGI Desktop Duplication работает, кодируется 1920x1080
     монитор 0: \\.\DISPLAY1 — 1920x1080
✅ Энкодер: Media Foundation: Intel® Quick Sync Video H.264 Encoder MFT
     (NVENC недоступен, и это нормально: ...)
✅ Декодер: H.264 D3D11VA готов (встроенный декодер Windows)

Энкодеры H.264, заявленные системой:
  • Intel® Quick Sync Video H.264 Encoder MFT — аппаратный
  • H264 Encoder MFT — софтверный

--- Вывод ---
✅ ХОСТ: машина может отдавать свой экран.
✅ КЛИЕНТ: машина может смотреть чужой экран.
```

**Прислать этот вывод целиком** — по нему видно всё нужное.

Как читать:

- **`✅ ХОСТ` и `✅ КЛИЕНТ`** — можно проверять в обе стороны.
- Строка «NVENC недоступен, и это нормально» — не ошибка: на машине
  без NVIDIA используется Intel или AMD, и это штатный путь.
- **`❌ ХОСТ`** — аппаратного энкодера нет вовсе либо ни один не
  подошёл. Клиентом машина при этом обычно остаётся годной.
- **`❌ КЛИЕНТ`** — дальше идти нельзя, нужен софтверный декодер,
  которого пока нет.

## Шаг 3. Открыть порты

Нужен **один порт**: 7000. Видео, ввод и курсор идут по нему вместе.

(Раньше портов было три — 7000, 7001, 7002. Отсюда старый симптом
«картинка идёт, а мышь и клавиатура нет»: открывали только первый.
Теперь такого не бывает — либо работает всё, либо ничего.)

На **хосте**, в PowerShell от администратора:

```powershell
New-NetFirewallRule -DisplayName "BetterDesk" -Direction Inbound `
  -Protocol UDP -LocalPort 7000 -Action Allow
```

Протокол именно **UDP**: QUIC работает поверх него, а не поверх TCP.

Если хост за роутером и проверка идёт через интернет — этот же порт
надо пробросить на его локальный адрес. В локальной сети
проброс не нужен.

Убрать правило после проверки:

```powershell
Remove-NetFirewallRule -DisplayName "BetterDesk"
```

## Шаг 4. Подключиться

Тот, чей экран показывают (**хост**), запускает у себя:

```powershell
cargo run --release -p bd-host -- --listen 0.0.0.0:7000 --seconds 120
```

Тот, кто смотрит (**клиент**), подключается — вместо `АДРЕС`
подставить IP хоста (локальный в одной сети, внешний через интернет):

```powershell
cargo run --release -p bd-client -- --connect АДРЕС:7000 --seconds 100
```

Порт указывается **один** — 7000. Остальные два клиент вычисляет сам.

Хост ждёт подключения 5 минут, клиент сдаётся через 15 секунд — то
есть **хост запускают первым**. `--seconds` задаёт длительность:
по её истечении обе стороны сами печатают итоги. Хосту стоит давать
с запасом, чтобы он не завершился раньше клиента.

Откроется окно с экраном хоста. **F9** показывает и прячет панель со
статистикой: задержка, fps, RTT, потери.

### Управление хостом — отдельно и осознанно

По умолчанию хост ввод клиента **принимает, но не применяет**: мышь
и клавиатура на нём не шевелятся. Чтобы клиент действительно управлял
хостом, хост запускается так:

```powershell
cargo run --release -p bd-host -- --listen 0.0.0.0:7000 --seconds 120 --inject-input
```

Флаг явный намеренно: аутентификации пока нет вообще, и любой, кто
дотянется до этих портов, получит управление. Для проверки в
локальной сети это нормально, через интернет — включать, только
понимая риск, и не оставлять запущенным.

### Проверить в обе стороны

Это **два отдельных прогона**, а не один: одна сессия показывает
экран в одну сторону.

1. Первый прогон: хостом машина A, клиентом машина B.
2. Второй прогон: поменяться ролями — хостом B, клиентом A.

Второй прогон получится, если `machine_probe` на машине B сказал
`✅ ХОСТ`. Видеокарта NVIDIA для этого не нужна — годятся Intel
QuickSync и AMD.

## Что смотреть глазами

Цифры соберутся сами, а вот это увидит только человек:

1. **Картинка живая**, не замирает и не идёт рывками.
2. **Нет пикселизации** — картинка не грубеет крупными квадратами.
3. **Курсор** нормального размера, и над текстом видна буква «I»,
   а не квадрат и не пустое место.
4. **Ничего не падает** за всё время прогона.

Если что-то из этого не так — описать словами, что именно видно.
Это ценнее любых цифр: несколько дефектов подряд нашлись именно так,
и ни один из них не давал ни ошибки, ни неверного числа.

---

## Что прислать в конце

1. Вывод `machine_probe` целиком.
2. Итоговые отчёты **обеих** сторон — их печатают `bd-host` и
   `bd-client` при завершении. Цифры двух сторон должны сходиться
   между собой, и расхождение само по себе полезная находка.
3. Словами: как выглядело — плавно или рвано, что было не так.

Задержка через интернет будет заметно больше, чем в локальной сети,
и это ожидаемо: критерий проекта (≤ 35 мс) задан для LAN. Здесь
проверяется не он, а то, что всё вообще работает на другой машине.

---

## Если что-то пошло не так

Приложения объясняют ошибки словами, а не кодами. Самые вероятные:

| Что видно | Что это значит |
|---|---|
| `linker link.exe not found` | Не установлены Build Tools с галочкой «Разработка классических приложений на C++». Поставить и **перезагрузиться**. VS Code — другая программа, не подходит |
| `Unable to find libclang` | Старая версия кода. Обновиться (`git pull`): теперь сборка без LLVM не падает, NVENC просто отключается |
| `NVENC-бэкенд отключён` в выводе сборки | **Норма**, а не ошибка. Значит нет LLVM; клиенту NVENC не нужен |
| `Захват экрана недоступен` | Гибридная графика — известное ограничение DXGI, фоллбэк запланирован |
| `Аппаратный декодер H.264 недоступен` | Нужен софт-декодер, его пока нет |
| `NVENC недоступен` | Норма: используется Intel QuickSync или AMD |
| `ни один аппаратный энкодер не подошёл` | Гибридная графика: энкодер не видит GPU, которому принадлежит кадр |
| Видео идёт, но курсор и клавиатура не работают | Сообщите разработчику: с одним каналом такого быть не должно — раньше это означало закрытые порты 7001-7002, теперь порт один |
| Соединение не устанавливается вовсе | Порты закрыты файрволом или NAT (шаг 3); правило должно быть на **UDP**, а не TCP |

Прямое соединение через NAT (без проброса порта) появится позже —
это отдельный этап работы.
