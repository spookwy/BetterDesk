# Модель безопасности BetterDesk

Документ описывает, от чего продукт защищает, **как именно**, и — что важнее —
**от чего он не защищает**. Второе честно проговорено, потому что ложные
обещания безопасности хуже их отсутствия.

Remote desktop даёт полный контроль над чужим компьютером. Это делает
требования к безопасности выше, чем у почти любого другого класса
пользовательского ПО.

## 1. Модель угроз

### 1.1. От кого защищаемся

| # | Противник | Возможности | Приоритет |
|---|---|---|---|
| 1 | Пассивный наблюдатель сети | Читает трафик (публичный Wi-Fi, провайдер) | Высокий |
| 2 | Активный MITM | Подменяет трафик, выдаёт себя за пира | Высокий |
| 3 | Скомпрометированный сервер сигналинга | Видит метаданные, может сводить не тех пиров | Высокий |
| 4 | Атакующий, знающий ID хоста | Пытается подключиться без пароля | Высокий |
| 5 | Подключившийся пользователь | Уже в сессии, атакует хост через протокол | Средний |
| 6 | Локальный процесс на хосте | Пытается украсть ключи или сессию | Средний |
| 7 | Пират | Реверсит бинарник ради обхода подписки | **Низкий** (§6) |

### 1.2. От чего не защищаемся принципиально

- Скомпрометированная ОС хоста (кейлоггер, руткит). Если машина заражена,
  remote desktop — не первая проблема.
- Физический доступ к разблокированной машине.
- Пользователь, добровольно давший доступ мошеннику. Это социальная инженерия;
  снижается предупреждениями в UI, а не криптографией.
- Реверс-инжиниринг клиентского бинарника (§6).
- **Локальный процесс под тем же пользователем.** DPAPI расшифрует
  ключ и для него — это его устройство, а не наш недосмотр (§3.1).
- **Подмена при самом первом подключении** к незнакомой машине.
  Отличить первую встречу от подмены изнутри невозможно; смягчается
  сверкой отпечатка голосом (§3.2).

Разница между «не защищаемся» и «не сделали» существенна, и в этом
документе она разведена: здесь — принципиальные пределы модели, в
§0 — то, что просто ещё не написано.

## 2. Транспортная безопасность

### 2.1. Два слоя, а не один

```
┌──────────────────────────────────────────────┐
│  Данные приложения (видео, ввод, файлы)      │
├──────────────────────────────────────────────┤
│  СЛОЙ 2: E2E — Noise IK          ⬜ НЕ СДЕЛАН │  ← релей не видит
│  X25519 ECDH + ChaCha20-Poly1305             │
├──────────────────────────────────────────────┤
│  СЛОЙ 1: QUIC + TLS 1.3            ✅ РАБОТАЕТ│  ← защита от сети
├──────────────────────────────────────────────┤
│  UDP                                         │
└──────────────────────────────────────────────┘
```

**Что есть сейчас (сентябрь 2026):** слой 1. Между двумя машинами
идёт QUIC с TLS 1.3, то есть трафик зашифрован, а подмену стороны
закрывает пиннинг ключей (§3.2). Сертификат при этом самоподписанный
и сам по себе ничего не подтверждает — доверие даёт **опознание по
ключу устройства**, которое проходит внутри уже установленного
соединения.

**Зачем тогда второй слой?** При работе через релей (§5.4 CLAUDE.md,
отложен до появления бюджета) TLS-сессия терминируется **на релее** —
он увидит открытый трафик. E2E-слой это исключает: релей двигает
байты, которые не может прочитать.

**Почему не сделан сейчас.** Пока соединение прямое, второй слой
защищает от угрозы, которой нет: посредника между сторонами не
существует. Делать его заранее — платить сложностью криптопротокола
за сценарий, до которого проект не дошёл.

Оговорка, из-за которой этот пункт нельзя откладывать бесконечно:
**добавить E2E в работающий протокол задним числом дороже**, чем
заложить сразу. Поэтому решение перепроверяется, как только релей
появляется в плане, а не когда он уже написан.

### 2.2. Выбор Noise IK (когда дойдёт до релея)

Не пишем свой криптопротокол. Noise Protocol Framework — формально
верифицированный набор паттернов рукопожатия. Паттерн **IK** подходит точно:
инициатор (клиент) заранее знает статический публичный ключ респондента
(хоста) — ровно наша ситуация после первого спаривания.

Свойства, которые даёт IK:
- Взаимная аутентификация по статическим ключам.
- Forward secrecy: компрометация долговременного ключа не раскрывает
  записанные ранее сессии.
- Защита идентичности инициатора от пассивного наблюдателя.
- Устойчивость к replay.

Реализация: крейт `snow` (Apache-2.0). **Не реализовывать примитивы вручную.**

### 2.3. Шифры

- Обмен ключами: X25519
- Симметричное: ChaCha20-Poly1305 (или AES-256-GCM при наличии AES-NI —
  быстрее на современных x86)
- Хеш: BLAKE2s / SHA-256
- Подписи: Ed25519

Ротация сессионного ключа: каждые 15 минут или 2^24 пакетов, что раньше.

## 3. Идентичность устройства и пиннинг

**Статус: реализовано** (этап 5, 2026-09-02). Код —
`bd-crypto::identity`, `bd-crypto::pinning`, `bd-secrets`.

### 3.1. Ключи

При первом запуске хост генерирует пару **Ed25519** (`DeviceIdentity`).
Это его настоящая идентичность. 9-значный ID — лишь удобное имя для
человека, **не средство аутентификации**: он короткий, предсказуемый и
передаётся через сервер, которому мы не доверяем полностью.

Разделение ролей записано в трёх местах кода, потому что смешать их
легко, а цена высока:

| | ID (девять цифр) | Ключ Ed25519 |
|---|---|---|
| назначение | назвать машину человеку | доказать, что это она |
| секретность | не секрет, диктуется вслух | приватная часть не покидает машину |
| подделка | тривиальна | требует приватного ключа |

**Слабые ключи отвергаются при разборе.** Для точки малого порядка
существует подпись, верная почти под любым сообщением, — предъявивший
такой ключ прошёл бы опознание, не зная никакого секрета. Обычный
`verify` в `ed25519-dalek` их **принимает** (совместимость со старыми
протоколами), поэтому используется `verify_strict`, а сам ключ
проверяется на `is_weak` уже при разборе — чтобы причина отказа была
названа, а не сводилась к «подпись не сошлась».

**Хранение приватного ключа: DPAPI** (`bd-secrets`,
`CryptProtectData` в контексте текущего пользователя). Файл,
скопированный на другой компьютер или открытый другим пользователем,
не расшифруется.

Старый незашифрованный ключ (от версий до этапа 5) **переносится под
защиту при первом запуске**. Без переноса обновление программы
сменило бы личность машины, и все, кто её запомнил, получили бы
предупреждение о подмене — а после пары ложных тревог человек
перестаёт читать настоящие.

**Честные ограничения:**

- от процесса, работающего с правами того же пользователя, DPAPI не
  защищает: он вызовет то же API и расшифрует. Полная защита
  требовала бы TPM или пароля при каждом запуске — оба ломают
  «скачал и запустил» (§7.1 CLAUDE.md);
- при переустановке Windows ключ DPAPI пропадает вместе с профилем, и
  машина честно теряет свою личность. Это ожидаемое поведение, а не
  сбой; отдельный вариант ошибки (`NotOurs`) называет причину, чтобы
  человек не искал повреждение диска.

### 3.2. Пиннинг — защита от скомпрометированного сигналинга

Сервер сигналинга сводит пиров. Скомпрометированный сервер может
подсунуть клиенту чужую машину вместо нужной — классический MITM.

**Пароль от этого не спасает, и это стоит проговорить, потому что
кажется наоборот.** Пароль доказывает, что подключающийся знает
секрет. Он ничего не говорит о том, **кому этот секрет сообщили**:
человек продиктует шесть цифр подставному хосту с той же
готовностью, что настоящему.

Защита — TOFU (trust on first use) с пиннингом:

1. **Опознание идёт до пароля.** Клиент шлёт случайный вызов (16
   байт), хост подписывает его ключом устройства. Порядок здесь и
   есть защита: сообщать секрет раньше, чем выяснено, с кем
   разговариваем, значит отдавать его кому попало.
2. **Первое соединение:** клиент показывает отпечаток (8 групп по 4
   hex-знака, 128 бит) и запоминает ключ. Отпечаток сверяется голосом
   — тем же звонком, которым диктуется пароль. Это единственный
   момент, требующий внимания человека.
3. **Последующие:** отпечаток проверяется молча.
4. **Изменение ключа:** подключение **останавливается**, показываются
   оба отпечатка — прежний и новый.

**Подпись проверяется раньше сличения со списком.** Иначе атакующий,
назвавшийся чужим ключом без подписи, получил бы вердикт «известная
машина»: ключ-то верный, он публичный и общеизвестен.

**Проверка ничего не запоминает сама.** Запись в список — отдельный
шаг, после согласия человека. Проверка, записывающая ключ при
сличении, тихо узаконивала бы подмену, то есть делала бы
противоположное тому, ради чего написана.

**Предел TOFU, записанный честно:** первое подключение не защищено.
Если подмена случилась именно тогда, клиент запомнит ключ атакующего.
Ничто, кроме внешнего канала доверия, не отличает первую встречу от
подмены — отсюда отпечаток, читаемый вслух. Все последующие
подключения защищены полностью.

**Смена ключа неоднозначна, и мы не притворяемся, что это не так.**
Так выглядит подмена; так же выглядит переустановка Windows или
потеря `device.key`. Отличить изнутри невозможно, поэтому решает
человек, а наше дело — дать ему обе строки и не подталкивать к
«OK» по привычке.

Это модель SSH, проверенная десятилетиями.

## 4. Авторизация сессии

**Статус: реализовано, кроме списка доверенных устройств.**

Слои, в порядке прохождения:

1. **Опознание устройства** (§3.2) — до всего остального. Клиент
   убеждается, что говорит с той машиной, прежде чем сообщать секрет.
2. **Пароль сессии.** Портативный режим: одноразовый пароль из шести
   цифр, генерируется при каждом запуске, показан на экране хоста.
   Хранится как **Argon2id**-хеш, никогда в открытом виде.

   Параметры — умолчания крейта `argon2`: **19 МБ памяти, 2
   итерации, параллелизм 1**. Это рекомендация OWASP, а не наш
   произвол. Ранняя редакция этого документа обещала «не менее 64 МБ
   и 3 итерации» — цифра была взята из воздуха и не соответствовала
   коду; исправлено по факту, а не наоборот.

   Проверка идёт через `verify_password` крейта, который сравнивает
   хеши за постоянное время.
3. **Проверка ДО первого кадра.** Соединение установлено, но экран не
   отдан. Проверь мы пароль после начала передачи, посторонний увидел
   бы хотя бы один кадр — а этого достаточно, чтобы прочесть, что
   открыто на экране.
4. **Подтверждение на хосте** (`--ask`) — человек у хоста явно
   разрешает подключение. Спрашивается **после** пароля: иначе
   всякий, кто знает девять цифр, дёргал бы владельца машины. Пароль
   отсеивает посторонних, вопрос защищает от того, кому пароль уже
   сказали, но кого не ждали именно сейчас.

   Молчание дольше минуты — **отказ**, а не согласие: пустить
   неизвестного, потому что хозяин не успел ответить, — ровно то, от
   чего вопрос защищает.

   **По умолчанию выключено**, и это осознанно: хост часто запускают,
   чтобы к нему подключились в отсутствие хозяина (§7.1 CLAUDE.md).
   Вопрос, на который некому ответить, там превратил бы продукт в
   неработающий.
5. ⬜ **Список доверенных устройств** — после спаривания клиент
   подключается без пароля. Не сделано; появится вместе с
   необслуживаемым доступом (этап 8).

**Отказ по паролю и отказ человека — разные ответы протокола**
(`Denied` и `Rejected`). Смешай их, и человек на клиенте пошёл бы
заново вводить правильный пароль, гадая, что набрал не так.

**Ограничение попыток:** три, затем сессия рвётся. Шесть цифр — это
миллион вариантов, и три попытки на соединение делают перебор
бессмысленным; хост при каждом запуске выдаёт новый пароль.
Экспоненциальная задержка не нужна: она защищала бы от перебора
внутри одной сессии, которого и так нет.

## 5. Серверная проверка подписки — центральное решение

### 5.1. Принцип

**Клиент не решает, есть ли подписка. Клиент не может установить соединение
через интернет без участия сервера.**

Это не «проверка», которую можно обойти патчем — это архитектурная
зависимость. Разница принципиальна: проверка в клиенте — это `if`, который
можно занопить. Зависимость — это отсутствие данных, которые неоткуда взять.

### 5.2. Как это работает

```
Клиент                     Сервер                      Хост
  │                          │                           │
  │                          │◄──── регистрация ID ──────│
  │                          │      (постоянное WS)      │
  │                          │                           │
  │── вход, получение JWT ──►│                           │
  │◄─ JWT (TTL 15 мин) ──────│                           │
  │                          │                           │
  │── «хочу к ID 123456789»─►│                           │
  │   + JWT                  │                           │
  │                          │ 1. проверка подписи JWT   │
  │                          │ 2. проверка подписки в БД │
  │                          │ 3. проверка лимитов       │
  │                          │                           │
  │                          │──── запрос кандидатов ───►│
  │                          │◄─── ICE-кандидаты ────────│
  │◄─ ICE-кандидаты ─────────│                           │
  │                          │                           │
  │══════ P2P, E2E-шифрование, сервер не участвует ═════►│
```

Ключевое: **ICE-кандидаты хоста (его реальный адрес) выдаются только после
проверки подписки на сервере.** Без адреса пира соединение невозможно
физически — это не проверка, а отсутствие необходимой информации.

### 5.3. Что даёт взлом клиента

Честный разбор:

| Что сделает взломщик | Результат |
|---|---|
| Уберёт проверку подписки в клиенте | Ничего. Клиент её и не делал |
| Подделает JWT | Не сможет — нет приватного ключа сервера (он на сервере) |
| Переиспользует чужой JWT | TTL 15 минут, привязан к device_id, лимит сессий |
| Будет использовать в LAN | **Сработает.** И это сознательное решение — см. ниже |
| Поднимет свой сигналинг-сервер | Сработает, но только для своих же хостов, требует своей инфраструктуры и не масштабируется как продукт |

**Почему LAN оставлен бесплатным:** технически закрыть его невозможно
(там нет сервера в цепочке), а попытки — навредят легальным пользователям
с плохим интернетом. Лучше сделать это явной особенностью бесплатного тарифа,
чем притворяться, что защищено.

### 5.4. Дополнительный контроль на сервере

- Лимит одновременных сессий на аккаунт.
- Лимит зарегистрированных устройств.
- Детекция аномалий: один аккаунт с 50 разных IP за час.
- Отзыв подписки прекращает выдачу новых токенов; текущая сессия
  завершается по истечении TTL.

## 6. Чего защита клиента дать НЕ может — честно

Раздел написан прямо, потому что нереалистичные ожидания здесь приводят
к трате недель на бесполезную работу.

### 6.1. Реверс бинарника неустраним

Код, исполняющийся на машине атакующего, будет прочитан. Это следствие
того, что процессор должен его выполнить. Ни один продукт в истории —
включая продукты компаний с бюджетами в миллиарды — этого не изменил.

**Вывод:** проектировать надо так, чтобы чтение кода не давало ничего.
Именно поэтому §5 построен на серверной зависимости, а не на секретах
в клиенте.

### 6.2. Обфускация — почти всегда пустая трата

Что она реально даёт: превращает час работы реверсера в день. Что стоит:
усложнение отладки собственных крашей, ложные срабатывания антивирусов,
раздутый бинарник.

**Для нас не окупается.** Единственный сценарий, где имело бы смысл —
если бы в клиенте был критичный секрет. Его там по построению нет.

### 6.3. Анти-дебаг вредит больше, чем помогает

`IsDebuggerPresent` и подобное обходится за минуты любым, кто знает,
что делает. Зато ломает: работу под отладчиком при поддержке пользователей,
совместимость с антивирусами (поведение неотличимо от малвари),
запуск в виртуалках (а это ваш собственный сценарий тестирования).

**Не делаем.**

### 6.4. Где усилия действительно оправданы

| Мера | Зачем | Приоритет |
|---|---|---|
| Серверная зависимость (§5) | Единственная работающая защита монетизации | Критично |
| Подпись Authenticode | Против подмены обновлений и ложных срабатываний AV. Защита **пользователя** | Высокий |
| Подписанные манифесты обновлений | Против подмены при доставке | Высокий |
| Фаззинг парсеров | Против реальных атак на пользователей | Высокий |
| Rate limiting на сервере | Против перебора и злоупотреблений | Средний |
| Обфускация, packer'ы, анти-дебаг | — | **Не делаем** |

### 6.5. Что мы не обещаем

Ни в маркетинге, ни в документации не заявляем «невзламываемость»,
«военное шифрование» и подобные формулировки. Заявляем проверяемое:
сквозное шифрование, релей не видит содержимого, открытая спецификация
протокола. Это честно и это то, что реально проверяется.

## 7. Поверхность атаки внутри сессии

Даже аутентифицированный пир может быть враждебным (украденный пароль,
скомпрометированный клиент). Ранжировано по опасности:

### 7.1. Передача файлов — самое опасное место

Атаки: path traversal (`../../Windows/System32`), абсолютные пути,
UNC-пути (`\\attacker\share`), симлинки и junction points, зарезервированные
имена Windows (`CON`, `PRN`, `AUX`, `NUL`, `COM1`), альтернативные потоки
данных (`file.txt:evil.exe`), Unicode-нормализация для обхода фильтров.

Обязательные меры:
- Все пути канонизируются (`std::fs::canonicalize`), затем проверяется,
  что результат **начинается с** разрешённого каталога.
- Имя файла от пира используется **только как имя**, никогда как путь.
- Явный чёрный список зарезервированных имён Windows.
- Запись через временный файл с последующим атомарным переименованием.
- Отдельная фаззинг-цель для функции валидации пути.

### 7.2. Парсеры протокола и H.264

Первый код, встречающий недоверенные байты. Правила (выполняются):
- ✅ Только safe Rust, никакого `transmute` буфера в структуру.
- ✅ Явная проверка длин перед каждым чтением.
- ✅ Ограничение максимального размера сообщения и числа фрагментов;
  индекс фрагмента проверяется против их числа — иначе сборщик,
  кладущий фрагмент по индексу, вырос бы по команде постороннего.
- ✅ **Фаззинг** — 20 свойств, 82 тысячи случаев за прогон
  (`bd-core/tests/fuzz_parsers.rs`,
  `bd-transport/tests/fuzz_packets.rs`). Идут обычными тестами, то
  есть в CI на каждом коммите, а не по особому поводу.

Проверяются три свойства, в порядке важности: **не паникует ни на
чём** (паника до авторизации — отказ в обслуживании по одному
датаграму), **не принимает мусор за валидное**, **encode → parse
ничего не теряет**.

**Оговорка, из-за которой критерий этапа 5 помечен «не буквально».**
Взят `proptest`, а не `cargo-fuzz`: последний требует nightly, а
toolchain проекта прибит к stable с этапа 0, и воспроизводимость
сборки продукта важнее буквы критерия.

Разница между ними измерена, а не предположена. При проверке тестов
на способность падать подделка `"grante"` в разборе `granted`
**прошла** мимо 4096 случайных строк: пространство семисимвольных
строк слишком велико, чтобы генератор набрёл на соседа валидного
слова. Coverage-guided фаззер дошёл бы туда сам.

Отсюда практика, применённая в коде: у каждого парсера, чей ответ
означает **разрешение**, есть отдельный тест на окрестность
валидного входа — обрезки, дописки, смена регистра. Случайная
генерация проверяет «не падает на мусоре»; «не принимает
почти-валидное» надо проверять построением.

Час работы libFuzzer остаётся отдельной задачей, если проект
когда-нибудь допустит nightly для папки `fuzz/`.

Аппаратный декодер — это драйвер, то есть код в ядре. Кривой H.264-поток
теоретически способен уронить драйвер. Ограничить нельзя, но можно
не усугублять: проверять базовую валидность NAL перед передачей в декодер.

### 7.3. Инжект ввода

✅ События ввода принимаются только из установленной
аутентифицированной сессии: до пароля хост игнорирует всё, кроме
сообщений авторизации.

✅ **Управление выключено по умолчанию** — режим «только просмотр».
Хост применяет ввод клиента только с флагом `--inject-input`. Флаг
явный намеренно: управление чужим компьютером — отдельное решение, и
включаться молча оно не должно.

⬜ **Мгновенный разрыв по горячей клавише на хосте — не сделан.**
Это заметный пробел, и он записан здесь, а не замолчан: человек за
хостом сейчас может остановить сессию только закрытием окна консоли.
Требование к реализации — работать **всегда**, в том числе при
зависшем UI, то есть жить не в оболочке, а в самом хосте.

⬜ Отзыв управления посреди сессии (без разрыва) тоже не сделан:
`--inject-input` задаётся при запуске и не меняется.

### 7.4. Буфер обмена

Форматы OLE от недоверенной стороны — известный вектор. Ограничить
принимаемые форматы белым списком (текст, изображения, список файлов),
не принимать произвольные CF-форматы.

### 7.5. Служба как LocalSystem

Работает с наивысшими правами — минимизируем логику внутри:
- Служба не парсит недоверенные данные сама; она проксирует их агенту,
  работающему с правами пользователя.
- Named pipe между ними — с явным DACL (SYSTEM + владелец активной сессии),
  никаких `NULL DACL`.
- Никаких путей к исполняемым файлам из конфигурации без валидации.

## 8. Приватность и метаданные

Что видит сервер сигналинга даже при полном E2E:
- Какой ID подключался к какому и когда.
- IP-адреса обеих сторон.
- Длительность сессии.

Это неустранимо для сервиса, который сводит пиров. Что делаем:
- Явно пишем это в политику конфиденциальности. Не притворяемся,
  что не видим ничего.
- Не логируем содержимое, не логируем IP дольше необходимого для
  антифрода (например, 30 дней).
- Даём возможность полностью обойти сервер в LAN.
