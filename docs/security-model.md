# Модель безопасности BetterDesk

Документ описывает, от чего продукт защищает, **как именно**, и — что важнее —
**от чего он не защищает**. Второе честно проговорено, потому что ложные
обещания безопасности хуже их отсутствия.

Remote desktop даёт полный контроль над чужим компьютером. Это делает
требования к безопасности выше, чем у почти любого другого класса
пользовательского ПО.

---

## 1. Модель угроз

### 1.1. От кого защищаемся

| # | Противник | Возможности | Приоритет |
|---|---|---|---|
| 1 | Пассивный наблюдатель сети | Читает трафик (публичный Wi-Fi, провайдер) | Высокий |
| 2 | Активный MITM | Подменяет трафик, выдаёт себя за пира | Высокий |
| 3 | Скомпрометированный сервер сигналинга | Видит метаданные, может сводить не тех пиров | Высокий |
| 4 | Атакующий, знающий ID хоста | Пытается подключиться без пароля | Высокий |
| 5 | Подключившийся пользователь | Уже в сессии, атакует хост через протокол | Средний |
| 6 | Локальный процесс на хосте | Пытается украсть ключи или сессию | Средний |
| 7 | Пират | Реверсит бинарник ради обхода подписки | **Низкий** (§6) |

### 1.2. От чего не защищаемся принципиально

- Скомпрометированная ОС хоста (кейлоггер, руткит). Если машина заражена,
  remote desktop — не первая проблема.
- Физический доступ к разблокированной машине.
- Пользователь, добровольно давший доступ мошеннику. Это социальная инженерия;
  снижается предупреждениями в UI, а не криптографией.
- Реверс-инжиниринг клиентского бинарника (§6).

## 2. Транспортная безопасность

### 2.1. Два слоя, а не один

```
┌──────────────────────────────────────────────┐
│  Данные приложения (видео, ввод, файлы)      │
├──────────────────────────────────────────────┤
│  СЛОЙ 2: E2E — Noise IK                      │  ← релей не видит
│  X25519 ECDH + ChaCha20-Poly1305             │
├──────────────────────────────────────────────┤
│  СЛОЙ 1: QUIC + TLS 1.3                      │  ← защита от сети
├──────────────────────────────────────────────┤
│  UDP                                         │
└──────────────────────────────────────────────┘
```

**Зачем два слоя, если TLS уже шифрует?** Потому что при работе через релей
(будущий этап) TLS-сессия терминируется на релее — он увидит открытый трафик.
E2E-слой это исключает: релей двигает байты, которые не может прочитать.
Заложено с самого начала, потому что добавить E2E в работающий протокол
задним числом — переписывание.

### 2.2. Выбор Noise IK

Не пишем свой криптопротокол. Noise Protocol Framework — формально
верифицированный набор паттернов рукопожатия. Паттерн **IK** подходит точно:
инициатор (клиент) заранее знает статический публичный ключ респондента
(хоста) — ровно наша ситуация после первого спаривания.

Свойства, которые даёт IK:
- Взаимная аутентификация по статическим ключам.
- Forward secrecy: компрометация долговременного ключа не раскрывает
  записанные ранее сессии.
- Защита идентичности инициатора от пассивного наблюдателя.
- Устойчивость к replay.

Реализация: крейт `snow` (Apache-2.0). **Не реализовывать примитивы вручную.**

### 2.3. Шифры

- Обмен ключами: X25519
- Симметричное: ChaCha20-Poly1305 (или AES-256-GCM при наличии AES-NI —
  быстрее на современных x86)
- Хеш: BLAKE2s / SHA-256
- Подписи: Ed25519

Ротация сессионного ключа: каждые 15 минут или 2^24 пакетов, что раньше.

## 3. Идентичность устройства и пиннинг

### 3.1. Ключи

При первом запуске хост генерирует пару **Ed25519**. Это его настоящая
идентичность. 9-значный ID — лишь удобное имя для человека, **не средство
аутентификации**: он короткий, предсказуемый и передаётся через сервер,
которому мы не доверяем полностью.

**Хранение приватного ключа** (по возрастанию надёжности):
- Минимум: DPAPI (`CryptProtectData`) с флагом `CRYPTPROTECT_LOCAL_MACHINE`
  для службы или пользовательский контекст для агента. Привязывает ключ
  к машине/пользователю.
- Лучше: дополнительное шифрование ключом, производным от пароля хоста
  (Argon2id), чтобы кража файла без пароля ничего не давала.

**Честное ограничение:** от процесса, работающего с правами того же
пользователя, DPAPI не защищает — он вызовет то же API и расшифрует.
Полная защита требовала бы TPM; это возможное улучшение, не блокер.

### 3.2. Пиннинг — защита от скомпрометированного сигналинга

Сервер сигналинга сводит пиров. Скомпрометированный сервер может подсунуть
клиенту свой ключ вместо ключа хоста — классический MITM.

Защита — TOFU (trust on first use) с пиннингом:
1. **Первое соединение:** клиент показывает fingerprint ключа хоста
   (например, 6 слов или 8 hex-групп). Пользователь сверяет его с тем,
   что показано на экране хоста. Это единственный момент, требующий
   внимания человека.
2. **Последующие:** fingerprint проверяется молча.
3. **Изменение ключа:** громкое предупреждение с блокировкой подключения
   до явного подтверждения. Формулировка должна объяснять риск, а не
   предлагать «OK» по привычке.

Это модель SSH, проверенная десятилетиями.

## 4. Авторизация сессии

Слои, все обязательны:

1. **Криптографическая аутентификация устройств** (Noise IK) — пройдена
   до любого обмена данными.
2. **Пароль сессии:**
   - Портативный режим: одноразовый пароль, генерируется при запуске,
     показан на экране хоста, живёт до перезапуска.
   - Установленный режим: постоянный пароль, хранится как **Argon2id**-хеш
     (параметры: не менее 64 МБ памяти, 3 итерации). Никогда в открытом виде.
   - Проверка пароля устойчива к timing-атакам (сравнение за постоянное время).
3. **Подтверждение на хосте** — для портативного режима по умолчанию
   включено: человек у хоста явно разрешает подключение.
4. **Список доверенных устройств** — после успешного спаривания клиент может
   подключаться без пароля. Список редактируется и очищается в UI.

**Rate limiting:** не более 5 попыток пароля, затем экспоненциальная
задержка. Это защита от перебора при известном ID.

## 5. Серверная проверка подписки — центральное решение

### 5.1. Принцип

**Клиент не решает, есть ли подписка. Клиент не может установить соединение
через интернет без участия сервера.**

Это не «проверка», которую можно обойти патчем — это архитектурная
зависимость. Разница принципиальна: проверка в клиенте — это `if`, который
можно занопить. Зависимость — это отсутствие данных, которые неоткуда взять.

### 5.2. Как это работает

```
Клиент                     Сервер                      Хост
  │                          │                           │
  │                          │◄──── регистрация ID ──────│
  │                          │      (постоянное WS)      │
  │                          │                           │
  │── вход, получение JWT ──►│                           │
  │◄─ JWT (TTL 15 мин) ──────│                           │
  │                          │                           │
  │── «хочу к ID 123456789»─►│                           │
  │   + JWT                  │                           │
  │                          │ 1. проверка подписи JWT   │
  │                          │ 2. проверка подписки в БД │
  │                          │ 3. проверка лимитов       │
  │                          │                           │
  │                          │──── запрос кандидатов ───►│
  │                          │◄─── ICE-кандидаты ────────│
  │◄─ ICE-кандидаты ─────────│                           │
  │                          │                           │
  │══════ P2P, E2E-шифрование, сервер не участвует ═════►│
```

Ключевое: **ICE-кандидаты хоста (его реальный адрес) выдаются только после
проверки подписки на сервере.** Без адреса пира соединение невозможно
физически — это не проверка, а отсутствие необходимой информации.

### 5.3. Что даёт взлом клиента

Честный разбор:

| Что сделает взломщик | Результат |
|---|---|
| Уберёт проверку подписки в клиенте | Ничего. Клиент её и не делал |
| Подделает JWT | Не сможет — нет приватного ключа сервера (он на сервере) |
| Переиспользует чужой JWT | TTL 15 минут, привязан к device_id, лимит сессий |
| Будет использовать в LAN | **Сработает.** И это сознательное решение — см. ниже |
| Поднимет свой сигналинг-сервер | Сработает, но только для своих же хостов, требует своей инфраструктуры и не масштабируется как продукт |

**Почему LAN оставлен бесплатным:** технически закрыть его невозможно
(там нет сервера в цепочке), а попытки — навредят легальным пользователям
с плохим интернетом. Лучше сделать это явной особенностью бесплатного тарифа,
чем притворяться, что защищено.

### 5.4. Дополнительный контроль на сервере

- Лимит одновременных сессий на аккаунт.
- Лимит зарегистрированных устройств.
- Детекция аномалий: один аккаунт с 50 разных IP за час.
- Отзыв подписки прекращает выдачу новых токенов; текущая сессия
  завершается по истечении TTL.

## 6. Чего защита клиента дать НЕ может — честно

Раздел написан прямо, потому что нереалистичные ожидания здесь приводят
к трате недель на бесполезную работу.

### 6.1. Реверс бинарника неустраним

Код, исполняющийся на машине атакующего, будет прочитан. Это следствие
того, что процессор должен его выполнить. Ни один продукт в истории —
включая продукты компаний с бюджетами в миллиарды — этого не изменил.

**Вывод:** проектировать надо так, чтобы чтение кода не давало ничего.
Именно поэтому §5 построен на серверной зависимости, а не на секретах
в клиенте.

### 6.2. Обфускация — почти всегда пустая трата

Что она реально даёт: превращает час работы реверсера в день. Что стоит:
усложнение отладки собственных крашей, ложные срабатывания антивирусов,
раздутый бинарник.

**Для нас не окупается.** Единственный сценарий, где имело бы смысл —
если бы в клиенте был критичный секрет. Его там по построению нет.

### 6.3. Анти-дебаг вредит больше, чем помогает

`IsDebuggerPresent` и подобное обходится за минуты любым, кто знает,
что делает. Зато ломает: работу под отладчиком при поддержке пользователей,
совместимость с антивирусами (поведение неотличимо от малвари),
запуск в виртуалках (а это ваш собственный сценарий тестирования).

**Не делаем.**

### 6.4. Где усилия действительно оправданы

| Мера | Зачем | Приоритет |
|---|---|---|
| Серверная зависимость (§5) | Единственная работающая защита монетизации | Критично |
| Подпись Authenticode | Против подмены обновлений и ложных срабатываний AV. Защита **пользователя** | Высокий |
| Подписанные манифесты обновлений | Против подмены при доставке | Высокий |
| Фаззинг парсеров | Против реальных атак на пользователей | Высокий |
| Rate limiting на сервере | Против перебора и злоупотреблений | Средний |
| Обфускация, packer'ы, анти-дебаг | — | **Не делаем** |

### 6.5. Что мы не обещаем

Ни в маркетинге, ни в документации не заявляем «невзламываемость»,
«военное шифрование» и подобные формулировки. Заявляем проверяемое:
сквозное шифрование, релей не видит содержимого, открытая спецификация
протокола. Это честно и это то, что реально проверяется.

## 7. Поверхность атаки внутри сессии

Даже аутентифицированный пир может быть враждебным (украденный пароль,
скомпрометированный клиент). Ранжировано по опасности:

### 7.1. Передача файлов — самое опасное место

Атаки: path traversal (`../../Windows/System32`), абсолютные пути,
UNC-пути (`\\attacker\share`), симлинки и junction points, зарезервированные
имена Windows (`CON`, `PRN`, `AUX`, `NUL`, `COM1`), альтернативные потоки
данных (`file.txt:evil.exe`), Unicode-нормализация для обхода фильтров.

Обязательные меры:
- Все пути канонизируются (`std::fs::canonicalize`), затем проверяется,
  что результат **начинается с** разрешённого каталога.
- Имя файла от пира используется **только как имя**, никогда как путь.
- Явный чёрный список зарезервированных имён Windows.
- Запись через временный файл с последующим атомарным переименованием.
- Отдельная фаззинг-цель для функции валидации пути.

### 7.2. Парсеры протокола и H.264

Первый код, встречающий недоверенные байты. Правила:
- Только safe Rust, никакого `transmute` буфера в структуру.
- Явная проверка длин перед каждым чтением.
- Ограничение максимального размера кадра и числа фрагментов
  (защита от исчерпания памяти).
- **Обязательный фаззинг** через `cargo-fuzz` — минимум час на цель
  перед закрытием этапа 5.

Аппаратный декодер — это драйвер, то есть код в ядре. Кривой H.264-поток
теоретически способен уронить драйвер. Ограничить нельзя, но можно
не усугублять: проверять базовую валидность NAL перед передачей в декодер.

### 7.3. Инжект ввода

События ввода принимаются только из установленной аутентифицированной
сессии. Дополнительно: возможность отключить управление (режим «только
просмотр») и мгновенный разрыв по горячей клавише на хосте — это должно
работать всегда, даже при зависшем UI.

### 7.4. Буфер обмена

Форматы OLE от недоверенной стороны — известный вектор. Ограничить
принимаемые форматы белым списком (текст, изображения, список файлов),
не принимать произвольные CF-форматы.

### 7.5. Служба как LocalSystem

Работает с наивысшими правами — минимизируем логику внутри:
- Служба не парсит недоверенные данные сама; она проксирует их агенту,
  работающему с правами пользователя.
- Named pipe между ними — с явным DACL (SYSTEM + владелец активной сессии),
  никаких `NULL DACL`.
- Никаких путей к исполняемым файлам из конфигурации без валидации.

## 8. Приватность и метаданные

Что видит сервер сигналинга даже при полном E2E:
- Какой ID подключался к какому и когда.
- IP-адреса обеих сторон.
- Длительность сессии.

Это неустранимо для сервиса, который сводит пиров. Что делаем:
- Явно пишем это в политику конфиденциальности. Не притворяемся,
  что не видим ничего.
- Не логируем содержимое, не логируем IP дольше необходимого для
  антифрода (например, 30 дней).
- Даём возможность полностью обойти сервер в LAN.
