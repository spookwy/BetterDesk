## Часть 1. Что берём у открытых решений

### 1.1. Sunshine (GPLv3)

Игровой хост-стример, совместимый с Moonlight. Ближайший аналог по
техническим задачам.

**Что заимствуем как идеи (не код):**
- DXGI Desktop Duplication как основной путь захвата, WGC как фоллбэк для
  гибридной графики. Это ровно наша ситуация.
- Ultra-low-latency настройки NVENC: без B-кадров, без look-ahead, CBR.
- Отдельный поток на каждую стадию пайплайна вместо async.
- Обработка `ACCESS_LOST` как штатной ситуации, а не ошибки.

**Что делаем иначе:**
- Sunshine ориентирован на игры (геймпады, HDR, высокие битрейты). Нам это
  не нужно — приоритет на чёткости текста.
- Он использует протокол Moonlight (наследие GameStream от NVIDIA) поверх
  ENet/RTP. Мы берём QUIC — современнее, даёт шифрование и миграцию соединения.
- У него нет NAT traversal вообще (предполагается LAN или ручной проброс).
  У нас это ключевая функция.

**Лицензия — критично.** GPLv3 означает: если мы возьмём **хоть строку** его
кода, весь BetterDesk обязан стать GPLv3 с открытыми исходниками. Это
несовместимо с закрытым платным продуктом. **Читать для понимания подходов —
можно. Копировать — нельзя.** Это не формальность: копирование архитектурно
специфичного кода отслеживается и создаёт реальный юридический риск при продаже.

### 1.2. RustDesk (AGPLv3)

Ближайший аналог по функционалу и единственный крупный на Rust.

**Что заимствуем как идеи:**
- Схема «9-значный ID + сигналинг-сервер» — проверенный UX, пользователи
  её понимают.
- Портативный режим без установки — прямо соответствует вашему требованию
  «скачал и работает».
- Разделение hbbs (сигналинг) / hbbr (релей) — правильное разделение
  дешёвого и дорогого трафика.

**Что делаем иначе:**
- RustDesk использует VP8/VP9/AV1 через libvpx и часто софтверный энкод —
  отсюда его жалобы на производительность под Windows. Мы делаем только
  аппаратный H.264.
- Транспорт TCP/UDP собственный. Мы — QUIC.
- Его E2E-шифрование опционально. У нас — всегда.

**Лицензия — ещё строже.** AGPLv3 добавляет сетевую оговорку: даже
предоставление сервиса по сети обязывает открыть исходники. Для платного
SaaS это несовместимо категорически. **Код не берём ни в каком виде.**

### 1.3. Moonlight (GPLv3)

Клиент. Интересен опытом рендеринга с минимальной задержкой и
джиттер-буфером. Те же лицензионные ограничения.

### 1.4. Итог по лицензиям

| Проект | Лицензия | Можно копировать код? | Можно изучать? |
|---|---|---|---|
| Sunshine | GPLv3 | Нет | Да |
| RustDesk | AGPLv3 | Нет | Да |
| Moonlight | GPLv3 | Нет | Да |
| x264 | GPL | Нет | — |
| openh264 | BSD-2 | **Да** | Да |
| quinn, str0m, windows-rs | MIT/Apache | **Да** | Да |

**Практическое правило для работы:** идеи, архитектурные подходы и знание
«какие настройки NVENC работают» — свободны, это факты, а не авторское право.
Конкретные реализации — нет. Если возникает соблазн «просто посмотреть, как
они это сделали, и написать так же» — писать **по документации API**, а не
по чужому коду.

## Часть 2. Три варианта стека

### Вариант A — «Прагматичный»: Rust + QUIC + NVENC + Tauri ✅ ВЫБРАН

```
Захват:     DXGI Desktop Duplication (windows-rs)
Энкод:      NVENC через nvidia-video-codec-sdk (MIT) или своя bindgen-обёртка
Транспорт:  quinn (QUIC) + str0m (ICE)
Крипто:     rustls (TLS 1.3) + snow (Noise IK) поверх
Декод:      D3D11VA / Media Foundation + openh264 (софт)
Рендер:     D3D11 напрямую, отдельное Win32-окно
UI:         Tauri v2
Сервер:     Rust + axum
```

**Плюсы:**
- Один язык на весь проект, включая сервер. Для одного человека это решающе.
- Все зависимости MIT/Apache/BSD — совместимы с закрытым продуктом.
- QUIC решает разом: шифрование, миграцию соединения, congestion control,
  прохождение через middlebox'ы.
- Tauri даёт красивый UI быстро, а видео идёт мимо него — оверхеда нет.
- `windows-rs` официально поддерживается Microsoft, покрытие Win32 полное.

**Минусы, честно:**
- Rust-обёртки NVENC менее зрелые, чем C++ SDK. Возможно, придётся писать
  свою тонкую обёртку через bindgen — это 2–4 дня работы.
- Придётся написать заметный объём `unsafe`-кода для DXGI/D3D11/NVENC.
  Rust здесь не спасает, он только локализует риск.
- QUIC datagrams для видео — правильно, но требует своей фрагментации
  и порядка (QUIC даёт только доставку без гарантий).
- Экосистема аудио (WASAPI loopback) в Rust тоже тонкая.

**Почему всё равно выбран:** минусы — это разовые затраты в днях. Плюсы —
это свойства, которые сохраняются весь срок жизни проекта. Единый язык
для клиента, хоста и сервера при одном разработчике перевешивает всё.

### Вариант B — «Гибридный»: Rust + C++ для медиа

```
Ядро, транспорт, UI:  Rust
Медиа-пайплайн:       C++ библиотека (NVENC/DXGI), связь через FFI
```

**Плюсы:**
- Прямой доступ к зрелым C++ SDK от NVIDIA/AMD/Intel без обёрток.
- Больше примеров кода и документации для медиа-части.
- Меньше `unsafe`-кода **в Rust** (он переезжает в C++, где просто не виден).

**Минусы:**
- Две системы сборки (Cargo + CMake), два языка, ручной FFI-слой между ними.
  Для одного человека это ощутимый постоянный налог.
- **Главное: не даёт выигрыша в безопасности.** Небезопасный код никуда
  не исчез, он просто перестал быть помеченным. Парсинг H.264 в C++ — ровно
  тот класс кода, ради которого выбирался Rust.
- Отладка через границу FFI заметно тяжелее.

**Когда бы выбрал:** если бы в команде был человек, уже написавший
медиапайплайн на C++. При нулевом опыте в обоих — нет смысла.

### Вариант C — «Быстрый старт»: WebRTC целиком

```
Всё медиа и транспорт: webrtc-rs или libwebrtc
UI:                    Tauri или Electron
```

**Плюсы:**
- NAT traversal, шифрование, congestion control, FEC — всё уже написано
  и оттестировано миллиардами пользователей.
- Веб-клиент получается почти бесплатно — прямое попадание в ваше
  требование по браузеру.
- Первый работающий прототип — за дни, а не недели.

**Минусы:**
- **Задержка.** WebRTC оптимизирован под видеозвонки: его джиттер-буфер и
  congestion control настроены на плавность, а не на минимальную задержку.
  Типично 80–150 мс. Обойти это можно только патчами внутрь libwebrtc —
  а это огромный C++ проект.
- Навязывает SDP, SRTP, свою модель медиа — трудно вставить свой контроль
  над кадрами.
- `webrtc-rs` заметно менее зрелый, чем libwebrtc; libwebrtc из Rust — это
  фактически вариант B с худшей эргономикой.
- Ориентирован на камеру, не на экран: захват текста страдает от
  настроек, рассчитанных на лица.

**Вердикт:** прямо противоречит главной цели проекта (20–30 мс). Parsec
и Moonlight не используют WebRTC ровно по этой причине. Взять из него
**только ICE** — правильное решение, что вариант A и делает.

## Часть 3. Отдельные технические решения

### 3.1. Как безопасно обернуть C-API в Rust

Практический подход для NVENC (и любого другого C SDK):

**Слой 1 — сырые биндинги.** `bindgen` в `build.rs` генерирует объявления
из `nvEncodeAPI.h`. Это отдельный внутренний модуль, наружу не экспортируется.
Заголовки SDK **не вендорим в репозиторий** (лицензия NVIDIA SDK этого
не разрешает) — путь берётся из переменной окружения `NVENC_SDK_PATH`.

**Слой 2 — RAII-обёртки.** Каждый ресурс C-API получает Rust-тип с `Drop`:

```rust
pub struct Encoder {
    raw: *mut c_void,          // не pub — наружу не утекает
    api: NvEncApi,
}

impl Drop for Encoder {
    fn drop(&mut self) {
        // SAFETY: raw получен из nvEncOpenEncodeSessionEx и не был
        // уничтожен ранее — Drop вызывается ровно один раз.
        unsafe { (self.api.nvEncDestroyEncoder)(self.raw); }
    }
}
```

Правило: **невозможно забыть освободить ресурс**, потому что нет публичного
способа его не освободить.

**Слой 3 — безопасный API.** Публичный `trait Encoder` не содержит указателей,
принимает и возвращает только безопасные типы. Пользователь крейта физически
не может вызвать UB.

**Проверки, которые обязательны в слое 2:**
- Каждый код возврата C-API проверяется и конвертируется в `Result`.
  Игнорирование кода возврата — источник тихой порчи памяти.
- Все буферы, передаваемые в C, живут не меньше вызова (гарантируется
  временами жизни, а не комментарием).
- `Send`/`Sync` реализуются вручную и **только** после проверки по
  документации, что API потокобезопасен. По умолчанию — не реализовывать.
  Ошибочный `unsafe impl Send` — самый опасный вид ошибки, потому что
  проявляется редко и не воспроизводится.

### 3.2. Почему видео не в webview — техническое обоснование

Три независимые причины:

1. **Композитинг.** WebView2 рендерит в свою поверхность, которую затем
   композитит DWM. Это минимум один дополнительный кадр (16.6 мс при 60 Гц).
2. **Нет контроля над очередью.** Через `<video>` или MSE вы не управляете
   тем, сколько кадров браузер держит в буфере. Он оптимизирует плавность,
   а нам нужна свежесть.
3. **Лишняя конверсия.** Декодированный NV12 придётся отдать браузеру,
   он сконвертирует и загрузит обратно в GPU.

Сообщество Tauri неоднократно пыталось совместить GPU-рендер и webview
в одном окне; надёжного решения на Windows нет до сих пор. Поэтому:
**два отдельных окна**, и оверлей рисуется в D3D11, а не в HTML.

Для будущего веб-клиента это ограничение снимается через WebCodecs — но там
и цель по задержке будет другой, честно заявленной как более высокая.

### 3.3. Почему synchronous threads, а не async в пайплайне

`tokio` отлично решает задачу «10 000 соединений, каждое иногда что-то шлёт».
Наша задача обратная: «одно соединение, поток кадров с дедлайном 16.6 мс».

Async-планировщик добавляет: непредсказуемость момента запуска задачи,
возможную миграцию между потоками (потеря кэша), сложность с блокирующими
FFI-вызовами (а NVENC блокирует). Всё это — джиттер в 2–5 мс, который нам
дороже, чем удобство.

Решение: `bd-transport` и сервер — async на tokio. Пайплайн захват →
энкод → отправка и приём → декод → рендер — выделенные потоки с высоким
приоритетом и каналами `crossbeam`. Граница между мирами — одна очередь.
