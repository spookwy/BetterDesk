# Журнал измерений

Задержка — главный критерий проекта, поэтому измерения фиксируются, а не
держатся в голове. Без записи невозможно заметить регресс: «кажется, стало
медленнее» — не аргумент.

**Что записывать в каждой строке:** дату, этап, конфигурацию (железо,
разрешение, битрейт, сеть), медиану и **95-й перцентиль**, разбивку по
стадиям. p95 важнее медианы — редкие всплески ощущаются сильнее, чем
стабильное среднее (docs/latency-budget.md §4).

Методика измерения — docs/latency-budget.md §4.

| 3 | LAN, две машины | ≤ 35 мс | **вердикт не выносится** ⚠️ |
| 3 | артефакты при 1 % потерь | ≤ 200 мс | **p95 117 мс** ✅ |
| 4 | интернет, две машины | соединение по ID | **1589 кадров, 0 потерь** ✅ |
| 4 | интернет, RTT | записать | **68.6 мс** ✅ |
| 4 | интернет, glass-to-glass | ≤ 50 мс | **измерить нечем** ⚠️ |
| 6 | 3 % потерь, доля потерянных кадров | ≤ 5 % | **2.87 %** ✅ |
| 6 | интернет, 3% потерь | ≤ 70 мс, без фризов | не измерено |
| 7 | после добавления UI | не хуже этапа 6 | не измерено |

⚠️ **Задержку через интернет измерить нечем, и это не описка.**
`ClockSync` снимает смещение часов по минимуму наблюдённых разниц, а
в минимум входит и самая быстрая доставка — через интернет это
половина RTT, одинаковая для всех кадров. Она уходит в смещение и
исчезает из результата; остаётся **джиттер**, а не задержка
(находка 67). Порог 35 мс вдобавок задан для LAN, так что сравнивать
с ним интернет-прогон было бы находкой 29 в третий раз.

Честная цифра требует съёмки камерой на 240 fps (§10.4) — она
единственная не зависит от согласования часов двух машин.

\* Рендер и декод в сквозном прогоне показывают **стоимость вызова**,
а не работы: GPU исполняет команды асинхронно. Настоящая цена декода
(0.21 мс) измерена отдельно через `ID3D11Query` в `decode_probe`.
Полная цена рендера проявится только в glass-to-glass — измерении
камерой (§10.4), которое учитывает и композитор, и дисплей.

### 2026-08-30 — этап 1, проба захвата DXGI

Первое реальное измерение. Инструмент: `cargo run --release -p bd-bench
--bin capture_probe`.

**Конфигурация:** DXGI Desktop Duplication, монитор 0 (1920×1080),
таймаут `AcquireNextFrame` 16 мс, нагрузка — рисование прямоугольников
на рабочем столе, 5 секунд.

**Главный вопрос — работает ли DXGI на гибридной графике — снят: РАБОТАЕТ.**
Это ожидалось как основной риск этапа 1 (CLAUDE.md §0.1). WGC-фоллбэк
остаётся нужным для чужих машин, но не блокирует разработку.

| Метрика | Значение |
|---|---|
| Время `AcquireNextFrame`, медиана | **1.00 мс** |
| p95 | 8.41 мс |
| максимум | 426 мс |
| Кадров за 5 с | 35 |
| Таймаутов | 175 |
| Восстановлений (`ACCESS_LOST`) | 0 |

**Выводы:**

1. **Медиана 1.00 мс укладывается в бюджет** (1–2 мс,
   docs/latency-budget.md §1.1). Захват не будет узким местом.
2. **p95 8.41 мс и максимум 426 мс — это не задержка захвата.** В это
   время входит *ожидание* следующего изменения экрана: когда картинка
   статична, `AcquireNextFrame` честно ждёт до таймаута. Мерить надо
   время от появления кадра, а не время ожидания — на этапе 1 это
   разделится, когда появится полный пайплайн.
3. **31 кадр из 35 пришёл с `content_changed = false`** — то есть
   изменился только курсор. Это подтверждает пользу проверки
   `LastPresentTime != 0`: почти 90% кадров не нужно перекодировать,
   что экономит и такт энкодера, и битрейт.
4. Обнаружено 2 монитора: `\\.\DISPLAY1` 1920×1080 (основной) и
   `\\.\DISPLAY2` 1707×1067. Многомониторность (этап 11) можно будет
   тестировать локально.

### 2026-08-30 — этап 1, инициализация NVENC

Замера задержки ещё нет — кодирование кадров не написано. Зафиксирован
факт работоспособности энкодера, чтобы отделить «настроено верно» от
«медленно» на следующем шаге.

**Проверено** (`cargo run --release -p bd-bench --bin nvenc_probe`):
сессия H.264 1920×1080@60, CBR 15 Мбит/с открыта и инициализирована
на RTX 5080 Laptop, драйвер 591.91.

Настройки, влияющие на задержку, применены:

| Параметр | Значение | Зачем |
|---|---|---|
| tuning | `ULTRA_LOW_LATENCY` | профиль низкой задержки |
| preset | P3 | компромисс: чёткость текста важнее пары процентов скорости |
| `gopLength` | `NVENC_INFINITE_GOPLENGTH` | нет периодических IDR → нет всплесков битрейта |
| `frameIntervalP` | 1 | **без B-кадров**: они дают +1 кадр задержки |
| rate control | CBR | предсказуемая нагрузка на канал |
| VBV buffer | 1 кадр | энкодер не копит данные впрок |

**Замечание по версиям:** используются заголовки API 13.0, а не 13.1.
Драйвер отвергает более новые — совместимость NVENC односторонняя
(CLAUDE.md §0.1, находка 12).

### 2026-08-30 — этап 1, ЖИВОЙ ТЕСТ: захват → энкод

Первое измерение реального куска пайплайна: кадры экрана проходят
через DXGI в NVENC и выходят сжатым H.264.

**Конфигурация:** 1920×1080, H.264 CBR 15 Мбит/с, пресет P3,
ULTRA_LOW_LATENCY, без B-кадров. Нагрузка — прямоугольники,
перерисовываемые на рабочем столе. Два прогона: 8 с и 6 с.

| Метрика | Прогон 1 (8 с) | Прогон 2 (6 с) |
|---|---|---|
| Кадров закодировано | 391 | 284 |
| Частота | 48.8 fps | 47.3 fps |
| **Время энкода, медиана** | **2.29 мс** | **2.31 мс** |
| Время энкода, p95 | 2.44 мс | 2.50 мс |
| Время энкода, максимум | 4.84 мс | 4.38 мс |
| Средний битрейт | 1.0 Мбит/с | 1.3 Мбит/с |
| Размер кадра | 2.5 КБ | 3.3 КБ |
| Ключевых кадров | 1 | 1 |
| Ошибок / восстановлений | 0 | 0 |

**Вердикт: 2.3 мс против бюджета 3–6 мс — вдвое лучше плана.**

**Выводы:**

1. **Zero-copy работает.** 2.3 мс на кадр 1080p физически недостижимы
   при копировании через системную память — одна копия BGRA-кадра
   (8 МБ) стоила бы больше. Правило §4.2.3 соблюдено на практике,
   а не только на бумаге.
2. **Стабильность высокая:** разброс медианы между прогонами 0.02 мс,
   p95 всего на 8% выше медианы. Энкодер не даёт всплесков.
3. **Один ключевой кадр за весь прогон** — подтверждает, что
   бесконечный GOP работает: нет периодических IDR, значит нет
   всплесков битрейта и пиков задержки (§5.2).
4. **Битрейт 1.0–1.3 Мбит/с при лимите 15** — на синтетической
   нагрузке (сплошные прямоугольники) кодек почти не тратит биты.
   На реальном рабочем столе с текстом цифра будет выше; это не
   показатель качества, а признак того, что CBR не «добивает»
   поток до лимита впустую.
5. **48 fps вместо 60** — упирается не в энкодер, а в источник:
   DXGI отдаёт кадр только при изменении экрана, а тестовая нагрузка
   перерисовывалась каждые 6 мс не синхронно с кадрами.

**Найденный дефект (исправлен):** при завершении драйвер возвращал
`NV_ENC_ERR_DEVICE_NOT_EXIST` на освобождении буфера и регистраций.
Причина — порядок полей в структуре: Rust уничтожает их сверху вниз,
и сессия закрывалась раньше зависящих от неё ресурсов. Поле `session`
перенесено в конец. Урок записан в CLAUDE.md §0.1, находка 16.

### 2026-08-30 — этап 1, ЖИВОЙ ТЕСТ: захват → энкод → декод

Пайплайн дошёл до декодера. Кадры экрана проходят DXGI → NVENC →
Media Foundation MFT (D3D11VA) и выходят NV12-текстурой в GPU.

**Конфигурация:** 1920×1080, H.264 CBR 15 Мбит/с, декодер —
`CLSID_MSH264DecoderMFT` с `MF_LOW_LATENCY` и DXGI-менеджером
устройств. Энкодер и декодер на одном D3D11-устройстве (сети ещё нет).
Инструмент: `cargo run --release -p bd-bench --bin decode_probe`.

| Метрика | Прогон 1 (12 с) | Прогон 2 (30 с) |
|---|---|---|
| Кадров декодировано | 115 | 1176 |
| Частота | 9.6 fps | 39.2 fps |
| Вызов `decode()`, медиана | 0.04 мс | 0.03 мс |
| **Декод до готовности в GPU, медиана** | **0.25 мс** | **0.21 мс** |
| Декод до готовности в GPU, p95 | 0.35 мс | 0.36 мс |
| Декод до готовности в GPU, максимум | 0.50 мс | 0.74 мс |
| Захват→энкод→декод, медиана | 2.38 мс | 2.21 мс |
| Ошибок потока | 0 | 0 |

**Вердикт: 0.21 мс против бюджета 3–5 мс — на порядок лучше плана.**

**Как измерялось, и почему это две разные цифры.** `ProcessOutput`
возвращает текстуру, в которую GPU может ещё писать: сам вызов стоит
0.03 мс, и принять это за время декода было бы самообманом. Поэтому
после каждого кадра ставится `ID3D11Query` типа EVENT, и замер идёт
до его готовности. Разница между 0.03 и 0.21 мс — ровно та работа,
которую делает NVDEC.

**Проверено, что декодируется картинка, а не пустота.** Один кадр за
прогон копируется в staging-текстуру, и по Y-плоскости считается
разброс яркости: 0..249 и 0..234 в двух прогонах. Пустая поверхность
дала бы константу. Это единственная копия GPU→CPU в пробе, и она
намеренно вынесена в отладочный путь — в продукте её быть не должно
(CLAUDE.md §4.2.3).

Проверка добавлена не для порядка: декодер, отдающий пустые
поверхности без ошибок, показал бы точно такие же тайминги. Это
частный случай правила из находки 4 — тест, который не умеет
провалиться, ничего не доказывает.

**Выводы:**

1. **Аппаратный декод подтверждён на живом железе.** MFT принял поток
   NVENC без единой ошибки на 1176 кадрах.
2. **Кадр остаётся в GPU.** Декодер явно проверяет, что буфер
   приводится к `IMFDXGIBuffer`, и возвращает ошибку, если MFT
   свалился на системную память. Ошибка не сработала ни разу.
3. **0.21 мс — это RTX 5080.** На слабом железе цифра будет заметно
   выше, и бюджет 3–5 мс остаётся в силе как ориентир для чужих
   машин. Для тестовой машины во Франции аппаратного декода нет
   вообще — там будет софтверный путь и +8–15 мс (этап 4).
4. **Расход бюджета: 3.5 мс из 25.** Захват 1.0 + энкод 2.3 + декод
   0.2. На сеть, джиттер-буфер, рендер и композитор остаётся ~21.5 мс.

**Найденная особенность: MFT выравнивает высоту до 1088.** H.264
кодирует макроблоками 16×16, и 1080 на 16 не делится. Декодер
сообщает `MF_E_TRANSFORM_STREAM_CHANGE` и отдаёт кадры 1920×1088.
Это не дефект, а нормальное поведение: нижние 8 строк — служебное
дополнение. Рендер обязан обрезать кадр до настоящего разрешения,
иначе внизу будет полоса мусора. Записано в CLAUDE.md §0.1, находка 18.

### 2026-08-30 — этап 1, ПОЛНЫЙ ПАЙПЛАЙН: захват → энкод → декод → окно

Пайплайн этапа 1 замкнут. Кадр проходит DXGI → NVENC → MFT → D3D11
swapchain и попадает на экран. Транспорта намеренно нет: сеть скрыла
бы, где теряется время (docs/roadmap.md, этап 1, пункт 3).

**Конфигурация:** 1920×1080, H.264 CBR 15 Мбит/с, окно 960×540,
FLIP_DISCARD, `SetMaximumFrameLatency(1)`, `Present(0)` без VSync,
конверсия NV12→RGB шейдером. Инструмент:
`cargo run --release -p bd-bench --bin loopback`.

| Метрика | Прогон 1 (20 с) | Прогон 2 (30 с) |
|---|---|---|
| Кадров показано | 4613 | 6392 |
| **Задержка захват→показ, медиана** | **2.17 мс** | **2.30 мс** |
| Задержка, p95 | 2.47 мс | 2.67 мс |
| Задержка, максимум | 5.13 мс | 5.40 мс |
| Восстановлений | 0 | 0 |

Разбивка (прогон 2, медиана / p95):

| Стадия | Медиана | p95 |
|---|---|---|
| encode | 2.24 мс | 2.49 мс |
| decode | 0.02 мс | 0.17 мс |
| render | 0.01 мс | 0.14 мс |

**Вердикт: 2.30 мс против критерия 25 мс.**

**Что эта цифра НЕ означает.** Три оговорки, без которых число
вводит в заблуждение:

1. **Decode и render здесь — стоимость вызова, а не работы.** GPU
   исполняет команды асинхронно, и 0.02 мс — это время, за которое
   `ProcessOutput` вернул управление. Настоящая цена декода измерена
   отдельно в `decode_probe` через `ID3D11Query`: **0.21 мс**. То же
   с рендером — реальная работа шейдера видна только в
   glass-to-glass.
2. **Это не glass-to-glass.** Не учтено ожидание кадра до захвата
   (~8 мс при 60 Гц, неустранимо) и задержка самого дисплея
   (docs/latency-budget.md §2). Честная проверка — камера на 240 fps
   (§10.4), и она даст цифру заметно выше.
3. **fps в этом прогоне не значим.** 213 fps физически невозможны от
   монитора 60 Гц: окно вывода стояло на захватываемом экране и
   питало само себя изменениями. На задержку это не влияет — каждый
   кадр измеряется отдельно, — но fps в таком прогоне ничего не
   говорит. Для честного fps нужен `--monitor 1` с окном на другом
   экране.

**Контрольный прогон на втором мониторе** (2560×1600, без петли):
медиана 5.11 мс, p95 5.42, 706 кадров за 20 с (35 fps). Рост
относительно 1080p объясняется площадью кадра: энкод 5.05 мс против
2.24 — кадр в 2 раза больше.

**Найденный дефект (исправлен): декодер отдаёт поверхности, не
пригодные для шейдера.** `CreateShaderResourceView` возвращал
`E_INVALIDARG`, потому что MFT создавал текстуры только с
`D3D11_BIND_DECODER` (флаги `0x200`). Лечится атрибутом
`MF_SA_D3D11_BINDFLAGS` на выходном потоке, выставленным **до**
`MFT_MESSAGE_NOTIFY_BEGIN_STREAMING` — после этого пул уже выделен.
Стало `0x208` (`DECODER | SHADER_RESOURCE`). Без этого рендеру
пришлось бы копировать каждый кадр в свою текстуру — лишний проход
по 3 МБ 60 раз в секунду. Записано в CLAUDE.md §0.1, находка 23.

**Найденный дефект (исправлен): стадия decode пропадала из отчёта.**
`FrameTimings::breakdown()` строил интервалы только между *соседними*
стадиями. На этапе 1 транспорта нет, `Sent` и `Received` не
отмечены — и время декода, попадавшее в несуществующую пару
`Received → Decoded`, исчезало из разбивки бесследно. Итоговая
задержка при этом оставалась верной, поэтому дефект не проявлялся
ничем, кроме отсутствующей строки. Теперь пары строятся по
фактически отмеченным стадиям, и добавлен тест
`breakdown_sums_to_total`: сумма стадий обязана сходиться с итогом.

### 2026-08-30 — этап 1, восстановление после ACCESS_LOST

**Найден и исправлен дефект, из-за которого восстановление
не работало вообще.** Это критерий этапа 1 («смена разрешения и
UAC-диалог не роняют процесс»), и до проверки он считался
выполненным — код обработки `ACCESS_LOST` был написан с самого
начала.

**Что было не так, две ошибки подряд:**

1. `recover()` пересоздавал **устройство D3D11**. Но `ACCESS_LOST`
   означает потерю дупликации, а не устройства — потеря устройства
   это `DEVICE_REMOVED`. На устройстве захвата живут энкодер,
   декодер и окно вывода: подменив его, восстановление оставляло
   весь стек с мёртвым указателем.
2. Новая дупликация создавалась **до** освобождения старой. DXGI
   разрешает одну дупликацию на выход в пределах процесса, поэтому
   `DuplicateOutput` возвращал `E_INVALIDARG`. Присваивание полю
   не спасает: оно освобождает старое значение только после того,
   как новое уже создано.

Вторая ошибка перекрывала первую: восстановление падало раньше, чем
успевало навредить. **Итог: ни один `ACCESS_LOST` не был бы
пережит.** Первый же UAC-диалог обрывал бы сессию.

**Почему дефект дожил до сих пор.** `ACCESS_LOST` не случается по
команде, и все предыдущие прогоны показывали «Восстановлений: 0».
Нулевой счётчик читался как «всё хорошо», хотя означал лишь, что
путь ни разу не исполнялся. Тот же урок, что и находка 4:
**проверка, которая не исполняется, ничего не доказывает.**

**Как проверено теперь.** Написана проба `recover_probe`, которая
вызывает `recover()` принудительно и проверяет, что указатель на
устройство не изменился. Проба сначала **запущена на сломанной
версии и провалилась**, и только потом — на исправленной:

```
До восстановления:  устройство 0x1593469d230, 1920x1080
  проход 1..3: восстановление прошло, кадры идут
После восстановления: устройство 0x1593469d230, 1920x1080
✅ Устройство пережило 3 восстановления неизменным.
```

Остаётся непроверенным на живом железе: смена разрешения и UAC как
источники события. Сама обработка теперь работает, но сценарий
«разрешение изменилось → энкодер настроен на старый размер»
требует пересоздания стека кодеков, и этого кода ещё нет —
капчурер только пишет предупреждение в лог.

### 2026-08-30 — этап 1, оверлей статистики

Критерий этапа 1 «задержка выводится на экран в реальном времени»
закрыт. До этого цифра существовала только в консоли — то есть была
доступна разработчику и недоступна никому больше.

**Реализация:** Direct2D + DirectWrite поверх поверхности swapchain
(`CreateDxgiSurfaceRenderTarget`). Текст рисуется **в тот же
D3D11**, что и видео (CLAUDE.md §6.1), без промежуточных текстур и
без копий в системную память.

Показывается: число кадров, fps, медиана и p95 задержки, разбивка по
стадиям. Переключается клавишей **F9** — §10.4 требует доступности
оверлея в любой сборке, а не только в отладочной.

**Три решения, каждое со своей причиной:**

1. **Отметка `Presented` ставится после отрисовки оверлея.** Оверлей
   — часть кадра, и его стоимость обязана попасть в замер. Поставить
   отметку раньше значило бы спрятать её цену от самого измерения,
   которое эта цифра и обслуживает.
2. **Строки пересчитываются 4 раза в секунду, а не каждый кадр.**
   При 60 fps цифры менялись бы быстрее, чем глаз успевает читать,
   а форматирование строк в горячем пути — лишняя аллокация на кадр.
3. **Цель вывода D2D отпускается перед `ResizeBuffers`.** Она держит
   поверхность заднего буфера, и без этого изменение размера окна
   возвращало бы ошибку — ровно та же причина, по которой
   отпускается представление заднего буфера.

Шрифт моноширинный (Consolas): пропорциональный заставлял бы цифры
прыгать по горизонтали при каждом обновлении.

### 2026-08-30 — этап 1, транспорт-заглушка в памяти

Последний пункт этапа 1: между энкодером и декодером появился
транспорт. Не QUIC — заглушка в памяти (docs/roadmap.md, этап 1,
пункт 3), потому что настоящая сеть на этом шаге скрыла бы, сколько
стоит наш собственный код.

**Но заглушка не прокидывает байты насквозь.** Она делает всё, кроме
собственно сети: нумерует кадры, режет их на датаграмы по 1200 байт,
собирает обратно на приёме, считает потери. Причина — на этапе 3
замена коснётся только доставки датаграмов, а фрагментация и сборка
уже будут отлажены здесь, где потери вносятся воспроизводимо, а не
поверх незнакомой сети, где к ним добавятся ещё и чужие сюрпризы.

**Конфигурация:** 1920×1080@60, H.264 CBR 15 Мбит/с, NVENC → заглушка
→ D3D11VA, RTX 5080 Laptop. Монитор 0, окно на нём же (fps не значим,
находка 25).

даст не «слегка хуже картинку», а неработоспособную сессию. Это
превращает пункт «FEC для видео» из желательного в обязательный и
задаёт ему проверяемую цель: при 3 % потерь доля потерянных кадров
должна упасть с 51 % до единиц процентов.

**Целостность.** Проба сверяет байты каждого доставленного кадра с

испорченный при сборке поток H.264 декодер чаще всего проглотит
молча, выдав мутную картинку вместо ошибки — тот же урок, что

**Ветка потерь исполнена по-настоящему.** На профиле mobile путь

прямое следствие находки 26: профиль без потерь оставил бы этот код
в состоянии «написан, но ни разу не исполнялся», а нулевой счётчик
читался бы как «работает».

### 2026-08-30 — этап 1, устранение периодической пикселизации

**Симптом от пользователя:** в окне `loopback` картинка в целом
стабильна, но раз в пару секунд на ~0.5 с вся она грубеет крупными
квадратами. Постоянно, независимо от действий.

#### Как искали

Первая гипотеза была неверной, и это стоило бы времени, если бы её
не проверили измерением. Предполагалось, что виноваты полные IDR:
при CBR с VBV размером в один кадр ключевой кадр не помещается в
бюджет, энкодер огрубляет картинку. Гипотеза выглядела убедительно,
потому что `intra_refresh` в конфиге объявлен, но к NVENC **не
применяется** — то есть обновление действительно шло полными IDR.

Проба `quality_probe` гипотезу **опровергла**: за 40 с ключевой
кадр был **один**, и всплески размера к нему не привязаны (0 %).
Правка энкодера под IDR не дала бы ничего.

Настоящая причина нашлась в счётчике частоты:

| Прогон | Кадров/с | Медиана разностного кадра |
|---|---|---|
| Монитор 0, окно на нём же | 222 | 2 301 Б |
| Монитор 1, петли нет | 32 | 12 071 Б |

**Кадры различаются в 5.2 раза при одном и том же битрейте.**

Механика простая и не зависит от петли обратной связи: DXGI отдаёт
кадр на каждое изменение экрана, а не 60 раз в секунду. Все они шли
в энкодер. CBR делит фиксированные 15 Мбит/с на **фактическое**
число кадров: при 222 кадрах/с каждому достаётся втрое меньше бит,
чем заложено в VBV, и энкодер огрубляет картинку, чтобы уложиться.

Петля обратной связи из находки 25 (окно вывода на захватываемом
экране) лишь доводила частоту до предела. **Раньше считалось, что
она влияет только на осмысленность цифры fps** — оказалось, и на
качество тоже.

#### Что исправлено

1. **`bd_core::FrameLimiter`** — ограничение частоты кодирования
   (новый модуль `pacing.rs`, 6 тестов). Лишний кадр не кодируется:
   его содержимое всё равно войдёт в следующий, а биты достанутся
   тем кадрам, которые пользователь увидит. Лимитер **не спит** —
   ожидание в горячем пути остановило бы захват и сделало следующий
   кадр устаревшим.

2. **`maxQP = 38`** — потолок огрубления. Без него энкодер при
   нехватке бит уходил в QP 45–51, где картинка распадается на
   квадраты. Цена: в редких сценах поток может превысить заданный
   битрейт. Для рабочего стола размен верный — нечитаемый текст
   хуже короткого всплеска трафика.

3. **VBV 1.5 кадра вместо 1.0** — буфер ровно в кадр упирался в
   потолок при любом всплеске сложности сцены, и качество проседало
   рывком. Полтора кадра дают запас, оставаясь много меньше кадра
   задержки.

4. **`enableAQ = 1`** — адаптивное квантование: биты идут туда, где
   артефакты заметнее, то есть в текст (главный сценарий, §7.2).
   Без AQ энкодер огрубляет кадр равномерно, и текст «плывёт» первым.

5. **`maxBitRate = averageBitRate`** для CBR — пресет оставлял здесь
   своё значение, и если оно меньше нашего среднего, контроллер
   молча зажимает поток. Ошибки при этом нет, есть только просевшее
   качество.

6. **`enableLookahead = 0`** явно — пресет мог включить его сам,
   а look-ahead копит кадры до кодирования, то есть прямо добавляет
   задержку (§5.2). Бюджет уехал бы незаметно.

#### Результат

Сопоставимая нагрузка (монитор 1, ~30 кадров/с):

| | До | После |
|---|---|---|
| Медиана разностного кадра | 12 071 Б | **17 540 Б** |

**+45 % бит на кадр при той же сцене.** Задержка не пострадала:
медиана 4.88 мс (encode 4.47 мс).

На мониторе 0 с петлёй: лимитер отбросил 873 лишних кадра из 2701.

**Проверено пользователем визуально: пикселизация исчезла
полностью.** Это и есть главный критерий — цифры лишь объясняют,
почему.

#### Урок

**Гипотеза, объясняющая симптом, ещё не является причиной.** Версия
про IDR была правдоподобной и опиралась на реальный дефект (не
применённый `intra_refresh`). Проба её опровергла за один прогон —
дешевле, чем правка энкодера, которая ничего бы не изменила и
создала бы ложную уверенность, что проблема решена.

Второй урок: **счётчик, который меряет не то, ради чего заведён,
маскирует дефект.** Fps считался «неинформативным в этом прогоне»
из-за петли обратной связи (находка 25) — и на него перестали
смотреть. А он всё это время показывал настоящую причину.

**Задержка не росла за прогон:** 23.58 мс на 1684-м кадре →

(очередь датаграмов, журнал отправленных кадров) нет.

**Вывод: критерий выполнен, этап 1 закрыт.** Пайплайн без сети —

#### Оговорка к строке `network` — 20.44 мс вместо заявленной 1 мс

Эта строка **не** означает, что канал стоит 20 мс. Профиль `lan`
задаёт 1 мс, и транспорт её соблюдает. Остальные 19 мс — свойство
пробы: `loopback` делает один `receive()` на один `send()`, а при
ненулевой задержке кадр не готов в той же итерации, где отправлен.
Он забирается на следующей, и к задержке канала прибавляется шаг
цикла кодирования (~17 мс при 60 fps).

Проверено тестом `delayed_link_never_delivers_in_the_sending_iteration`:
на канале с задержкой ни одна из 20 попыток не отдала кадр в своей
итерации. В настоящем клиенте приём идёт своим потоком и такта
энкодера не ждёт, поэтому на продукт это не переносится.

**До исправления отчёт врал** (находка 34): вердикт вычитал из итога
заявленную профилем задержку (1 мс) вместо измеренной стадии (20 мс),
и 19 мс записывались в счёт пайплайна. Прогон рапортовал «пайплайн
22.29 мс» там, где на деле 3 мс. Критерий формально выполнялся
(22.29 ≤ 25), поэтому расхождение не разбирали.

Сверка после правки — совпадение, которого и следовало ожидать:

| Профиль | Задержка канала | Пайплайн без сети |
|---|---|---|
| `perfect` | 0 мс | 3.06 мс |
| `lan` | 1 мс | 3.00 мс |

#### Эффект агитатора

Измерен отдельно, чтобы флаг не оказался инструментом, незаметно
меняющим цифры:

| Режим | Кадров за 20 с |
|---|---|
| без `--agitate` (бездействие) | 143 |
| с `--agitate` (бездействие) | 1047 |

Задержка в обоих случаях та же (~3 мс): агитатор даёт поток кадров,
а не ускоряет пайплайн.

Стадия `network` в `loopback` через QUIC показывала **20.44 мс** на

на клиенте, включая ожидание своей очереди в потоке QUIC и сам
`ClockSync`, оценка которого на коротком прогоне ещё грубая.
Сколько из этого неустранимо — вопрос замера **между двумя
машинами**, где появится настоящий RTT; на одной машине разделить
эти составляющие нечем.

**Чего этот замер НЕ доказывает.** Критерий этапа 3 сформулирован
как «≤ 35 мс в LAN **между двумя реальными машинами**». Здесь обе
стороны на одной машине, поэтому вердикт «✅ 8.02 ≤ 35» относится

ровно ошибка находки 29 (вердикт не о том, что измерено).


### 2026-09-01 — этап 3/6, FEC (Reed-Solomon): потери кадров 38.8 → 2.9 %

**Конфигурация:** 2560×1600, профиль `mobile` (3 % потерь, 80 мс,
джиттер 40 мс), заглушка транспорта, 25 с на прогон.

Заглушка, а не QUIC, выбрана намеренно: потери здесь вносятся
**воспроизводимо**, и два прогона можно сравнить. Через настоящую
сеть разница утонула бы в шуме канала.

| | потеряно кадров | вытеснено с паритетом | показано |
|---|---|---|---|
| без FEC | 38.83 % | — | 906 (36.2 fps) |
| с FEC 25 % | **2.87 %** | 43 | **1450 (58.0 fps)** |

**Критерий этапа 6 («при 3 % потерь ≤ 5 % кадров») выполнен** — на
этапе 3, раньше срока: без FEC прогон через интернет дал бы рваную
картинку, а он был условием закрытия этапов 3 и 4.

#### Заодно закрылся критерий этапа 3

Профиль `lossy` (ровно 1 %, под формулировку критерия):

| | потеряно кадров | p95 восстановления |
|---|---|---|
| без FEC | 12.20 % | 884 мс |
| с FEC | **0.53 %** | **50 мс** |

На 2560×1600 без FEC p95 доходил до 1149 мс при пороге 200. Причина
была предсказана находкой 53 и подтвердилась: **ключевые кадры сами
терялись**, потому что идут 63 фрагментами, и `0.99⁶³ ≈ 53 %`.

Задержка не пострадала: p95 37.18 → 40.57 мс.

#### Почему Reed-Solomon, а не XOR — посчитано ДО кода

При одинаковой избыточности 25 %:

| фрагментов в кадре | XOR по группам | Reed-Solomon |
|---|---|---|
| 22 (разностный) | 4.4 % потерь | 0.0 % |
| 63 (ключевой) | **12.4 % потерь** | 0.0 % |

XOR проваливает критерий ровно на **ключевых** кадрах, чья потеря
дороже всего: он защищает группы по отдельности, RS тратит ту же
избыточность на кадр целиком.

#### Что стоило дороже всего

Первая версия **ухудшила** результат — 45.7 % против 38.8 %. Три
правдоподобных объяснения опровергнуты замером (нехватка вызовов
`receive` — цикл крутился чаще; вытеснение по ёмкости — та же ёмкость
в тесте давала 5 %; переупорядочивание — порядок сохранялся). Ответил
счётчик: **499 кадров выброшено при живом паритете** против 45
восстановленных.

Паритет слался **после** данных, и кадр, ждущий его, вытеснялся
следующим — гибель за шаг до спасения. Лечится перемежением.

**Оговорка к цифре «восстановлено».** Она честная (кадры, собранные
с участием паритета), но читается как «спасено». Паритет перемежён с
данными, поэтому условие «хватает» выполняется досрочно — когда
недостающие фрагменты ещё **в пути**. Отличить «потеряно» от «в пути»
на приёме нельзя, это свойство задачи. Замер показал, что ожидание
дороже лишней работы: 2.87 % потерь при «чинить сразу» против 6.2 %
при «ждать хвоста». Сколько FEC спас на самом деле, показывает только
сравнение двух прогонов.

### 2026-09-01 — этапы 3 и 4 ЗАКРЫТЫ: две машины через интернет

**Конфигурация:** хост — Москва (RTX 5080, 2560×1600), клиент —
Франция (машина Максима), сигналинг — Oracle Cloud, Франкфурт.
Два разных роутера, обе стороны за NAT.

**Итог: 1589 кадров, 0 потерь, RTT 68.6 мс.** Максим видел экран.
NAT пробился с первой попытки с обеих сторон.

Этим прогоном закрыты сразу четыре висевших пункта: hole punching
через разные роутеры, замер между двумя машинами, пароль сессии на
живом канале и подключение по ID через интернет.

#### Чего этот прогон НЕ измерил

Отчёт напечатал «медиана 13.99 мс» при RTT 68.6 мс — **меньше
половины RTT**, то есть быстрее света. И бодрое «✅ критерий этапа 3
выполнен» под этим.

Причина в `ClockSync` (находка 67): половина RTT одинакова для всех
кадров, уходит в оценку смещения часов и исчезает из результата.
Остаётся джиттер. Ограничение было **записано в самом `ClockSync`** и
до этого дня ничего не стоило: в LAN половина RTT — доли миллисекунды.

Верхняя оценка задержки: **≥ 34.3 мс** (половина RTT) плюс пайплайн
~8 мс, то есть порядка 40–45 мс. Это оценка, а не измерение.

**Настоящей цифры задержки через интернет у проекта нет.** Клиент
теперь печатает объяснение вместо галочки, а честная проверка —
съёмка камерой на 240 fps (§10.4).

#### Три дефекта, найденные прогоном, — и ни один не сетевой

- хост давал на ввод пароля 60 с; человек диктовал его голосом и
  уложился в 70 — сессия закрылась за десять секунд до ввода.
  Выглядело как сетевая ошибка при исправном канале;
- хост печатал «Жду клиента (300 с)», а ждал 90;
- «Неверный пароль» печаталось на служебный зонд, до ввода.

Все три не проявляются на localhost: там пароль виден в соседнем
окне, а обе стороны запускаются одной рукой подряд. **Тайминги были
рассчитаны на машину, а не на человека.**

### 2026-09-02 — этап 5: опознание хоста не стоит задержки

**Конфигурация:** 1920×1080@60, NVENC, CBR 15 Мбит/с, обе стороны на
одной машине (замер пайплайна, не сети — см. оговорку ниже).

Вопрос замера был один: **не подорожало ли рукопожатие**. Опознание
добавляет к нему два сообщения и одну проверку подписи Ed25519.

| | медиана | p95 | кадров |
|---|---|---|---|
| до опознания (прогон с паролем) | 9.15 мс | 13.52 мс | 838 |
| после, по ID с пиннингом | **8.95 мс** | 13.30 мс | 332 |

Разница в пределах шума между прогонами. Это и ожидалось: подпись
Ed25519 проверяется **один раз за сессию**, а не на кадр, и стоит
десятки микросекунд против 8.95 мс пути кадра.

Время от установления соединения до создания окна — **74 мс** на
прогоне с паролем: опознание, пароль и Argon2 вместе.

#### Три ветки пиннинга, проверенные живьём

Проверка на способность провалиться (находка 4) здесь не
формальность: модуль, который не умеет остановить подмену, не
защищает ни от чего.

| ветка | что сделано | результат |
|---|---|---|
| первая встреча | чистый `known_hosts` | отпечаток показан, совпал с хостовым, запомнен |
| известный ключ | повторное подключение | «Машина опознана», молча, exit 0 |
| **подмена** | чужой ключ подставлен в `known_hosts` | **подключение остановлено, exit 1**, оба отпечатка показаны |

Третья строка и есть смысл работы. До неё дыра выглядела так: хост
на публичном сигналинге, клиент подключается по девяти цифрам и
диктует пароль — кому угодно, кто занял этот ID.

#### Что этот замер НЕ доказывает

Обе стороны на одной машине, поэтому цифра относится к пайплайну, а
не к критерию этапа 3 (записано в самой пробе). И опознание здесь
проверено против **подмены записи в файле**, а не против настоящего
подставного хоста в сети: второе требует второй машины и злого
умысла, первое воспроизводит ровно то состояние, на которое код
реагирует.

Разница существенна — ровно та, о которой находки 32 и 59: проверка
воспроизводит не то состояние, ради которого написана. Здесь она
покрывает **сличение и реакцию**, но не путь, которым чужой ключ
попадает в сеть.

### 2026-09-02 — этап 5: DPAPI и подтверждение человеком

**Конфигурация:** 1920×1080@60, NVENC, CBR 15 Мбит/с, обе стороны на
одной машине (замер пайплайна, не сети).

Вопрос тот же, что и у опознания: **не подорожал ли запуск**. DPAPI
вызывается один раз при старте хоста, `--ask` добавляет ожидание
человека в рукопожатие.

| прогон | медиана | p95 | кадров |
|---|---|---|---|
| до DPAPI (опознание с пиннингом) | 8.95 мс | 13.30 мс | 332 |
| `--ask` с ответом «y» | 8.39 мс | 12.99 мс | 502 |
| после DPAPI, подключение по ID | **8.63 мс** | 13.67 мс | 327 |

Разброс в пределах шума. Иначе и быть не могло: `CryptProtectData`
зовётся один раз за запуск, а не на кадр.

#### Миграция ключа: проверено на живом файле

Главный риск был не в скорости, а в **потере личности машины**.

| | размер `device.key` | первые байты | отпечаток |
|---|---|---|---|
| до | 32 байта | `9a57 ec5f 73b5 6117` (сам ключ) | `CCFC 3D03 1633 89F9…` |
| после | 262 байта | `0100 0000 d08c 9ddf` (блоб DPAPI) | `CCFC 3D03 1633 89F9…` |

**Отпечаток не изменился** — значит запись в `known_hosts` у клиента
осталась годной, и подключение прошло с «Машина опознана по
сохранённому ключу», без предупреждения о подмене.

Второй запуск переноса уже не делает (в логе нет строки «перенесён
под защиту DPAPI»), отпечаток прежний.

#### Что проверено на способность провалиться

Проверки, подменённые нарочно, чтобы убедиться, что они умеют падать
(находка 4):

| подмена | что упало |
|---|---|
| `protect` возвращает вход без шифрования | `sealed_bytes_do_not_contain_the_secret`, `file_on_disk_does_not_contain_the_raw_key` |
| миграция пропущена | `plain_key_survives_migration`, `migration_actually_encrypts_the_file` |

Вторая строка важнее: без неё «миграция работает» было бы
непроверяемым утверждением, а цена ошибки — ложная тревога о подмене
у всех, кто машину запомнил.

#### Чего этот замер НЕ доказывает

Что ключ защищён **от всего**. DPAPI расшифрует его для любого
процесса, работающего под тем же пользователем, — это его устройство,
а не наш недосмотр (записано в шапке `bd-secrets`). Закрывается
кража файла, а не локальный вредонос.
